# 项目实现总结与后续计划

更新日期：2026-08-21

## 1. 文档目的

本文总结当前 RK3568 实时音视频边缘分析网关已经实现的代码、每个模块解决的问题、
使用的核心知识点，以及完成当前 Mock 阶段后应当如何继续开发。

本文只描述仓库中已经存在并通过测试的能力。V4L2、ALSA、RKNN、RGA、MPP、H.264、
AAC、MP4 和 RTSP 尚未接入，不能在简历或面试中表述为已经完成。

## 2. 当前阶段一句话结论

项目已经完成一套不依赖摄像头、麦克风和 Rockchip SDK 的企业级 Mock 音视频管道：
它可以按真实节拍生成视频帧和音频块，经过模拟推理、校验编码、独立输出、指标监控和
故障恢复后安全停止，并通过 30 项单元与集成测试。

当前成果的价值不是“做出了能播放的视频”，而是先建立了后续真实硬件接入所需的稳定
接口、数据契约、线程模型、时间戳体系、背压策略、故障模型和回归测试基线。

## 4. 整体架构

### 4.1 数据流

```text
                           +-> 推理有界队列 -> MockInferenceEngine
                           |                    |
MockVideoCapture -> 一帧 --+                    +-> 最新检测结果快照
                           |
                           +-> 视频编码队列 -> ChecksumVideoEncoder --+
                                                                     |
MockAudioCapture -> 音频有界队列 -> ChecksumAudioEncoder ------------+-> PacketRouter
                                                                        |-> Null Sink
                                                                        `-> JSONL Sink
```

监控线程不直接处理媒体数据，它定期读取 worker 进展、队列状态、错误和延迟指标。当某个
本应运行的线程长期没有成功处理数据时，监控线程把“线程还活着但业务已卡死”的情况升级
为致命错误。

### 4.2 分层关系

```text
rkav_core     公共类型、错误、时钟、队列、配置、指标、几何算法
    ^
rkav_mock     Mock 采集、Mock 推理、Checksum 编码
    ^
rkav_app      Application、PacketRouter、Sink
    ^
rkav-gateway  命令行、信号、日志初始化和进程退出码
```

这样分层的目的，是让硬件 SDK 不进入公共核心。以后增加 V4L2、ALSA、RKNN 或 MPP 时，
新增具体后端并通过接口注入，不需要重写队列、时间戳、配置、监控和主生命周期。

## 5. 各模块实现说明

### 5.1 工程和构建系统

已经实现：

- 使用 CMake 将项目拆分为 `rkav_core`、`rkav_mock`、`rkav_app` 和可执行程序。
- 使用 `PUBLIC`/`PRIVATE` 控制头文件、链接库和编译选项的传播范围。
- 提供 Mock、V4L2、ALSA、RKNN、RGA、MPP 等编译开关；当前只开启 Mock。
- GCC/Clang 开启 `-Wall -Wextra -Wpedantic -Wconversion -Wshadow` 和 `-Werror`。
- 提供 Debug、Release、ASan/UBSan 构建入口和 Windows/Linux 构建脚本。
- GitHub Actions 配置格式检查、静态分析、Debug 测试和 Sanitizer 测试。

涉及知识点：

- 现代 CMake target 化管理。
- 依赖传播和编译边界。
- 条件编译与可选后端。
- 编译期质量门禁、静态分析和 Sanitizer。
- Debug 与 Release 构建差异。

### 5.2 Error 和 Result 错误模型

项目没有使用裸整数或一段字符串表达全部失败，而是定义结构化 `Error`：错误类别、
系统错误码、模块、操作、消息和是否可重试。`Result<T>` 同时承载成功值或错误。

这使调用方可以区分：

- 配置错误：启动前直接拒绝。
- 状态错误：例如重复 Open、Flush 后继续 Encode。
- 可恢复错误：例如音频 XRUN。
- 设备持续失联：先退避重试，再由健康检查判断无进展。
- 致命输出错误：由 Application 保存第一个根因并请求全局停止。

涉及知识点：

- 代数数据类型思想，即“成功值或失败值”。
- 模板和 `std::variant`。
- 显式错误传播，避免异常跨工作线程传播。
- 错误分类、上下文补充和根因保留。

### 5.3 Buffer、Frame 和 Packet 数据契约

实现了统一的 `Buffer`、`VideoFrame`、`AudioFrame`、`DetectionBatch` 和
`EncodedPacket`。数据不仅包含字节，还包含序号、PTS/DTS、格式、尺寸、stride、时间基
和内存类型等元数据。

关键约束包括：

- RGB888 的 stride 不能小于 `width * 3`。
- Buffer 字节数必须能容纳声明的图像或 PCM 样本。
- 音频采样率、声道数、每声道样本数必须有效。
- 编码包必须有合法时间基、codec 和 payload。
- `shared_ptr<Buffer>` 允许一帧分发给多个只读消费者而不复制大块内存。
- `MemoryKind` 和 DMA-BUF 描述为后续零拷贝链路预留扩展点。

涉及知识点：

- 音视频字节布局、像素格式和 PCM 布局。
- stride 与 width 的区别。
- PTS、DTS、time_base。
- RAII、共享所有权和只读扇出。
- 在模块边界校验数据不变量。

### 5.4 单调时钟、节拍器和时间戳换算

管道内部统一使用微秒级单调时钟，不使用会受到系统校时影响的墙上时间。视频帧 deadline
从固定起点和帧序号计算，而不是每帧简单 `sleep_for(33ms)`。

例如 30 FPS 的理论周期不是整数微秒。如果每次都把周期截断后累加，运行越久误差越大；
从绝对起点计算第 N 帧 deadline，可以把舍入误差限制在一个时间刻度内。

项目还提供 `ManualClock`，测试可以手动推进时间，不必真的等待几秒钟。

涉及知识点：

- `std::chrono::steady_clock`。
- 相对时间、绝对 deadline 和累计漂移。
- 有理数时间基换算及整数溢出检查。
- 依赖注入和可测试时间。
- `condition_variable` 与 `stop_token` 协作取消。

### 5.5 有界队列和背压

所有跨线程数据通道都使用固定容量 `BoundedQueue<T>`，没有使用无限增长容器。队列支持：

- `block_producer`：满时阻塞生产者，适合不能静默丢失的音频。
- `drop_newest`：丢掉刚到的数据。
- `drop_oldest`：丢掉最老数据，适合保持视频新鲜度。
- `keep_latest`：清空旧数据，只保留最新数据，适合实时推理。
- `Drain`：停止后处理完存量数据。
- `Abort`：发生致命错误时立即清空并退出。
- 超时、取消、关闭、高水位、丢弃数和吞吐统计。

涉及知识点：

- 生产者/消费者模型。
- 互斥锁、条件变量和虚假唤醒。
- 背压与实时系统中的延迟/完整性取舍。
- `std::stop_token`、`std::stop_callback` 和可取消阻塞。
- 线程安全快照与统计一致性。

### 5.6 Mock 视频采集

`MockVideoCapture` 按配置的宽、高和 FPS 生成 RGB888 测试图，包括色条、移动目标框和帧号。
相同配置与帧序号产生确定结果，因此测试失败可以稳定复现。

它还支持读取延迟、指定帧后失败和连续失败等故障注入，用来验证重试和监控逻辑。

涉及知识点：

- RGB888 内存布局和逐像素写入。
- 帧率调度和序号驱动的确定性数据。
- Open/Read/Close 状态机。
- 故障注入与可重复测试。

### 5.7 Mock 音频采集

`MockAudioCapture` 可生成静音或连续正弦波 S16_LE PCM。它按采样率和块时长计算每块样本数，
并在不同音频块之间保存相位，避免每个块都从零相位开始造成波形不连续。

XRUN 注入后，Application 调用 `Recover()` 并重试同一个逻辑块，因此不会偷偷跳过一段
音频 PTS。持续断连则进入带退避的重试，最终由健康监控报告卡死。

涉及知识点：

- PCM、采样率、声道、S16_LE 和交错样本。
- 正弦波离散采样、幅值缩放和相位连续性。
- 音频时间戳连续性。
- ALSA XRUN 的抽象恢复契约。
- 可恢复错误与持续故障的区别。

### 5.8 图像几何和 Mock 推理

实现了 letterbox 缩放元数据和检测框逆变换。模型通常要求固定输入尺寸，原图等比例缩放
后会产生补边；模型输出框必须先减去补边，再除以缩放比例，最后裁剪到原图边界。

`MockInferenceEngine` 模拟推理耗时，并根据输入帧生成确定检测结果。检测结果保存源帧序号、
源 PTS 和完成时间，视频编码线程可以判断结果是否来自正确帧以及是否过期。

涉及知识点：

- letterbox、坐标系变换和边界裁剪。
- 推理前处理/后处理的数据契约。
- 实时结果的新鲜度，而不只是“有没有结果”。
- 不可变快照与跨线程共享。

### 5.9 Checksum Encoder

当前编码器不生成 H.264 或 AAC，而是校验输入后计算摘要，生成带明确 Mock codec 标识的包。
这样可以在没有 MPP/FFmpeg 时验证编码阶段的状态机、时间戳、关键帧周期、音频连续性和
PacketRouter，而不会把随机字节伪装成真实码流。

编码器实现了 `Open -> Encode -> Flush -> Close` 生命周期，并拒绝错误调用顺序。

涉及知识点：

- 编码器状态机和 Flush 语义。
- 输入一帧不一定输出一个包的接口设计。
- 音视频包时间基。
- 校验和用于数据链路正确性验证。

### 5.10 PacketRouter 和输出隔离

每个 Sink 都有自己的有界队列和消费线程。编码线程只做快速投递，不直接执行磁盘或网络
I/O。因此一个慢 Sink 只会填满自己的队列，不会拖住其他 Sink 和采集线程。

输出支持：

- `NullPacketSink`：不保存 payload，但校验包结构及每路 DTS 单调性。
- `JsonlPacketSink`：把包元数据写成逐行 JSON，便于人工检查。
- `required=true`：失败会停止整个管道。
- `required=false`：失败后隔离该 Sink，其他链路继续运行。

涉及知识点：

- 扇出、独立消费者和故障隔离。
- 慢 I/O 与实时线程解耦。
- required/optional 依赖语义。
- DTS 单调性和输出状态机。

### 5.11 配置系统

配置流程不是简单读取 JSON，而是：读取文件、解析类型、拒绝未知字段、填充默认值、执行
范围检查和跨字段语义检查。

典型检查包括：

- 拼错 `fps` 不能静默采用默认值。
- 音频采样率乘块时长必须得到整数样本数。
- 至少有一个输出启用。
- Sink 模拟延迟不能达到关闭期限。
- worker 卡死超时不能短于正常最慢阶段的工作周期。
- 选择尚未编译的真实后端必须在创建线程前失败。

涉及知识点：

- JSON 到强类型配置映射。
- schema 版本、白名单字段和 fail-fast。
- 单字段校验与跨字段约束。
- 配置错误的精确路径定位。

### 5.12 日志、指标和健康检查

日志采用单行 JSON，包含时间、级别、模块、事件、消息和扩展字段，方便脚本检索。高频
逐帧路径不打印 INFO，避免日志 I/O 反过来影响实时处理。

指标包含：

- 视频/音频采集数、推理请求与结果数、编码包数和路由包数。
- 错误数、恢复数和过期检测结果数。
- 各阶段延迟的 p50、p95、p99。
- 队列当前深度、容量、高水位、丢弃数和超时数。
- worker 最近成功进展时间、最近错误时间和连续错误次数。

涉及知识点：

- 可观测性、结构化日志和指标聚合。
- 原子计数器与互斥保护的复合数据。
- 延迟分位数比平均值更能反映长尾问题。
- “线程存活”和“业务有进展”是两个不同概念。

### 5.13 Application 生命周期

`Application` 是管道总控，负责创建后端、创建队列、启动线程、汇聚错误和停止资源。

启动顺序：

```text
校验配置 -> 创建并 Open 后端 -> 创建 Router/Sink -> 先启动消费者 -> 再启动采集者
```

正常停止顺序：

```text
请求停止 -> 停采集 -> Drain 处理队列 -> Flush 编码器 -> Drain Sink -> Close 后端
```

致命错误停止：

```text
保存第一个根因 -> 请求全局停止 -> Abort 队列 -> join 线程 -> Close 全部后端
```

使用 `std::jthread` 和 `stop_token` 管理线程，没有 detached thread。状态通过原子状态机和
互斥锁保护，重复停止和析构兜底不会遗留后台线程。

涉及知识点：

- RAII、状态机和依赖倒置。
- `std::jthread`、协作式取消和线程 join。
- 启动失败的反向回滚。
- Drain 与 Abort 两种停止语义。
- 多线程错误汇聚和保留首个根因。

### 5.14 进程入口和部署骨架

`main.cpp` 实现命令行解析、配置加载、日志级别、SIGINT/SIGTERM、自动运行时长和退出码。
信号处理函数只修改 `sig_atomic_t`，实际加锁、日志和停止操作由普通控制线程执行。

仓库还提供 systemd service、Windows/Linux 构建脚本和长稳脚本。当前粤嵌板使用
Buildroot/BusyBox/SysV init，不是 systemd；ARM64 静态程序已在板端运行，Linux 信号和板端
长稳仍需继续验收。

涉及知识点：

- 异步信号安全。
- 命令行严格解析和进程退出码。
- systemd 服务生命周期。
- 自动化构建、测试和运行脚本。

## 7. 本阶段的重要设计取舍

### 7.1 为什么先做 Mock

Mock 把硬件不可控因素移除，使并发、背压、时间戳、停止和错误恢复可以稳定复现。它不是
最终产品，但会永久保留作为 CI 和回归测试后端。

### 7.2 为什么视频可以丢，音频默认不丢

实时视频更重视看到“现在”，积压旧帧只会增加延迟；音频丢一个块会产生可听断裂并破坏
连续时间轴。因此推理使用 `keep_latest`，视频常用 `drop_oldest`，音频默认阻塞并在超时
后显式报错。

### 7.3 为什么正常停止要 Drain

正常退出时，已经采集的数据应尽量走完编码和输出；致命错误时数据可能不可信，而且继续
等待可能卡死，所以采用 Abort。两种语义不能混成一个简单的 `running=false`。

### 7.4 为什么保留第一个致命错误

一个根因可能引发多个线程后续报错。例如 Sink 首先失败，队列关闭后编码线程也会失败。
如果不断覆盖错误，最后看到的往往只是连锁反应。保存第一个错误更利于定位根因。

### 8.1 第一优先级：完成 RK3568 板端 M5 验收

ARM64 静态程序已经在目标板完成配置校验和 10 秒 Mock 运行。接入新外设前，继续补齐以下证据：

6. 在 Ubuntu 原生构建中执行 ASan/UBSan；目标板侧以功能、资源和长稳证据为主。
7. 执行 30 分钟长稳，记录 CPU、RSS、温度、队列高水位和错误趋势。
8. 为 BusyBox/SysV init 适配启动脚本，再执行 2 小时长稳；当前板卡不执行 systemd 验收。

M5 完成标准：测试全通过、RSS 没有持续上涨、队列不突破容量、正常停止无超时、没有未知
错误、温度和 CPU 在可接受范围内。

仓库现已提供 `tools/m5_board_validation.sh`，适合有 CMake 和常规 GNU 工具的 Linux 板卡。
当前精简 Buildroot 需要按
[Buildroot 交叉编译与 RK3568 上板阶段总结](./09-buildroot-cross-compile-and-board-bringup-summary.md)
执行交叉构建、板端测试、信号和长稳；systemd 步骤不适用于该镜像。

### 8.2 第二优先级：接入 V4L2 摄像头

只新增 `V4L2VideoCapture`，保持 `IVideoCapture`、`VideoFrame` 和 Application 不变。

建议步骤：

1. 用 `v4l2-ctl --list-devices` 和 `--list-formats-ext` 记录真实设备能力。
2. 实现 Open 时的格式、分辨率和 FPS 协商，不能假定请求值就是实际值。
3. 先用 MMAP 跑通单路采集，再考虑 DMA-BUF。
4. 把驱动时间戳转换到项目单调微秒时间域。
5. 验证 stride、bytesused、断连、重连和停止唤醒。
6. 新增硬件集成测试，同时保持全部 Mock 测试通过。

验收：连续采集 30 分钟，序号/PTS 单调，断开摄像头能报告明确错误，重新插入后的策略符合
设计，内存不增长。

### 8.3 第三优先级：接入 ALSA 麦克风

只新增 `AlsaAudioCapture`，实现参数协商、阻塞读取和 `Recover()`。

重点验证：实际 card/device、采样率、声道、format、period size、buffer size、短读、XRUN、
USB 断连和音频 PTS 连续性。不要写死 `hw:1,0`，设备枚举结果应进入配置或稳定映射。

### 8.4 第四优先级：接入 RKNN 推理

在 BSP、RKNN Runtime 和模型版本固定后实现 `RknnInferenceEngine`：

1. 查询模型输入输出 tensor 属性。
2. 实现 RGB/NV12 到模型输入的预处理。
3. 复用现有 letterbox 元数据和检测框逆变换。
4. 先验证结果正确，再测 NPU 延迟和吞吐。
5. 对比 Mock/CPU 参考结果，建立固定样例回归测试。

### 8.5 第五优先级：RGA、MPP 和真实输出

推荐顺序：

```text
CPU 预处理正确 -> RGA 加速 -> MPP H.264 -> AAC -> MP4 -> RTSP
```

每次只替换一个阶段，并保留上一阶段作为 fallback。不要同时接入 RGA、RKNN、MPP 和 RTSP，
否则出现花屏、时间戳错误或卡死时很难判断根因。

### 8.6 第六优先级：性能优化

只有功能正确并有指标后再优化：

- 用 p95/p99 而不是感觉判断慢阶段。
- 用队列高水位判断生产/消费速率是否失衡。
- 用 CPU、RSS、温度和 NPU 利用率建立基线。
- 从 CPU Buffer 逐段替换为 DMA-BUF/RGA/MPP 零拷贝。
- 调整线程优先级前先确认真正瓶颈，不盲目使用实时调度策略。

## 9. 后续每个阶段都必须遵守的开发循环

```text
记录环境和设备能力
    -> 只接入一个后端
    -> 写最小硬件测试
    -> 跑全部 Mock 回归测试
    -> 做故障注入
    -> 做 30 分钟长稳
    -> 记录指标和结论
    -> 再进入下一模块
```

每个真实问题都应同步追加到 `06-项目问题汇总-面试版.md`，并在
`07-项目问题汇总-通俗版.md` 中补一份便于复习的解释。建议保留日志、命令、配置和修复前后
数据，这些证据比只写“解决了一个 bug”更有面试价值。

## 10. 面试时的项目介绍参考

### 10.1 30 秒版本

我做的是一个面向 RK3568 的实时音视频边缘分析网关。由于前期只有开发板、没有完整外设，
我先用 C++20 建立了可替换后端的 Mock 管道，完成音视频节拍生成、推理、编码包校验、
多输出分发、背压、时间戳、健康监控和安全停止。项目使用有界队列控制内存和延迟，使用
统一单调时钟保证 PTS，使用故障注入验证 XRUN、慢推理、慢输出和设备断连，当前 30 项
测试全部通过。后续只替换 V4L2、ALSA、RKNN 和 MPP 后端，不重写主流程。

### 10.2 面试中必须主动说明的边界

- 当前 Checksum Encoder 不是真实 H.264/AAC。
- 当前 MockInference 不是真实 RKNN 推理。
- Windows 30 项测试通过；ARM64 静态 Mock 已在 RK3568 Buildroot 完成 10 秒运行。
- 板端 30 项测试、Linux 信号、长稳和 SysV 自启动仍待留档；systemd 不适用于当前镜像。

清楚说明边界不会降低项目价值，反而能体现工程判断：无法验证的硬件能力不伪造，先把可
验证的公共核心做正确，并为后续替换留下回归基线。
