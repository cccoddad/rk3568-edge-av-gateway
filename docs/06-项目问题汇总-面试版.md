- **实际遇到**：本项目开发或构建过程中已经出现，有代码、测试或操作记录支持。
- **设计时主动规避**：根据实时音视频和并发开发经验提前识别，并通过设计或测试验证。
- **待硬件验证**：真实设备阶段很可能出现，但当前没有足够证据声称已经解决。

## 3. 已解决和已验证问题

### P001：Windows/Ninja 无法处理工程路径

**来源：实际遇到**
**状态：已解决**

#### 问题

工程目录包含非 ASCII 内容以及一个不可见的零宽字符。Windows 下部分 Ninja/MinGW 工具链
在生成或打开目标文件路径时失败，即使肉眼看路径没有问题。

#### 典型现象

- CMake 配置成功，但 Ninja 编译时报告找不到源文件、目标文件或 build.ninja 中的路径。
- 复制终端中的路径手动执行仍失败。
- 同一代码放到短英文路径后可以正常构建。

#### 根因

路径经过 CMake、Ninja、编译器和 Windows 文件 API 多层传递。某一层对 Unicode、零宽字符
或路径规范化的处理不一致，最终生成的字节序列或规范路径与真实目录不一致。

#### 排查操作

```powershell
# 确认当前真实路径
(Get-Location).Path

# 检查文件是否能被 PowerShell 直接枚举
Get-ChildItem -LiteralPath .

# 把源码映射到短路径后重新配置，验证是否确实是路径问题
cmd /c mklink /J C:\Users\CC\.cache\rkav-src "<工程绝对路径>"
cmake -S C:\Users\CC\.cache\rkav-src -B C:\Users\CC\.cache\rkav-build\debug -G Ninja
```

排查思路是只改变一个变量：代码和编译器不变，仅改变路径。如果短路径成功，问题基本可以
定位到工具链路径处理，而不是 C++ 代码。

#### 解决措施

- 创建短 ASCII Junction：`C:\Users\CC\.cache\rkav-src` 指向真实源码目录。
- 构建目录也放到短 ASCII 路径下，不把生成文件写回原目录。
- Windows 构建脚本自动复用该短路径，减少人工配置错误。

#### 验证

Debug 和 Release 均能完整编译，30 项测试全部通过。

#### 涉及知识点

- Unicode 路径、零宽字符和路径规范化。
- Windows Junction 与符号链接。
- out-of-source build。
- 控制变量法定位构建问题。

#### 面试回答参考

项目路径里有一个肉眼不可见的零宽字符，部分 Windows Ninja 工具链无法一致处理。我的排查
方式是保持代码和工具链不变，只把源码映射到短 ASCII 路径重新构建，确认根因在路径层。
最终通过 Junction 和独立短路径构建目录解决，并把处理固化到 PowerShell 构建脚本中。

### P002：没有完整外设和 SDK，如何开始开发

**来源：实际遇到**
**状态：Mock 阶段已解决，真实后端待继续**

#### 问题

项目目标需要摄像头、麦克风、RKNN、RGA 和 MPP，但开发初期只有 RK3568 板卡。直接等待
硬件会浪费时间，直接编写无法运行的 SDK 调用又不能验证正确性。

#### 根因

硬件依赖和业务主流程耦合时，任何缺失设备都会阻塞整个项目；同时无法区分以后出现的错误
究竟来自设备、驱动、SDK 还是并发主流程。

#### 排查操作

1. 列出不依赖硬件也必须正确的能力：数据模型、时间戳、队列、生命周期、配置和监控。
2. 列出只能实机验证的能力：V4L2 协商、ALSA 参数、RKNN 兼容性、MPP 码流。
3. 为 Capture、Inference、Encoder、Sink 定义稳定接口。
4. 使用确定性 Mock 实现接口，并通过故障注入覆盖异常路径。

#### 解决措施

- 采用依赖倒置，将硬件能力隐藏在接口之后。
- 先实现完整 Mock 管道和自动化测试。
- 保留真实后端编译开关，但不写未验证的伪实现。
- 明确文档边界，Checksum 包不宣称是真实编码。

#### 验证

无外设条件下，双路管道、慢推理、慢输出、XRUN 和设备断连均可重复验证。

#### 涉及知识点

- 依赖倒置、接口隔离和策略模式。
- Mock、Fake 与真实后端的边界。
- 可测试架构和增量替换。
- 硬件抽象层。

#### 面试回答参考

我没有用不可运行的硬件调用填充工程，而是先稳定公共契约。Capture、Inference、Encoder 和
Sink 都通过接口隔离，Mock 按真实节拍生成可校验数据并支持故障注入。这样后续接 V4L2、
ALSA、RKNN 和 MPP 时只替换后端，主流程和 30 项回归测试继续复用。

### P003：下游变慢导致队列和内存无限增长

**来源：设计时主动规避**
**状态：已通过慢推理和慢 Sink 集成测试**

#### 问题

采集速度高于推理、编码或输出速度时，如果队列无限增长，短期看起来没有丢帧，长期会造成
内存上涨、延迟越来越大，最后 OOM。

#### 典型现象

- RSS 持续增长。
- 当前画面越来越落后于真实时间。
- 停止时需要很久才能处理完积压。
- 低负载测试正常，运行时间越长越差。

#### 排查操作

1. 记录每个队列的当前深度、容量、高水位和丢弃数。
2. 比较生产速率和消费速率。
3. 人工增加推理或 Sink 延迟，观察队列是否突破容量。
4. 检查延迟增长是处理耗时增加还是排队时间增加。

#### 解决措施

- 所有线程间队列固定容量。
- 推理队列使用 `keep_latest`，只处理最新画面。
- 视频编码队列通常 `drop_oldest`，以实时性优先。
- 音频队列阻塞生产者，超时后显式失败，不静默丢音频。
- 指标记录高水位、超时和丢弃数量。

#### 验证

慢推理测试确认推理队列容量保持 1 并产生可观测丢帧；慢 Sink 测试确认其队列容量保持 2，
同时采集线程继续前进。

#### 涉及知识点

- 生产者/消费者、背压和 Little's Law。
- 吞吐量、排队延迟和内存之间的关系。
- 实时性与数据完整性的业务取舍。

#### 面试回答参考

我没有使用无限队列，而是为每条跨线程通道定义容量和溢出策略。视频追求新鲜度，允许丢旧；
音频追求连续性，默认阻塞并超时报错。我还通过慢推理、慢 Sink 故障注入检查队列高水位，
证明内存不会随运行时间无限增长。

### P004：固定 sleep 导致视频时间长期漂移

**来源：设计时主动规避**
**状态：已通过分数帧率误差测试**

#### 问题

使用 `sleep_for(1s / fps)` 控制帧率时，整数截断、线程调度延迟和每帧处理耗时会不断累加，
造成帧率和 PTS 长期漂移。

#### 排查操作

1. 记录第 0 帧的时间起点。
2. 比较第 N 帧实际 deadline 与公式 `start + N / fps`。
3. 长序列运行后检查误差是否随 N 线性增大。
4. 区分系统唤醒晚和理论 deadline 本身漂移。

#### 解决措施

`FramePacer` 每次都从固定起点和序号计算绝对 deadline，然后 `WaitUntil` 该时间点。即使某次
线程晚醒，下一帧仍以原始时间轴为基准，不把本次延迟累加到以后。

#### 涉及知识点

- 单调时钟、绝对 deadline、调度抖动。
- 有理数帧率和整数舍入误差。
- PTS 时间轴。

#### 面试回答参考

简单 sleep 控制帧率会把截断和调度误差逐帧累积。我用固定 epoch 加帧序号计算每帧绝对
deadline，并使用单调时钟等待。测试验证长序列误差保持有界，而不是随帧数增长。

### P005：阻塞线程收到停止请求后无法退出

**来源：设计时主动规避**
**状态：已通过队列取消、Drain 和 Abort 测试**

#### 问题

线程可能阻塞在队列条件变量、模拟采集等待或输出 I/O 中。只设置 `running=false` 并不能
自动唤醒它，主线程在 `join()` 时可能永久等待。

#### 排查操作

1. 观察停止日志停在哪个阶段。
2. 检查每个阻塞点是否同时等待“数据/空位、关闭、取消”。
3. 检查请求停止后是否调用 `notify_all()`。
4. 给停止过程设置期限并打印尚未退出的 worker。

#### 解决措施

- 使用 `std::jthread` 和 `stop_token` 进行协作式取消。
- 队列通过 `stop_callback` 在取消时唤醒条件变量。
- `Close()` 唤醒所有生产者和消费者。
- 正常退出使用 Drain，致命错误使用 Abort。
- 按采集、处理、输出依赖顺序停止和 join。

#### 涉及知识点

- 条件变量谓词、虚假唤醒。
- 协作式取消和 `stop_callback`。
- 线程生命周期、join 和死锁排查。

#### 面试回答参考

停止标志只改变状态，不能唤醒阻塞线程。我把 stop_token 纳入每个阻塞谓词，并通过
stop_callback 调用 notify_all。队列关闭也会唤醒等待者，正常路径 Drain，错误路径 Abort，
因此 join 有明确退出条件。

### P006：音频 XRUN 恢复后出现 PTS 缺口

**来源：设计时主动规避**
**状态：已通过周期 XRUN 测试**

#### 问题

音频读取发生 XRUN 后，如果先增加块序号或 PTS，再恢复并读取下一块，就会在逻辑时间轴上
跳过一段音频。听感可能出现断裂，后续音画同步也会受到影响。

#### 排查操作

1. 开启每 N 块一次的确定性 XRUN 注入。
2. 记录恢复前后块序号、PTS 和 samples_per_channel。
3. 用公式检查相邻 PTS 差是否等于块时长。
4. 检查失败读取是否已经提交序号或相位状态。

#### 解决措施

- 只有成功生成完整块后才提交 sequence、PTS 和正弦相位。
- XRUN 时调用 `Recover()`，随后重试同一个逻辑块。
- 恢复次数计入指标，不能静默吞掉错误。

#### 验证

集成测试周期注入 XRUN，最终 `recoveries_total > 0`、无致命错误，单元测试检查 PTS 连续。

#### 涉及知识点

- ALSA XRUN、事务式状态提交。
- PCM 连续性和音频时钟。
- 至少一次重试与幂等思想。

#### 面试回答参考

XRUN 的关键不只是调用 recover，还要避免先提交时间轴状态。我把 sequence、PTS 和音频相位
的推进放到成功读取之后，恢复后重试同一个逻辑块，因此不会制造隐藏的 PTS 缺口。

### P007：慢 Sink 阻塞编码和采集主链路

**来源：设计时主动规避**
**状态：已通过慢 Sink 隔离测试**

#### 问题

如果编码线程同步写文件或网络，一个慢磁盘、慢客户端或网络抖动会阻塞编码线程，继续向上
传导到采集线程，最终整条管道延迟升高。

#### 排查操作

1. 给某个 Sink 注入固定写延迟。
2. 观察采集计数是否停止、其他 Sink 是否受影响。
3. 查看每个 Sink 自己的队列高水位和丢包数。
4. 对比编码耗时与实际 Sink 写耗时。

#### 解决措施

PacketRouter 为每个 Sink 创建独立有界队列和 worker。编码线程只投递共享不可变 Packet，
实际 I/O 在 Sink worker 中完成。

#### 涉及知识点

- Fan-out、隔离舱模式和异步 I/O 边界。
- 共享不可变对象。
- 慢消费者隔离。

#### 面试回答参考

我没有让编码线程直接执行输出 I/O，而是为每个 Sink 建立独立有界队列和工作线程。慢输出
只会消耗自己的队列预算，测试证明采集仍持续，其他输出不被它拖住。

### P008：输出故障应该全局退出还是隔离

**来源：设计时主动规避**
**状态：required/optional 两种场景均已测试**

#### 问题

所有输出失败都退出会降低可用性，所有输出失败都忽略又可能导致“进程正常但没有核心结果”。

#### 解决措施

配置为每个输出定义 `required`：

- required Sink 失败：记录第一个错误并停止全局管道。
- optional Sink 失败：记录一次错误，隔离该 Sink，主链路继续。

#### 排查操作

使用 `fail_after_packets` 确定性注入故障，分别检查 Application 状态、错误计数、其他流的
处理计数和最终退出结果。

#### 涉及知识点

- 故障域、降级服务和关键依赖。
- 可用性与正确性权衡。
- 配置驱动的容错策略。

#### 面试回答参考

我把输出分为业务必需和可选。必需输出失败意味着结果已无法交付，需要停止；可选输出失败
则隔离，避免辅助日志或旁路输出拖垮主业务。这两个分支都有故障注入测试。

### P009：设备持续失联造成忙等或假存活

**来源：设计时主动规避**
**状态：已通过持续断连集成测试**

#### 问题

设备错误标记为 retryable 后，如果立即无限重试，会占满 CPU 并刷爆日志；如果线程一直重试
却从不成功，系统看似存活，实际没有数据输出。

#### 排查操作

1. 注入从指定音频块开始的持续断连。
2. 观察 CPU、错误频率和最近成功进展时间。
3. 区分“线程循环仍在跑”和“成功处理计数仍在增加”。
4. 检查监控是否能指出具体卡死 worker。

#### 解决措施

- 可重试错误之间固定退避 100 ms，避免忙等。
- 每个 worker 记录最近成功进展时间。
- 监控线程超过阈值后报告具体 worker stall 并受控退出。

#### 涉及知识点

- 指数/固定退避、错误风暴。
- liveness 与 progress。
- watchdog 和健康检查。

#### 面试回答参考

可重试不等于永远重试。我先加退避避免 CPU 忙等，再记录 worker 最近成功进展。线程即使
仍在循环，只要超过阈值没有成功数据，也会被监控判定为 stall 并停止，这解决了假存活。

### P010：JSON 字段拼错却静默使用默认值

**来源：设计时主动规避**
**状态：已通过未知字段和跨字段负向测试**

#### 问题

如果配置解析器忽略未知字段，用户把 `fps` 写成 `fpps` 后，程序仍会启动并使用默认值。
现象像性能问题，实际上是配置根本没有生效。

1. 构造包含故意拼错字段的最小 JSON。

#### 面试回答参考

配置系统最危险的不是解析失败，而是拼错后仍成功。我对每层对象做未知字段拒绝，并把解析

### P011：stride/Buffer 大小错误造成越界或花屏

**来源：设计时主动规避**
**状态：已通过非法 RGB stride 测试**

#### 问题

图像 width 表示有效像素宽度，stride 表示内存中一行实际字节数。硬件常因对齐使 stride
大于有效宽度。如果错误使用 `width * bytes_per_pixel` 访问每行，可能出现错行、花屏或越界。

#### 排查操作

1. 打印 width、height、format、stride、bytesused 和 Buffer size。
2. 按格式计算最小 stride 和最小总字节数。
3. 使用小图和带 padding 的人工样例验证行首地址。
4. 开启 ASan 检查越界。

#### 解决措施

帧进入下游前执行 `ValidateVideoFrame`；像素访问基于 `y * stride + x * bytes_per_pixel`，
不假设行紧密排列。

#### 涉及知识点

- 图像内存布局、对齐、stride/pitch。
- Buffer 边界检查。
- V4L2/RGA/MPP 格式兼容基础。

#### 面试回答参考

我把 stride 作为帧契约的一部分，而不是从 width 临时推导。所有后端输出先校验最小 stride
和 Buffer 大小，逐行访问使用真实 stride，这为以后接 V4L2 和 RGA 的对齐内存做好了准备。

### P012：音频块时长不能得到整数样本数

**来源：设计时主动规避**
**状态：已通过 44.1 kHz/7 ms 负向测试**

#### 问题

每块每声道样本数为：

sample_rate * frame_duration_ms / 1000

例如 44100 Hz 和 7 ms 得到 308.7 个样本，但样本数必须是整数。直接截断会让实际块时长和

检查乘积能否被 1000 整除，并比较“样本数推导的真实时长”和配置时长。

#### 解决措施

配置校验阶段拒绝不能形成整数样本块的组合，而不是运行时截断。

#### 涉及知识点

- 离散采样、采样率和块大小。
- 整数时间计算和累计误差。
- 启动前语义校验。

#### 面试回答参考

音频是离散样本，块大小不能是小数。我在配置阶段检查采样率乘块时长是否能整除 1000，
不允许运行时截断，从源头保证 PCM 样本数和 PTS 推进一致。

### P013：推理结果过期或绑定到错误视频帧

**来源：设计时主动规避**
**状态：CPU OSD 软件 MP4 已验证；RK3568 实机 OSD 尚未验证**

#### 问题

推理线程和视频编码线程异步运行。编码当前帧时拿到的可能是旧帧检测结果，如果不携带来源

1. 在检测结果中记录 `frame_sequence` 和 `source_pts_us`。
2. 记录 `completed_at_us`，计算结果年龄。
3. 注入慢推理，检查过期计数和队列丢旧行为。
4. OSD 接入后用固定样例比较原图与叠加图，并在软件 MP4 中核对叠加计数。

#### 解决措施

- `DetectionBatch` 明确绑定源帧序号和 PTS。
- 最新结果以不可变 `shared_ptr` 快照跨线程共享。
- 编码阶段检查 `max_result_age_ms`，过期结果计入指标。
- 推理队列 `keep_latest`，避免持续处理陈旧画面。

#### 涉及知识点

- 异步流水线的数据关联。
- 最终一致性、新鲜度窗口和不可变快照。
- 实时推理中的延迟/吞吐取舍。

#### 面试回答参考

异步推理不能只保存“最后一个框”。我让每批结果携带源 frame sequence、PTS 和完成时间，
编码端检查来源与结果年龄；慢推理时队列只保留最新帧。CPU OSD 已在 H.264/AAC 软件 MP4 中
验证 151/151 帧精确叠加；真实 RK3568 的 RGA/MPP 路径仍需单独验收。

我没有把时间戳当普通毫秒数，而是让 Packet 显式携带 time_base。换算使用整数有理数并检查

### P015：启动到一半失败导致资源泄漏

**来源：设计时主动规避**
**状态：已实现反向回滚和析构兜底**

#### 问题

视频已经打开、音频也已经打开，但推理或编码器初始化失败时，如果直接返回，前面打开的
资源和线程可能泄漏。

#### 排查操作

列出每个启动步骤成功后新增的资源，给中间步骤注入失败，检查 Close 次序、线程数量和最终
Application 状态。

#### 解决措施

#### 涉及知识点

我按工作负载而不是品牌和峰值读取选卡。视频需要持续写入，所以U3/V30优先；A1/A2对运行应用

所有场景。

目前不能说已经解决。可以回答：我已经把硬件 SDK 隔离在独立后端，并准备了版本基线和

### P021：V4L2 请求参数与设备实际协商参数不同

**来源：待硬件验证**
**状态：未解决**

#### 可能问题

驱动返回的 width、height、pixelformat、bytesperline 和 sizeimage 才是实际契约。

#### 排查操作

### P022：ALSA 设备号变化和真实 XRUN

**来源：待硬件验证**
**状态：未解决**

#### 可能问题

- USB 麦克风插拔后 card 编号变化，写死 `hw:1,0` 失效。
- 请求 48 kHz/单声道时设备实际只支持其他组合。
- period/buffer 设置不合理导致频繁 XRUN。
- `snd_pcm_readi` 短读、EPIPE 或 ENODEV 没有正确映射。

#### 排查操作

```bash
arecord -l
arecord -L
cat /proc/asound/cards

arecord -D <device> -f S16_LE -r 48000 -c 1 -d 10 /tmp/test.wav

```

- 优先使用稳定 CARD 名称或配置匹配，不依赖易变化的数字编号。

- 明确 period size、buffer size 和阻塞模式。
- EPIPE 映射为 XRUN 并走 `Recover()`；ENODEV 映射为断连。

### P067：GitHub 整仓克隆被重置，SDK 无法下载

**来源：实际遇到**
**状态：已解决**

#### 现象与影响

`git clone --depth 1 --branch v1.4.0` 返回 `Recv failure: 连接被对方重置`。脚本没有立即停止，
后续 `cd`、Git LFS、头文件检查和哈希命令全部在不存在的目录中继续报错。

#### 根因与解决

直接原因是到 GitHub 的长连接不稳定；流程问题是首条关键命令失败后仍继续执行。项目只需要
固定版本的 `rknn_api.h` 和 AArch64 `librknnrt.so`，因此改用 GitHub blob API 按对象下载，
增加 `curl --retry --retry-all-errors`，并用官方固定 SHA-256 校验。所有后续脚本使用
`set -euo pipefail`，关键文件用 `test -f` 提前失败。

#### 验证与面试表达

两个文件的大小、ELF 架构和 SHA-256 均通过，C17 冒烟程序随后完成交叉编译和板端运行。
面试时可强调：我把不稳定的整仓下载缩小为最小、可校验的供应链输入，并让失败立即终止。

### P068：静态 `libstdc++` 仍引入高版本 GLIBC

**来源：实际遇到**
**状态：已解决**

#### 现象与根因

Ubuntu 24.04 的 AArch64 G++ 13 成功链接主程序，`readelf` 却显示要求 GLIBC 2.36 和 2.38，
板端只有 2.35。`-static-libstdc++ -static-libgcc` 只消除了板端 C++ 运行库依赖，并不会把
glibc 也变成旧版本；新版静态 C++ 库自身仍引用构建 sysroot 的新 glibc 符号。

#### 解决与验证

独立冒烟改为 C17；C++ 主程序固定在 Ubuntu 22.04 容器中使用 GCC/G++ 11.4 和 glibc 2.35
sysroot 构建。脚本枚举全部 `GLIBC_*`，任何高于 2.35 的符号都会失败。CI 最终产物最高只要求
GLIBC 2.34，动态依赖不包含 `libstdc++.so`。

2026-08-28 的 MPP/RGA 候选后端再次验证了这条门禁：Ubuntu 24.04 GCC 13 的 AArch64 编译可完成
40/40，但 ELF 要求 `GLIBC_2.38`，没有部署；切换到同一项目的 Ubuntu 22.04 容器后也完成 40/40，
最高仅 `GLIBC_2.34`，候选程序 SHA-256 为
`136a7e0641946f55f398603bc982164c8190dd38566f14f8ad89994043384399`。

#### 面试表达

ABI 兼容性由目标 sysroot 和符号版本决定，不由“编译成功”或“静态链接了一个库”决定。

### P069：TF 卡自动挂载为 `noexec`，程序不能直接运行

**来源：实际遇到**
**状态：已解决**

#### 现象与根因

TF 卡以 exFAT/FUSE 自动挂载到 `/media/sdcard0`，挂载参数包含 `noexec`。即使文件显示有执行
位，也不能可靠地从卡上直接启动。

#### 解决与验证

板端先从 `/proc/mounts` 解析真实挂载点，校验 SHA-256，再复制到 `/tmp` 或 `/userdata`，执行
`chmod 0755`。传输结束后 `sync`、`umount` 并确认 `/proc/mounts` 已无该设备。RKNN 冒烟和
YOLOv5 工具均通过该流程部署并运行。

#### 面试表达

可移动介质是传输载体，不是默认可信的执行位置；部署必须同时验证内容完整性和挂载语义。

### P070：固定猫狗测试图被误解为业务摄像头输入

**来源：实际遇到**
**状态：已解决**

#### 现象与根因

板端自带 MobileNet 示例和猫狗图片，容易被误认为项目最终应处理的内容。实际上固定图片用于
建立可重复参考；MobileNet 是分类模型，只能证明 Runtime/NPU 基础链路，不能输出检测框。

#### 解决与验证

先用固定输入验证确定性，再抓取 `/dev/video9` 真实 MJPEG 帧，完成 JPEG 解码、RGB 缩放和
MobileNet 推理；之后转换 YOLOv5s 并在真实摄像头单帧上得到目标框。每个里程碑都明确“基础
设施验证”和“业务模型验证”的边界。

#### 面试表达

固定测试向量负责可重复性，真实输入负责代表性，二者互补而不是互相替代。

### P071：RKNN 转换未指定平台而默认使用 RK3566

**来源：实际遇到**

#### 现象与根因

Toolkit2 输出 `target_platform is None, use rk3566 as default`。如果只看到转换成功就部署，

### P072：NPU 开机 warning 被误认为本轮推理故障

**来源：实际遇到**
**状态：已区分，设备树风险继续保留**

#### 现象与根因

`dmesg` 中存在 `pd_npu-supply`、leakage、power model 和 dynamic coefficient 缺失等 6 条
日志。它们来自开机设备树初始化，不代表每次推理都新增故障。

#### 解决与验证

运行前记录 uptime、NPU/IOMMU 中断和相关内核日志；运行 10 次后只比较新时间窗口。结果是
NPU 中断增加 10，没有新增 NPU/IOMMU fault、timeout 或 panic，温度从 46.111 上升到

#### 面试表达

日志排查必须建立时间边界和增量证据，不能把历史告警直接归因于当前操作。

### P073：CI 容器有交叉 `readelf` 但缺少通用 `readelf`

**来源：实际遇到**

#### 现象与根因

#### 面试表达

“客户端存在”“守护进程运行”“当前用户被授权”是三层独立检查。

### P077：5 V 风扇插头不匹配，是否改用 12 V

## 7. MJPEG、ALSA 联合与长稳阶段新增问题

### P079：libjpeg-turbo 版本和跨平台构建不可漂移

**来源：实际遇到 / 设计时主动规避**
**状态：已锁定并通过 Windows、AArch64 构建**

#### 问题与影响

真实摄像头输出 MJPEG，主程序必须引入 JPEG 解码库。如果 Windows 使用一个系统库版本、
Ubuntu 交叉构建使用另一个版本，而板端再动态加载未知 `libjpeg.so`，API、ABI 和解码行为就
可能漂移。板端旧 Buildroot 也不适合临时安装新动态库。

#### 根因与方案

JPEG 解码属于主链路确定性依赖，不能依赖构建机或板端“碰巧安装”的版本。项目固定
libjpeg-turbo 3.1.4.1，并锁定源码 SHA-256：

```text
ecae8008e2cc9ade2f2c1bb9d5e6d4fb73e7c433866a056bd82980741571a022
```

使用 TurboJPEG 内存 API，通过 CMake 外部项目构建静态库；AArch64 路径关闭 SIMD，避免交叉
汇编工具差异。构建完成后继续检查 ELF 架构、动态依赖和最高 GLIBC 符号版本。

#### 验证

- Windows Debug/Release 43 项测试全部通过；
- 真实 1280x720 UGREEN JPEG 样本通过；
- AArch64 程序最高要求 GLIBC 2.34，板端为 2.35；
- 板端程序不新增 `libjpeg.so` 动态依赖。

#### 面试回答参考

我没有直接使用系统 JPEG 库，而是把版本、源码哈希和链接方式都作为可复现构建的一部分。
这样 PC 回归、交叉编译和旧 Buildroot 板端使用的是同一套解码实现，并通过最终 ELF 门禁证明
没有把新系统依赖带到板端。

### P080：在 30 FPS 主路上解码全部 MJPEG 会浪费 CPU

**来源：设计时主动规避**
**状态：已实现并实机量化**

#### 问题与取舍

摄像头约 30 FPS，而当前 RKNN 推理配置只需要 5 FPS。若视频采集后立刻把每帧 MJPEG 都在
CPU 展开成 1280x720 RGB888，会产生约 2.76 MB/帧的内存写入和不必要的 JPEG 计算。实测单次
解码 p50 约 32–34 ms，全帧 CPU 解码会逼近一个 CPU 核心的持续预算。

项目把限帧放在解码前：只有进入容量 1 `keep_latest` 推理队列的新鲜帧才解码，原始 MJPEG
继续走视频编码分支。10 秒取得 49 次解码/推理，60 秒取得 291 次，解码样本、推理请求、结果
和 NPU 中断相等。

#### 残余边界

该方案只解决 5 FPS 推理支路。后续生成 30 FPS H.264 仍需按总体架构建立 FFmpeg 软件媒体
基线，再根据指标接入 MPP/RGA；不能用当前推理抽帧结果冒充完整视频编码能力。

#### 面试回答参考

优化不是先换硬件 API，而是先把昂贵操作放到正确的数据率边界。我先在推理限帧后解码，
用计数和延迟证明只支付实际需要的成本，同时保留原始 MJPEG 给未来编码路径。

### P081：ALSA 在 RKNN 初始化前启动导致确定性启动 XRUN

**来源：实际遇到**
**状态：已解决，30 分钟三硬件长稳已通过**

#### 现象

真实摄像头 + ALSA + RKNN 第一次 10 秒联合运行中，音频最终仍得到约 500 个块，但出现一次：

```text
alsa_audio.poll: ALSA capture overrun: Broken pipe
category=xrun, native_code=32, retryable=true
```

最终 `recoveries_total=1`，而独立 `arecord` 两秒录音成功，说明不能简单归咎于麦克风或 USB。

#### 定位证据

- ALSA 后端约在 `05:52:18.616` 打开并执行 START；
- Application 工作线程约在 `05:52:18.815` 才开始；
- 间隔约 199 ms；

### P085：延迟滑动窗口样本数被误当成累计解码数

**来源：实际遇到**
**状态：已定位并通过原始证据重验收**

#### 现象

30 分钟后台重试中网关退出码为 0，视频、音频、推理、NPU 中断和 packet 全部守恒，错误、
恢复、队列丢弃与残留均为 0，但控制器最终仍写出 `status=failed:1`。第一处失败条件是
`decode_samples=3594` 没达到 8,500，下一条还要求它等于 8,714 次推理请求。

#### 根因

`video_decode.samples` 不是累计解码计数，而是计算 p50/p95/p99 的延迟滑动窗口当前样本量。
指标实现最多保留 4,096 个样本，达到上限后删除最旧四分之一，因此运行越久，该值也不会持续
增长到 8,500。控制脚本混淆了“窗口样本量”和“累计工作量”，又因 `set -e` 在第一条假条件
失败后立即退出。

#### 修复与证据

累计工作量改查 `inference_requests_total >= 8500`，同时要求请求数、结果数和 NPU 中断增量
相等；解码窗口只要求大于 0 且不超过 4,096。原始 `status=failed:1`、日志和控制脚本没有被
覆盖，另存 `original-evidence.sha256` 与 `corrected-validation.log`。五份原始证据哈希复核均为
`OK`，修正规则后结论为 `three_hardware_soak_30m=passed_after_validation_rule_correction`。

#### 面试回答参考

稳定性验收不仅要看阈值，还要确认指标语义。我通过第一处失败条件回溯到指标容器实现，发现
脚本把有界延迟窗口当成累计计数。随后保留原始失败证据，用哈希证明材料未变，再按正确累计
指标重验收，避免为了得到绿色状态而盲目重跑。

随后受控重试确认 Python、lz4、`-j2` 与 kernel defconfig 均通过，但继续暴露 P104；仍没有新增 Image、
DTB 或 boot 产物。

### P104：Ubuntu 缺少 GMP 开发头文件

**来源：实际遇到**
**状态：失败证据已保存，待补依赖并单测前置检查**

lz4 门禁通过后的受控 kernel 重试在 `check-kernel.sh` 报 “Your gmp header is missing”，并提示安装
`libgmp-dev`。构建仍停在正式 Image/DTB 编译前；Image、候选 DTB、kernel `boot.img` 和 firmware
`boot.img` 均不存在。

本次日志路径为 `evidence/sdk-kernel-lz4-20260903-160022/kernel.log`，SHA-256 为
`505744c2e7c479fa7a0701cee17326c34c7695c5ca112c466200417af9820e2e`；开始时间证据 SHA-256 为
`f79dedad43c825c3a8de662fd616c8db44fffd810e60ece346d9d18d0556c0de`。下一步安装脚本明确要求的
`libgmp-dev` 后，先单独运行 `check-kernel.sh`，避免为发现下一个主机依赖而重复完整构建入口。

`libgmp-dev` `2:6.3.0+dfsg-2ubuntu6.1` 随后安装成功，GMP 头文件编译探针返回 0；前置检查继续运行到
P105。安装日志 SHA-256 为 `0688c591f12d3f176f41542bf3bdf02c95605b64e5bae58f60e42fc524ae3094`。

### P105：GMP 通过后继续发现 MPC 开发头文件缺失

**来源：实际遇到**
**状态：已定位，待批量补齐明确依赖**

单独运行 `check-kernel.sh` 后，Python、lz4、flex、OpenSSL 与 GMP 检查均已越过，脚本在 MPC 头文件处
提示安装 `libmpc-dev` 并返回 1。前置检查日志 SHA-256 为
`3c64b09c3868f070b74d3a275023a2fac4f46fefed12544e6d67b5ff3bec913c`。

完整脚本已确认其主机包/头文件检查范围为 `python-is-python3`、`flex`、`libssl-dev`、`libgmp-dev`、
`libmpc-dev` 和 `libncurses-dev`，另有已通过的 lz4 能力检查。随后一次性安装/确认这组明确依赖：新增
`libmpc-dev`、`libmpfr-dev`、`libncurses-dev`，四个头文件编译探针均返回 0，`check-kernel.sh` 返回 0，
`ALL_KERNEL_PRECHECK_GATE=PASS`。随后受控 normal kernel 实编已通过，详见 P106/P107 和第 50 号交接。

### P106：候选构建成功后仍需确认 IO 电源域

**来源：实际遇到**
**状态：主机构建通过，上板安全门禁未通过**

隔离 SDK normal kernel 以实际 `-j2` 完成，生成 37102080 字节 Image、185067 字节候选 DTB 和
37520896 字节 FIT `boot.img`。候选 DTB 的 model、compatible、GMAC1 输入时钟、PB5 复位以及
`tx_delay=0x41`、`rx_delay=0x1e` 均通过反编译断言，`FINAL_KERNEL_GATE=PASS`。

SDK 随后明确要求再次确认 `pmu_io_domains`，尤其是 Wi-Fi、Flash、Ethernet IO 电源域。定向比较已确认：
`pmuio2` 均为 3.3V，`vccio3` 均接可切换 SD 供电，`vccio5/7` 均为 3.3V；但 factory 的 `vccio4/6`
接固定 1.8V，当前候选继承 EVB1 后却接 3.3V；同名 `vccio_acodec` 供给的 `vccio1` 在 factory 为
3.3V、候选为 3.0V。因此当前候选 FIT 明确禁止刷写。下一步先确认 5.10 源码中的 regulator label，再构造
只覆盖这三项差异的候选 v2 并重新编译/反编译。

5.10 EVB1 include 链随后确认 `vccio_acodec`、`vcc_1v8`、`vcc_3v3` 三个 label 与
`&pmu_io_domains` 覆盖入口均存在，`label_gate=0`。当前 `vccio_acodec` 固定 3.0V、`vcc_1v8` 固定
1.8V，供电定义与反编译结果一致。候选 v2 可独立 include 现有 GMAC1 候选，只覆盖
`vccio_acodec` 的 3.3V 和 `vccio4/6-supply = <&vcc_1v8>`，无需改公共 EVB DTSI。

候选 v2 已创建并由 SDK 增量构建成功。DTB 中 `vccio1` 与 `vccio_acodec` phandle 相同，`vccio4/6` 与
`vcc_1v8` phandle 相同，`vccio5/7` 与 `vcc_3v3` phandle 相同。最后门禁因 P108 没有读到 acodec 的
数值而报告失败；随后用正确 unsigned 类型复核，`IODOMAIN_V2_FINAL_GATE=PASS`。IO 电源域门禁已解除，
但候选仍不得上板，下一步先核对 eMMC/SD、PMIC、串口和 USB 等启动关键节点。

### P107：自动电源域检查达到 PCRE 回溯上限

**来源：实际遇到**
**状态：构建未被阻断，但自动检查结果不能视为完整**

kernel 构建结束后的检查连续 7 次报告 `grep: ... exceeded PCRE's backtracking limit`，随后仍打印电源域
人工确认警告并报告 build hook 成功。该错误不否定 Image/DTB/FIT 的构建与哈希，但说明脚本对展开后的大型
DTS 文本执行复杂正则时可能没有完成全部匹配。脚本源码已确认它使用跨节点的 `grep -Pzo` 贪婪模式并通过
`eval` 追踪 phandle；大型 DTS 上连续 7 次超限。后续电源域验收不依赖这条 grep 的成功摘要，已改为直接
提取候选/factory 的 `pmu_io_domains`、phandle、regulator 名称和电压并逐项比较。

### P108：fdtget 类型参数错误造成候选 v2 假失败

**来源：实际遇到**
**状态：已用正确类型复核通过**

候选 v2 的 patch、SDK 配置与增量构建均返回成功，实际 phandle 映射也已符合 factory。但验证脚本用
`fdtget -td` 读取微伏值；本机 fdtget 仅支持 `s/i/u/x/r`，因此报 `invalid type string`，使
`acodec_min/max` 为空并导致 `structured_gate=1`、`IODOMAIN_V2_GATE=FAIL`。

这不是 DTS 编译失败或电源域引用错误。随后对同一个 v2 DTB 使用 `fdtget -tu` 读取 unsigned 十进制值：
`vccio_acodec=3300000..3300000`、`vccio_sd=1800000..3300000`，全部 supply phandle、GEC model 和 GMAC
属性同时通过，最终门禁为 `PASS`。验证结果文本 SHA-256 为
`9e77a196916aee6c3c2cf4931f93ff134444d0f36792d33ccf02d87fa5336b55`。

### P109：Wi-Fi 控制器用途与 EVB 不同

5.10 EVB1 将 Wi-Fi/SDIO 配在 `sdmmc2`（地址 `fe000000`，aliases `mmc3`），GEC factory 则将
RTL8723DS 配在 `sdmmc1`（地址 `fe2c0000`，aliases `mmc2`），并把 `fe000000` 禁用。当前有线网关
不依赖 Wi-Fi，v3 先关闭 EVB Wi-Fi 节点，避免错误 GPIO/电源时序；GEC Wi-Fi 后续单独移植。

### P110：调试串口状态与 factory 不同

factory 的 `serial0`、`serial1` 为 `okay`，5.10 EVB 候选均为 `disabled`。两路 5.10 节点已有稳定
label/pinctrl，v3 仅启用状态，便于首次启动观察和恢复；是否对应 GEC 排针仍需上板实测。

### P111：为什么第一次 v3 一两分钟就结束

第一次 SDK 构建中的候选 v3 覆盖块缺少结束符 `};`，内层 DTC 返回 2；SDK 外层错误显示 `build_exit=0`。
后续用 v1 重新生成 v3 并补齐覆盖块后，SDK 内核构建成功，证明原问题是候选文本错误。旧 v2 产物曾被
`fresh=0` 正确排除，不能拿旧文件验收 v3。

### P112：为什么直接 DTC 会在 `#include` 行失败

内核 DTS 使用 C 预处理器处理 `#include` 和宏；直接执行 `dtc -I dts` 不会做这一步，所以在 include 行
报语法错误。这个结果只能说明验证命令不完整，不能否定 DTS。v3 随后由 SDK 正常内核路径预处理并完成 DTC、
DTB 和 FIT boot 构建。

## 8. 面试追问速查

### 7.1 为什么不用无锁队列

当前数据速率和线程数量下，正确的有界语义、可取消阻塞、Drain/Abort 和可测试性优先于理论
上的极限吞吐。互斥锁版本更容易证明正确。后续只有指标证明队列锁成为瓶颈时，才考虑 SPSC
ring buffer，并重新实现关闭、背压和指标语义。

### 7.2 为什么使用 shared_ptr

同一视频帧需要同时发给推理和编码，同一编码包又要发给多个 Sink。共享只读 Buffer 可以
避免大块像素或 payload 复制。代价是原子引用计数，因此后续零拷贝优化时仍需用指标验证，
不能默认它没有成本。

### 7.3 为什么不用异常处理所有错误

采集失败、XRUN、队列超时属于预期运行结果，使用 `Result<T>` 可以明确分类和恢复策略；
线程入口仍捕获未预期异常，转成结构化致命错误，避免异常逃出线程导致 `std::terminate`。

### 7.4 为什么监控最近进展，不只看线程状态

线程可能在无限重试、空循环或等待永远不会来的条件，操作系统仍认为它存活。实时服务真正
关心的是是否持续产生有效帧、块或包，所以最近成功进展比单纯 alive 更有意义。

### 7.5 为什么不能现在做全链路零拷贝

零拷贝取决于摄像头格式、V4L2 缓冲类型、RGA/RKNN/MPP 对 DMA-BUF 的支持、stride 和缓存
同步。当前硬件组合未知，提前写死很容易得到不可运行的设计。项目先保留 MemoryKind 和
DMA-BUF 契约，待 CPU 路径正确后逐段替换并测量收益。

## 10. 面试表达原则

1. 先说影响，再说错误信息；面试官更关心你是否理解业务后果。
2. 排查要体现假设和证据，不要说“试了很多方法最后好了”。
3. 说明为什么选择当前方案，以及它的代价。
4. 用测试、指标和长稳结果证明修复，不用“看起来没问题”。
5. 对待硬件验证项明确说尚未完成，再讲已经准备的接口和排查方法。
6. 不背诵代码细节，重点解释不变量：时间戳连续、内存有界、线程可停、错误可定位。
