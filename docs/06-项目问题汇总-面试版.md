## 3. 已解决和已验证问题

### P001：Windows/Ninja 无法处理工程路径

**来源：实际遇到**
**状态：已解决**

#### 问题

工程目录包含非 ASCII 内容以及一个不可见的零宽字符。Windows 下部分 Ninja/MinGW 工具链
在生成或打开目标文件路径时失败，即使肉眼看路径没有问题。

#### 典型现象

- CMake 配置成功，但 Ninja 编译时报告找不到源文件、目标文件或 build.ninja 中的路径。
- 复制终端中的路径手动执行仍失败。
- 同一代码放到短英文路径后可以正常构建。

#### 根因

路径经过 CMake、Ninja、编译器和 Windows 文件 API 多层传递。某一层对 Unicode、零宽字符
或路径规范化的处理不一致，最终生成的字节序列或规范路径与真实目录不一致。

#### 排查操作

```powershell
# 确认当前真实路径
(Get-Location).Path

# 检查文件是否能被 PowerShell 直接枚举
Get-ChildItem -LiteralPath .

# 把源码映射到短路径后重新配置，验证是否确实是路径问题
cmd /c mklink /J C:\Users\CC\.cache\rkav-src "<工程绝对路径>"
cmake -S C:\Users\CC\.cache\rkav-src -B C:\Users\CC\.cache\rkav-build\debug -G Ninja
```

排查思路是只改变一个变量：代码和编译器不变，仅改变路径。如果短路径成功，问题基本可以
定位到工具链路径处理，而不是 C++ 代码。

#### 解决措施

- 创建短 ASCII Junction：`C:\Users\CC\.cache\rkav-src` 指向真实源码目录。
- 构建目录也放到短 ASCII 路径下，不把生成文件写回原目录。
- Windows 构建脚本自动复用该短路径，减少人工配置错误。

#### 验证

Debug 和 Release 均能完整编译，30 项测试全部通过。

#### 涉及知识点

- Unicode 路径、零宽字符和路径规范化。
- Windows Junction 与符号链接。
- out-of-source build。
- 控制变量法定位构建问题。

#### 面试回答参考

项目路径里有一个肉眼不可见的零宽字符，部分 Windows Ninja 工具链无法一致处理。我的排查
方式是保持代码和工具链不变，只把源码映射到短 ASCII 路径重新构建，确认根因在路径层。
最终通过 Junction 和独立短路径构建目录解决，并把处理固化到 PowerShell 构建脚本中。

### P002：没有完整外设和 SDK，如何开始开发

**来源：实际遇到**
**状态：Mock 阶段已解决，真实后端待继续**

#### 问题

项目目标需要摄像头、麦克风、RKNN、RGA 和 MPP，但开发初期只有 RK3568 板卡。直接等待
硬件会浪费时间，直接编写无法运行的 SDK 调用又不能验证正确性。

#### 根因

硬件依赖和业务主流程耦合时，任何缺失设备都会阻塞整个项目；同时无法区分以后出现的错误
究竟来自设备、驱动、SDK 还是并发主流程。

#### 排查操作

1. 列出不依赖硬件也必须正确的能力：数据模型、时间戳、队列、生命周期、配置和监控。
2. 列出只能实机验证的能力：V4L2 协商、ALSA 参数、RKNN 兼容性、MPP 码流。
3. 为 Capture、Inference、Encoder、Sink 定义稳定接口。
4. 使用确定性 Mock 实现接口，并通过故障注入覆盖异常路径。

#### 解决措施

- 采用依赖倒置，将硬件能力隐藏在接口之后。
- 先实现完整 Mock 管道和自动化测试。
- 保留真实后端编译开关，但不写未验证的伪实现。
- 明确文档边界，Checksum 包不宣称是真实编码。

#### 验证

无外设条件下，双路管道、慢推理、慢输出、XRUN 和设备断连均可重复验证。

#### 涉及知识点

- 依赖倒置、接口隔离和策略模式。
- Mock、Fake 与真实后端的边界。
- 可测试架构和增量替换。
- 硬件抽象层。

#### 面试回答参考

我没有用不可运行的硬件调用填充工程，而是先稳定公共契约。Capture、Inference、Encoder 和
Sink 都通过接口隔离，Mock 按真实节拍生成可校验数据并支持故障注入。这样后续接 V4L2、
ALSA、RKNN 和 MPP 时只替换后端，主流程和 30 项回归测试继续复用。

### P003：下游变慢导致队列和内存无限增长

**来源：设计时主动规避**
**状态：已通过慢推理和慢 Sink 集成测试**

#### 问题

采集速度高于推理、编码或输出速度时，如果队列无限增长，短期看起来没有丢帧，长期会造成
内存上涨、延迟越来越大，最后 OOM。

#### 典型现象

- RSS 持续增长。
- 当前画面越来越落后于真实时间。
- 停止时需要很久才能处理完积压。
- 低负载测试正常，运行时间越长越差。

#### 排查操作

1. 记录每个队列的当前深度、容量、高水位和丢弃数。
2. 比较生产速率和消费速率。
3. 人工增加推理或 Sink 延迟，观察队列是否突破容量。
4. 检查延迟增长是处理耗时增加还是排队时间增加。

#### 解决措施

- 所有线程间队列固定容量。
- 推理队列使用 `keep_latest`，只处理最新画面。
- 视频编码队列通常 `drop_oldest`，以实时性优先。
- 音频队列阻塞生产者，超时后显式失败，不静默丢音频。
- 指标记录高水位、超时和丢弃数量。

#### 验证

慢推理测试确认推理队列容量保持 1 并产生可观测丢帧；慢 Sink 测试确认其队列容量保持 2，
同时采集线程继续前进。

#### 涉及知识点

- 生产者/消费者、背压和 Little's Law。
- 吞吐量、排队延迟和内存之间的关系。
- 实时性与数据完整性的业务取舍。

#### 面试回答参考

我没有使用无限队列，而是为每条跨线程通道定义容量和溢出策略。视频追求新鲜度，允许丢旧；
音频追求连续性，默认阻塞并超时报错。我还通过慢推理、慢 Sink 故障注入检查队列高水位，
证明内存不会随运行时间无限增长。

### P004：固定 sleep 导致视频时间长期漂移

**来源：设计时主动规避**
**状态：已通过分数帧率误差测试**

#### 问题

使用 `sleep_for(1s / fps)` 控制帧率时，整数截断、线程调度延迟和每帧处理耗时会不断累加，
造成帧率和 PTS 长期漂移。

#### 排查操作

1. 记录第 0 帧的时间起点。
2. 比较第 N 帧实际 deadline 与公式 `start + N / fps`。
3. 长序列运行后检查误差是否随 N 线性增大。
4. 区分系统唤醒晚和理论 deadline 本身漂移。

#### 解决措施

`FramePacer` 每次都从固定起点和序号计算绝对 deadline，然后 `WaitUntil` 该时间点。即使某次
线程晚醒，下一帧仍以原始时间轴为基准，不把本次延迟累加到以后。

#### 涉及知识点

- 单调时钟、绝对 deadline、调度抖动。
- 有理数帧率和整数舍入误差。
- PTS 时间轴。

#### 面试回答参考

简单 sleep 控制帧率会把截断和调度误差逐帧累积。我用固定 epoch 加帧序号计算每帧绝对
deadline，并使用单调时钟等待。测试验证长序列误差保持有界，而不是随帧数增长。

### P005：阻塞线程收到停止请求后无法退出

**来源：设计时主动规避**
**状态：已通过队列取消、Drain 和 Abort 测试**

#### 问题

线程可能阻塞在队列条件变量、模拟采集等待或输出 I/O 中。只设置 `running=false` 并不能
自动唤醒它，主线程在 `join()` 时可能永久等待。

#### 排查操作

1. 观察停止日志停在哪个阶段。
2. 检查每个阻塞点是否同时等待“数据/空位、关闭、取消”。
3. 检查请求停止后是否调用 `notify_all()`。
4. 给停止过程设置期限并打印尚未退出的 worker。

#### 解决措施

- 使用 `std::jthread` 和 `stop_token` 进行协作式取消。
- 队列通过 `stop_callback` 在取消时唤醒条件变量。
- `Close()` 唤醒所有生产者和消费者。
- 正常退出使用 Drain，致命错误使用 Abort。
- 按采集、处理、输出依赖顺序停止和 join。

#### 涉及知识点

- 条件变量谓词、虚假唤醒。
- 协作式取消和 `stop_callback`。
- 线程生命周期、join 和死锁排查。

#### 面试回答参考

停止标志只改变状态，不能唤醒阻塞线程。我把 stop_token 纳入每个阻塞谓词，并通过
stop_callback 调用 notify_all。队列关闭也会唤醒等待者，正常路径 Drain，错误路径 Abort，
因此 join 有明确退出条件。

### P006：音频 XRUN 恢复后出现 PTS 缺口

**来源：设计时主动规避**
**状态：已通过周期 XRUN 测试**

#### 问题

音频读取发生 XRUN 后，如果先增加块序号或 PTS，再恢复并读取下一块，就会在逻辑时间轴上
跳过一段音频。听感可能出现断裂，后续音画同步也会受到影响。

#### 排查操作

1. 开启每 N 块一次的确定性 XRUN 注入。
2. 记录恢复前后块序号、PTS 和 samples_per_channel。
3. 用公式检查相邻 PTS 差是否等于块时长。
4. 检查失败读取是否已经提交序号或相位状态。

#### 解决措施

- 只有成功生成完整块后才提交 sequence、PTS 和正弦相位。
- XRUN 时调用 `Recover()`，随后重试同一个逻辑块。
- 恢复次数计入指标，不能静默吞掉错误。

#### 验证

集成测试周期注入 XRUN，最终 `recoveries_total > 0`、无致命错误，单元测试检查 PTS 连续。

#### 涉及知识点

- ALSA XRUN、事务式状态提交。
- PCM 连续性和音频时钟。
- 至少一次重试与幂等思想。

#### 面试回答参考

XRUN 的关键不只是调用 recover，还要避免先提交时间轴状态。我把 sequence、PTS 和音频相位
的推进放到成功读取之后，恢复后重试同一个逻辑块，因此不会制造隐藏的 PTS 缺口。

### P007：慢 Sink 阻塞编码和采集主链路

**来源：设计时主动规避**
**状态：已通过慢 Sink 隔离测试**

#### 问题

如果编码线程同步写文件或网络，一个慢磁盘、慢客户端或网络抖动会阻塞编码线程，继续向上
传导到采集线程，最终整条管道延迟升高。

#### 排查操作

1. 给某个 Sink 注入固定写延迟。
2. 观察采集计数是否停止、其他 Sink 是否受影响。
3. 查看每个 Sink 自己的队列高水位和丢包数。
4. 对比编码耗时与实际 Sink 写耗时。

#### 解决措施

PacketRouter 为每个 Sink 创建独立有界队列和 worker。编码线程只投递共享不可变 Packet，
实际 I/O 在 Sink worker 中完成。

#### 涉及知识点

- Fan-out、隔离舱模式和异步 I/O 边界。
- 共享不可变对象。
- 慢消费者隔离。

#### 面试回答参考

我没有让编码线程直接执行输出 I/O，而是为每个 Sink 建立独立有界队列和工作线程。慢输出
只会消耗自己的队列预算，测试证明采集仍持续，其他输出不被它拖住。

### P008：输出故障应该全局退出还是隔离

**来源：设计时主动规避**
**状态：required/optional 两种场景均已测试**

#### 问题

所有输出失败都退出会降低可用性，所有输出失败都忽略又可能导致“进程正常但没有核心结果”。

#### 解决措施

配置为每个输出定义 `required`：

- required Sink 失败：记录第一个错误并停止全局管道。
- optional Sink 失败：记录一次错误，隔离该 Sink，主链路继续。

#### 排查操作

使用 `fail_after_packets` 确定性注入故障，分别检查 Application 状态、错误计数、其他流的
处理计数和最终退出结果。

#### 涉及知识点

- 故障域、降级服务和关键依赖。
- 可用性与正确性权衡。
- 配置驱动的容错策略。

#### 面试回答参考

### P009：设备持续失联造成忙等或假存活

**来源：设计时主动规避**
**状态：已通过持续断连集成测试**

#### 问题

设备错误标记为 retryable 后，如果立即无限重试，会占满 CPU 并刷爆日志；如果线程一直重试
却从不成功，系统看似存活，实际没有数据输出。

#### 排查操作

1. 注入从指定音频块开始的持续断连。
2. 观察 CPU、错误频率和最近成功进展时间。
3. 区分“线程循环仍在跑”和“成功处理计数仍在增加”。
4. 检查监控是否能指出具体卡死 worker。

#### 解决措施

- 可重试错误之间固定退避 100 ms，避免忙等。
- 每个 worker 记录最近成功进展时间。
- 监控线程超过阈值后报告具体 worker stall 并受控退出。

#### 涉及知识点

- 指数/固定退避、错误风暴。
- liveness 与 progress。
- watchdog 和健康检查。

#### 面试回答参考

可重试不等于永远重试。我先加退避避免 CPU 忙等，再记录 worker 最近成功进展。线程即使
仍在循环，只要超过阈值没有成功数据，也会被监控判定为 stall 并停止，这解决了假存活。

### P011：stride/Buffer 大小错误造成越界或花屏

**来源：设计时主动规避**
**状态：已通过非法 RGB stride 测试**

#### 问题

图像 width 表示有效像素宽度，stride 表示内存中一行实际字节数。硬件常因对齐使 stride
大于有效宽度。如果错误使用 `width * bytes_per_pixel` 访问每行，可能出现错行、花屏或越界。

#### 排查操作

1. 打印 width、height、format、stride、bytesused 和 Buffer size。
2. 按格式计算最小 stride 和最小总字节数。
3. 使用小图和带 padding 的人工样例验证行首地址。
4. 开启 ASan 检查越界。

#### 解决措施

帧进入下游前执行 `ValidateVideoFrame`；像素访问基于 `y * stride + x * bytes_per_pixel`，
不假设行紧密排列。

#### 涉及知识点

- 图像内存布局、对齐、stride/pitch。
- Buffer 边界检查。
- V4L2/RGA/MPP 格式兼容基础。

#### 面试回答参考

我把 stride 作为帧契约的一部分，而不是从 width 临时推导。所有后端输出先校验最小 stride
和 Buffer 大小，逐行访问使用真实 stride，这为以后接 V4L2 和 RGA 的对齐内存做好了准备。

### P015：启动到一半失败导致资源泄漏

### P016：多线程连锁错误覆盖真正根因

### P017：在信号处理函数中执行不安全操作

**来源：设计时主动规避**
**状态：代码已实现，SIGINT/SIGTERM 已在 RK3568 Linux 进程级验证**

#### 问题

SIGINT/SIGTERM 可能在任意代码执行点打断线程。信号处理函数中调用日志、加锁、分配内存或

#### 解决措施

handler 只设置 `volatile sig_atomic_t` 标志；普通控制线程轮询该标志，然后调用线程安全的

均为 0。

#### 涉及知识点

- POSIX 异步信号安全。
- 中断上下文与普通线程上下文。
- sig_atomic_t。

#### 面试回答参考

信号 handler 不能当普通回调使用。我只在其中设置 sig_atomic_t，日志、锁和 Application
停止都转移到普通控制线程执行。我在 RK3568 上分别发送 SIGTERM 和 SIGINT，两次都以 0 退出，
停止原因正确且队列排空，证明该关闭路径已完成进程级验证。

#### 面试回答参考

我先确认 `duration 0` 的产品语义，再通过进程、日志进展和信号退出验证区分“长期运行”和“卡死”。
程序能持续产出指标并响应两种信号正常排空队列，因此这是预期无限运行，不是线程死锁。

### P036：Mock 计数被误认为来自真实摄像头和麦克风

**来源：实际遇到**
**状态：已澄清；真实采集仍未开始**

#### 问题

长稳日志出现 `video_captured_total`、`audio_captured_total` 和 `inference_results_total`，但当时
摄像头和麦克风并未接入。若仅根据字段名汇报，会错误声称已完成真实音视频采集和模型识别。

#### 排查操作

1. 检查 `mock.json` 中各 backend 是否为 `mock`。
2. 检查进程启动参数和实现类。
3. 对照 `lsusb`、V4L2 和 ALSA 枚举，确认外接设备是否存在。
4. 检查 codec 是否为 Checksum Mock 类型，而非 H.264/AAC。

#### 解决措施

文档和汇报中把计数表述为“Mock 视频帧、Mock 音频块和 Mock 推理结果”。这些数据用于验证线程、
队列、时间戳、路由、停止和资源稳定性，不用于证明真实画质、音质、NPU 性能或编码性能。

#### 验证

当前配置明确为 Mock；项目文档也列出真实 V4L2、ALSA、RKNN 和 MPP 尚未完成。

#### 涉及知识点

- Test Double/Mock 与真实后端。
- 控制面、数据面和验收口径。
- 指标名称不等于数据来源证据。

#### 面试回答参考

我主动区分了“管道在目标板工作”和“真实媒体后端完成”。当前计数由 Mock 按30FPS和20ms音频块
生成，证明调度、背压、生命周期和可观测性，但不代表摄像头、麦克风或NPU已经接入。

### P037：不理解板端 CPU、RSS、温度和采样行数

**来源：实际遇到**
**状态：已解释并完成 600 秒资源基线**

#### 问题

板端长稳出现 `cpu=84%`、`rss=4376kB`、`temp=45555mC` 和 CSV 61 行，容易产生以下误解：
CPU 来自电脑、84% 占满四核、温度是 45555 摄氏度、61 行代表 61 次有效采样。

#### 排查操作

```bash
cat /sys/devices/system/cpu/online
grep '^VmRSS:' /proc/<pid>/status
head -n 1 /proc/stat
awk '{print $14+$15}' /proc/<pid>/stat
cat /sys/class/thermal/thermal_zone0/temp
wc -l resources.csv
```

#### 解决措施

脚本从板端 `/proc` 和 `/sys` 采集。CPU 百分比按核数归一，约84%表示约0.84个核心；RSS是进程
常驻物理内存；温度节点以毫摄氏度表示，45555mC约为45.6摄氏度；CSV 61行包含1行表头和60个样本。

#### 验证

600 秒测试中 RSS 稳定在4376kB、线程数稳定为9、温度45.0到46.1摄氏度、无热中止、错误和
队列丢弃为0。

#### 涉及知识点

- `/proc/<pid>/stat`、`/proc/stat` 的 CPU tick 差分。
- RSS、虚拟内存与内存泄漏趋势。
- thermal zone 的单位和 CPU DVFS。
- 采样间隔、表头和数据点数量。

#### 面试回答参考

我为精简 Buildroot 写了只依赖 `/proc`、`/sys` 和 BusyBox 的长稳脚本，通过相邻采样的进程与
系统tick差计算CPU。600秒内RSS和线程数稳定、温升约1摄氏度、无丢包，说明当前Mock基线稳定；
同时我明确这不是未来真实采集和NPU负载的性能结论。

### P038：存在设备节点就认为外设已经接入

**来源：实际遇到**
**状态：已完成 BSP 能力盘点；外接设备待到货验证**

#### 问题

板端已有 `/dev/video0` 到 `/dev/video8` 和 `/dev/snd`，但这些可能来自板载 ISP、虚拟视频节点
或板载声卡。节点存在不等于外接 USB 摄像头和麦克风已经枚举，也不能直接把设备号写死。

#### 排查操作

```bash
lsusb
dmesg | tail -n 100
v4l2-ctl --list-devices
v4l2-ctl -d /dev/videoN --all
v4l2-ctl -d /dev/videoN --list-formats-ext
arecord -l
cat /proc/asound/cards
```

外设到货后比较插入前后的输出，建立 USB VID/PID、驱动、设备节点和能力之间的映射。

#### 解决措施

配置不默认使用 `/dev/video0` 或 `hw:1,0`。先枚举并按设备能力选择，再把实际节点作为配置输入；
必要时使用稳定的 udev 名称或 CARD 标识，而不是依赖可能变化的序号。

#### 验证

当前只验证了工具、库和 BSP 节点存在。外接 UVC/UAC 设备的枚举、采集和重插恢复仍待执行。

#### 涉及知识点

- V4L2/media controller 节点与实体拓扑。
- ALSA card/device 编号和 USB 热插拔。
- 设备枚举证据与能力协商。

#### 面试回答参考

我不会看到 `/dev/video0` 就直接打开，而是通过 `v4l2-ctl --list-devices` 和插拔前后差异把物理
设备映射到节点，再查询实际格式。这样避免把ISP统计节点当采集节点，也避免USB重插后编号变化。

### P039：按品牌或分辨率选择 USB 摄像头

**来源：设计时主动规避**
**状态：已确定筛选原则；绿联 2K 自动对焦双麦克风款待到货验证**

#### 问题

“大品牌”“2K”和“免驱”不能单独证明摄像头适合旧 Buildroot。项目同时需要视频和音频，真正
关键的是标准 UVC 视频、USB Audio/UAC 麦克风、Linux 兼容性以及设备支持的像素格式和帧率。

#### 排查操作

采购前向商家确认具体 SKU、Linux 免驱、UVC/UAC 和退货条件。到货后执行 P038 中的枚举命令，
重点检查 MJPEG/YUYV、1280x720或1920x1080、30FPS和麦克风声卡。

#### 解决措施

选择绿联129元的2K自动对焦双麦克风款，主要考虑当前项目和后续电脑会议/直播复用。板端首次接入
仍从720p或1080p@30开始，不直接追求2K；若UVC/UAC或目标格式不支持，则按退货条件处理。

#### 验证

当前是采购决策，不是实现证据。只有 `lsusb`、V4L2格式枚举、ALSA录音样本和长稳通过后，才能
标记为板端兼容。

#### 涉及知识点

- USB Video Class、USB Audio Class。
- 分辨率、帧率、像素格式和USB带宽。
- 采购规格、驱动兼容和到货验收的区别。

#### 面试回答参考

我没有按品牌直接判断兼容，而是把需求转成UVC、UAC、格式、帧率和Linux驱动约束。2K用于后续
复用，板端先协商720p/1080p降低变量；采购完成仍标记待验证，直到真实采集和录音证据齐全。

### P040：用峰值读取速度判断存储卡是否适合录像

**来源：设计时主动规避**
**状态：已明确选型原则；实卡容量和持续写入待验证**

#### 问题

存储卡宣传常突出“读取100MB/s或180MB/s”，但相机录制更依赖最低持续写入。A1/A2主要描述
应用随机读写，也不是视频录像的首要指标。“项目后复用”和“24小时循环覆盖录像”还是两种需求。

#### 排查操作

1. 核对卡面和型号，不只看商品标题。
2. 录像用途检查 U3/V30；应用用途再关注 A1/A2。
3. 查询目标大疆设备的官方兼容列表。
4. 到货后做全容量真伪测试和持续写入测试，再交给板卡或相机格式化。

#### 解决措施

- 在已比较的64GB选项中，ORICO-TF30的U3/V30/A1、标称写入50MB/s，比Kingston
  SDCS3的U1/V10/A1更适合录像。
- 若优先降低未来大疆兼容风险，选择官方验证的Kingston Canvas Go! Plus
  `SDCG4/64GB`或`SDCG4/128GB`。
- 若需求是24小时循环覆盖，应改选High Endurance，而不是普通消费级运动相机卡。

#### 验证

当前完成规格比较，尚未完成实卡真伪、全容量、持续写入、RK3568文件系统和大疆设备验证。

#### 涉及知识点

- U1/U3、V10/V30的最低持续写入等级。
- A1/A2随机IOPS与主机支持。
- 峰值速度、持续速度、耐久写入和兼容列表。

#### 面试回答参考

我按工作负载而不是品牌和峰值读取选卡。视频需要持续写入，所以U3/V30优先；A1/A2对运行应用
更重要。未来大疆使用还要看官方兼容列表，长期循环监控则要换高耐久介质，不能用一套指标覆盖
所有场景。

## 5. 待硬件后端阶段重点问题

### P020：RK3568 库、驱动与 SDK 版本不匹配

**来源：待硬件验证**
**状态：未解决，先建立排查方法**

#### 可能问题

RKNN、RGA 和 MPP 同时依赖开发头文件、用户态动态库以及内核驱动。三者版本只要不匹配，
就可能出现编译成功但初始化或运行失败的问题。

#### 可能现象

- 编译期找不到头文件或符号。
- 链接成功但运行时报 `undefined symbol`。
- RKNN 初始化失败、模型版本不兼容或 NPU 驱动报错。
- MPP/RGA API 与网上示例签名不同。

#### 排查操作

```bash
uname -a
cat /etc/os-release
ldconfig -p | grep -E 'rknn|rga|rockchip_mpp'
readelf -d ./rkav-gateway
ldd ./rkav-gateway
nm -D /path/to/library.so | grep symbol_name
dmesg | tail -n 200
```

还需记录 BSP 镜像、内核、NPU 驱动、Runtime、开发头文件和模型转换工具的完整版本，不能只
写“用了最新版”。

#### 解决原则

- 优先使用板卡/BSP 厂商提供的同一套版本矩阵。
- 编译头文件版本必须与运行时动态库匹配。
- 先运行官方最小样例，再接入项目接口。
- 每升级一个组件都重新执行固定输入回归和长稳测试。

#### 涉及知识点

- ABI、动态链接、SONAME、驱动/用户态版本矩阵。
- 交叉编译 sysroot。
- BSP 与通用 Linux 的差异。

#### 面试回答建议

目前不能说已经解决。可以回答：我已经把硬件 SDK 隔离在独立后端，并准备了版本基线和
动态链接排查流程；待板端 Runtime 明确后先验证官方样例，再增量接入。

### P021：V4L2 请求参数与设备实际协商参数不同

**来源：待硬件验证**
**状态：未解决**

#### 可能问题

请求 1280x720@30 RGB，并不代表设备会接受；USB 摄像头可能只支持 MJPEG/YUYV 某些组合。
驱动返回的 width、height、pixelformat、bytesperline 和 sizeimage 才是实际契约。

#### 排查操作

```bash
v4l2-ctl --list-devices
v4l2-ctl -d /dev/video0 --all
v4l2-ctl -d /dev/video0 --list-formats-ext
v4l2-ctl -d /dev/video0 --stream-mmap=4 --stream-count=300 --stream-to=/dev/null
dmesg | tail -n 100
```

#### 解决原则

- Open 时执行能力枚举和格式协商。
- 使用 `VIDIOC_G_FMT` 返回值填充 `VideoCapabilities`。
- 按实际 bytesperline/bytesused 访问数据。
- 先 MMAP 正确，再尝试 DMA-BUF 零拷贝。

#### 涉及知识点

- V4L2 ioctl、能力协商、MMAP streaming。
- UVC 带宽和像素格式。
- 驱动返回参数优先于请求参数。

### P022：ALSA 设备号变化和真实 XRUN

**来源：待硬件验证**
**状态：未解决**

#### 可能问题

- USB 麦克风插拔后 card 编号变化，写死 `hw:1,0` 失效。
- 请求 48 kHz/单声道时设备实际只支持其他组合。
- period/buffer 设置不合理导致频繁 XRUN。
- `snd_pcm_readi` 短读、EPIPE 或 ENODEV 没有正确映射。

#### 排查操作

```bash
arecord -l
arecord -L
cat /proc/asound/cards
arecord -D hw:CARD=<name>,DEV=0 --dump-hw-params /dev/null
arecord -D <device> -f S16_LE -r 48000 -c 1 -d 10 /tmp/test.wav
dmesg | tail -n 100
```

#### 解决原则

- 优先使用稳定 CARD 名称或配置匹配，不依赖易变化的数字编号。
- 读取 ALSA 实际协商参数。
- 明确 period size、buffer size 和阻塞模式。
- EPIPE 映射为 XRUN 并走 `Recover()`；ENODEV 映射为断连。
- 用样本数推进音频 PTS，不用每次读取完成的墙上时间代替。

#### 涉及知识点

- ALSA PCM 状态机和硬件参数协商。
- period、buffer、latency 和 XRUN。
- USB 设备枚举稳定性。

## 6. 面试追问速查

### 6.1 为什么不用无锁队列

当前数据速率和线程数量下，正确的有界语义、可取消阻塞、Drain/Abort 和可测试性优先于理论
上的极限吞吐。互斥锁版本更容易证明正确。后续只有指标证明队列锁成为瓶颈时，才考虑 SPSC
ring buffer，并重新实现关闭、背压和指标语义。

### 6.2 为什么使用 shared_ptr

同一视频帧需要同时发给推理和编码，同一编码包又要发给多个 Sink。共享只读 Buffer 可以
避免大块像素或 payload 复制。代价是原子引用计数，因此后续零拷贝优化时仍需用指标验证，
不能默认它没有成本。

### 6.3 为什么不用异常处理所有错误

采集失败、XRUN、队列超时属于预期运行结果，使用 `Result<T>` 可以明确分类和恢复策略；
线程入口仍捕获未预期异常，转成结构化致命错误，避免异常逃出线程导致 `std::terminate`。

### 6.4 为什么监控最近进展，不只看线程状态

线程可能在无限重试、空循环或等待永远不会来的条件，操作系统仍认为它存活。实时服务真正
关心的是是否持续产生有效帧、块或包，所以最近成功进展比单纯 alive 更有意义。

### 6.5 为什么不能现在做全链路零拷贝

零拷贝取决于摄像头格式、V4L2 缓冲类型、RGA/RKNN/MPP 对 DMA-BUF 的支持、stride 和缓存
同步。当前硬件组合未知，提前写死很容易得到不可运行的设计。项目先保留 MemoryKind 和
DMA-BUF 契约，待 CPU 路径正确后逐段替换并测量收益。

## 8. 面试表达原则

1. 先说影响，再说错误信息；面试官更关心你是否理解业务后果。
2. 排查要体现假设和证据，不要说“试了很多方法最后好了”。
3. 说明为什么选择当前方案，以及它的代价。
4. 用测试、指标和长稳结果证明修复，不用“看起来没问题”。
5. 对待硬件验证项明确说尚未完成，再讲已经准备的接口和排查方法。
6. 不背诵代码细节，重点解释不变量：时间戳连续、内存有界、线程可停、错误可定位。
