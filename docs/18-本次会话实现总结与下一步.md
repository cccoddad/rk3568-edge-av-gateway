# 本次会话实现总结与下一步

更新日期：2026-08-27

## 1. 文档用途

本文是本轮长会话的正式交接记录，覆盖从准备 RKNN 1.4.0 开发文件、独立 NPU 冒烟、
YOLOv5 模型转换和真实摄像头单帧检测，到把 RKNN 后端接入主程序并解决交叉编译 ABI 问题
的全过程。

以后开启新会话时，应先阅读本文和
[项目当前开发状态](19-项目当前开发状态.md)，不要从聊天记录猜测当前进度。

## 2. 当前一句话结论

项目已经证明真实绿联摄像头、USB 麦克风、RKNN Runtime 1.4.0、NPU 驱动 0.8.2 和
RK3568 YOLOv5s INT8 模型分别可用；主程序已经新增 `RknnInferenceEngine`，CI 也生成了
最高只要求 GLIBC 2.34 的 AArch64 程序。当前停在 Ubuntu 本地构建机下载
`ubuntu:22.04` Docker 基础镜像这一步，尚未把新主程序部署到板端运行。

真实摄像头输出仍为 MJPEG，而主程序 RKNN 后端当前只接收 CPU RGB/BGR 帧。下一项代码
开发是增加 MJPEG 解码预处理层，不是重写 RKNN 后处理。

### 4.3 实现 C17 RKNN 独立冒烟程序

新增并迭代 `tools/rknn_smoke` 独立程序，完成：

- 加载 RKNN 模型；
- 查询 Runtime、驱动、模型输入和输出 tensor；
- 设置 UINT8 NHWC 输入；
- 连续执行指定次数推理；
- 读取浮点输出并检查全部值有限；
- 输出推理耗时和摘要；
- 使用构建脚本拒绝高于板端 GLIBC 2.35 的程序。

最初使用 Ubuntu 24.04 G++ 13 构建的 C++ 冒烟程序最高要求 GLIBC 2.38，无法在板端启动。
将独立冒烟程序改为 C17 后，最高要求降到 GLIBC 2.34，板端兼容性通过。

### 4.4 使用 TF 卡建立可靠部署链路

大文件 TFTP 曾触发旧网卡驱动 watchdog 和内核异常，因此本阶段停止使用网口传输大文件，
改为：

```text
Ubuntu 生成部署目录
-> VMware 共享目录进入 Windows 下载目录
-> Windows 复制到 TF 卡
-> 安全弹出 TF 卡
-> 插入板端右侧 push-push TF 卡槽
-> 板端从 /media/sdcard0 校验并复制到 /tmp 或 /userdata
-> sync 和 umount 后再拔卡
```

TF 卡以 exFAT/FUSE 自动挂载在 `/media/sdcard0`，带有 `noexec`，所以不能直接在卡上执行程序。
正确做法是复制到板端文件系统，再执行 `chmod 0755`。

### 4.5 完成 MobileNet NPU 冒烟

板端自带模型：

```text
/usr/share/model/RK356X/mobilenet_v1.rknn
```

已经完成单次和 100 次连续推理。约 11 ms 的单次核心推理意味着 100 次通常只需一两秒，
因此“眨几下眼就结束”是正常现象，不是脚本跳过执行。

板端自带猫、狗测试图片只用于分类模型基础设施验证，不代表项目业务目标。MobileNet 证明
Runtime 和 NPU 能运行；项目最终需要输出类别、置信度和检测框的目标检测模型。

### 4.6 完成真实摄像头单帧预处理

从绿联摄像头 `/dev/video9` 抓取 1280x720 MJPEG 帧，完成：

```text
MJPEG/JPEG 解码
-> RGB 转换
-> 缩放为模型输入尺寸
-> 保存原始 RGB 字节
-> 输入 RKNN
```

MobileNet 对真实摄像头帧推理成功，且 NPU/IOMMU 中断计数增加，证明不是只运行了 CPU
模拟器。

### 4.7 转换 RK3568 YOLOv5s INT8 模型

在 x86_64 Docker 环境中使用 RKNN Toolkit2 1.4.0，将官方 YOLOv5s ONNX 转为 RK3568
INT8 RKNN 模型。最终模型 SHA-256：

```text
dccc47b4988107957a1806f6a85b688ee36b86074c7ba21231782b6ea8bdac0d
```

第一次转换没有显式设置目标平台，工具提示默认使用 RK3566。该产物没有部署；最终脚本明确
设置 `target_platform='rk3568'` 并重新转换、导出和验证。

### 4.8 实现 YOLOv5 C17 后处理和板端检测工具

在 `tools/rknn_smoke/yolov5_postprocess.c` 中实现：

- 80x80、40x40、20x20 三尺度输出解码；
- anchor 和 stride 还原；
- object/class 阈值过滤；
- 逐类别 NMS；
- 输出容量和非法 tensor 检查。

固定 `bus.jpg` 在模拟器得到 4 个 person 和 1 个 bus。随后在板端完成真实摄像头单帧检测，
并完成连续 10 次推理基线。

连续推理实测：

| 项目 | 结果 |
|---|---:|
| 连续次数 | 10 |
| 最后一次核心 NPU 耗时 | 93445 us |
| 含输出和日志整体吞吐 | 5.848 次/秒 |
| NPU 中断增量 | 10 |
| 新增 NPU/IOMMU 错误 | 0 |
| 温度 | 46.111 -> 48.333 摄氏度 |

开机日志中的 6 条 NPU 功耗模型 warning 是历史日志；运行前后增量比较证明本轮没有新增错误。

### 4.9 把 RKNN YOLOv5 接入主程序

提交 `6cefd516af885ae65672b42f3217feddbc633cfd` 完成主程序后端接入，主要包括：

- 新增 `RknnInferenceEngine`，使用 Pimpl 隔离厂商 SDK；
- 校验模型为一个 640x640 NHWC 输入和 80/40/20 三路 NCHW 输出；
- 接收 CPU RGB888/BGR888 帧并缩放到 640x640；
- 调用 RKNN Runtime 完成量化输入、推理和浮点输出获取；
- 复用 C17 YOLOv5 解码和 NMS；
- 将模型坐标映射回来源帧尺寸；
- 保留来源 frame sequence 和 PTS；
- 使用 RAII 保证所有错误路径释放 RKNN 输出；
- 配置新增模型路径、最大推理帧率、目标阈值、NMS 阈值和最大检测数；
- Application 工厂支持 `backend=rknn`；
- 在推理队列之前按 `max_fps` 抽帧，初始策略为 5 FPS、容量 1、`keep_latest`；
- 单元和集成测试增加到 37 项。

### 4.10 固定 AArch64 C++ 构建环境

Ubuntu 24.04 的 AArch64 G++ 13 即使静态链接 `libstdc++/libgcc`，仍会把 GLIBC 2.36 和
2.38 符号带入主程序。为此新增：

- `tools/docker/rknn-gateway-build.Dockerfile`；
- `tools/build_rknn_gateway_container.sh`；
- 独立的 `build/cross-aarch64-rknn-ubuntu22.04` 构建目录；
- ELF 架构、动态依赖和 GLIBC 版本硬门禁。

正式交叉编译固定使用 Ubuntu 22.04、GCC/G++ 11.4.0。GitHub CI 已验证生成程序：

```text
NEEDED: librknnrt.so
NEEDED: libm.so.6
NEEDED: libc.so.6
NEEDED: ld-linux-aarch64.so.1
最高 GLIBC: 2.34
rknn_gateway_build=passed
```

## 6. 下一步操作

### 6.1 第一步：从国内代理取得 Ubuntu 22.04 基础镜像

在 Ubuntu 执行。该步骤不会重新解压源码：

```bash
sg docker -c 'bash -s' <<'RKAV'
set -euo pipefail

MIRROR_IMAGE="m.daocloud.io/docker.io/library/ubuntu:22.04"
LOCAL_IMAGE="ubuntu:22.04"

pull_passed=0
for attempt in 1 2 3 4 5
do
    echo "pull_attempt=$attempt"
    if docker pull "$MIRROR_IMAGE"; then
        pull_passed=1
        break
    fi
    sleep 5
done

test "$pull_passed" -eq 1
docker tag "$MIRROR_IMAGE" "$LOCAL_IMAGE"
docker image inspect "$LOCAL_IMAGE" \
    --format 'image_id={{.Id}} architecture={{.Architecture}} os={{.Os}}'
RKAV
```

如果这一段仍失败，应先保存完整错误，不要删除已经解压的项目，也不要重新安装 Ubuntu。

### 6.2 第二步：继续构建并生成 Windows 部署包

基础镜像准备成功后执行：

```bash
sg docker -c 'bash -s' <<'RKAV'
set -euo pipefail
export LC_ALL=C

PROJECT_ROOT="$HOME/rk3568-work/rkav-8c95223"
RKNN_SDK_ROOT="$HOME/rk3568-work/vendor/rknpu2-v1.4.0/runtime/RK356X/Linux/librknn_api"
ARTIFACT_DIR="$PROJECT_ROOT/out/aarch64-rknn-gateway"
DEPLOY_DIR="/mnt/hgfs/WinDownloads/rkav-8c95223-rknn-gateway-deploy"

test -f "$PROJECT_ROOT/tools/build_rknn_gateway_container.sh"
test -f "$RKNN_SDK_ROOT/include/rknn_api.h"
test -f "$RKNN_SDK_ROOT/aarch64/librknnrt.so"
test ! -e "$DEPLOY_DIR"

cd "$PROJECT_ROOT"
export RKNN_SDK_ROOT
sh ./tools/build_rknn_gateway_container.sh

file "$ARTIFACT_DIR/rkav-gateway"
readelf -d "$ARTIFACT_DIR/rkav-gateway" | grep 'Shared library'
readelf --version-info "$ARTIFACT_DIR/rkav-gateway" |
    grep -o 'GLIBC_[0-9.]*' |
    sort -Vu

(
    cd "$ARTIFACT_DIR"
    sha256sum --check SHA256SUMS
)

mkdir -p "$DEPLOY_DIR"
cp "$ARTIFACT_DIR/rkav-gateway" "$DEPLOY_DIR/"
cp "$ARTIFACT_DIR/rk3568-rknn-rgb.json" "$DEPLOY_DIR/"

(
    cd "$DEPLOY_DIR"
    sha256sum rkav-gateway rk3568-rknn-rgb.json > SHA256SUMS
    sha256sum --check SHA256SUMS
)

ls -lh "$DEPLOY_DIR"
cat "$DEPLOY_DIR/SHA256SUMS"
echo "deploy_dir=$DEPLOY_DIR"
RKAV
```

### 6.3 第三步：通过 TF 卡部署到板端

本地构建完成后，流程为：

1. Windows 把 `rkav-8c95223-rknn-gateway-deploy` 复制到 TF 卡根目录；
2. 使用 Windows“安全弹出”；
3. 插入板端右侧 TF 卡槽；
4. 板端校验 SHA-256；
5. 复制到 `/userdata/rkav/gateway-8c95223`；
6. `chmod 0755 rkav-gateway`；
7. `sync` 并卸载 TF 卡；
8. 运行 `config/rk3568-rknn-rgb.json` 对应的 Mock RGB + RKNN 10 秒测试；
9. 对比运行前后 NPU 中断和内核错误增量。

板端测试命令应在看到本地生成的实际 SHA-256 后再固定，不能提前猜测程序哈希。

### 6.4 第四步：实现 MJPEG 解码预处理接口

主程序 Mock RGB + RKNN 通过后，下一项代码开发为：

1. 新增稳定的 `IVideoDecoder` 或等价预处理接口；
2. 使用成熟 JPEG 解码库把 `/dev/video9` 的 MJPEG payload 转为 CPU RGB/BGR；
3. 保留 sequence、PTS、来源宽高和 stride；
4. 把解码错误分类为可恢复帧错误或设备级错误；
5. 增加固定 JPEG、损坏 JPEG、尺寸变化和连续帧测试；
6. 将输出交给现有 `RknnInferenceEngine`；
7. 先做 10 秒和 60 秒，再做 30 分钟长稳；
8. 最后再评估 RGA、DMA-BUF 和零拷贝优化。

## 7. 当前必须遵守的边界

- 已经证明独立工具可以对真实摄像头单帧执行 YOLOv5 NPU 检测。
- 已经实现主程序 RKNN 后端并通过交叉构建，不等于主程序已经在板端运行。
- 主程序尚不能直接处理 MJPEG，因此不能宣称实时摄像头目标检测完成。
- Checksum 编码器不是 H.264/AAC，当前也没有 MP4 或 RTSP 成品输出。
- 板端 NPU 开机 warning 没有在推理期间新增，但设备树功耗模型缺失仍是残余风险。
- 12 V 风扇不能直接接入 5 V 接口；当前计划更换为 5 V USB 风扇，不影响短时功能验证。
