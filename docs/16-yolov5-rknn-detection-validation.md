# RK3568 YOLOv5s RKNN 目标检测验证

## 1. 阶段边界

本阶段把独立 RKNN 验证从 MobileNet 分类推进到 YOLOv5s 目标检测模型，已经完成：

- 使用 RKNN Toolkit2 1.4.0 将官方 YOLOv5s ONNX 转换为 RK3568 INT8 RKNN 模型；
- 在 x86_64 转换机模拟器上得到可重复的类别、置信度和检测框；
- 在 RK3568 板端真实 NPU 上加载模型并取得三路完整输出张量；
- 在仓库中实现与官方示例公式一致的纯 C17 解码、阈值过滤和逐类别 NMS。

这一阶段仍是独立工具验证，主音视频管道的 inference 配置仍为 Mock。只有后续把 RKNN
后端接入 `IInferenceEngine` 并完成实时摄像头验收后，才能把主程序描述为真实 NPU 检测。

## 3. x86_64 模拟器参考结果

官方 `bus.jpg` 在 Toolkit2 模拟器中得到 5 个 NMS 后结果：

| 类别 | 置信度 | 框坐标 `[left, top, right, bottom]` |
| --- | ---: | --- |
| person | 0.8223356 | `[473.267, 231.938, 562.127, 519.760]` |
| person | 0.8179780 | `[211.990, 245.029, 283.708, 513.937]` |
| person | 0.7971193 | `[115.250, 232.442, 207.784, 546.110]` |
| person | 0.4627231 | `[79.092, 339.180, 121.600, 514.235]` |
| bus | 0.7545359 | `[86.417, 134.418, 558.108, 460.418]` |

阈值沿用官方 v1.4.0 示例：object/class probability 阈值为 `0.25`，逐类别 NMS IoU 阈值为
`0.45`。

官方示例分别过滤 object probability 和最高 class probability，最终打印的 confidence 是两者
乘积。因此保留下来的结果中，乘积 confidence 可能低于 `0.25`；这与“直接按乘积使用 0.25
阈值”的策略不同，后续接入主程序时必须通过配置明确选择。

## 4. RK3568 真实 NPU 实测

目标板环境保持不变：

- Buildroot 2018.02-rc3，Linux 4.19.232，AArch64；
- glibc 2.35；
- RKNN Runtime API 1.4.0，NPU driver 0.8.2；
- `/usr/lib/librknnrt.so` MD5 为 `757e7f089e657a7fc28c67c71738f0cc`。

板端先对 TF 卡部署包执行 SHA-256 全量校验，再复制到 `/tmp`，卸载 TF 卡后运行。实测结果：

- `rknn_init`、输入设置、执行、三路输出读取和释放全部成功；
- 三路输出元素数分别为 `1632000`、`408000` 和 `102000`；
- 三路反量化浮点输出全部为有限值；
- 核心推理耗时 `95564 us`；
- NPU 中断计数从 `0` 增加到 `1`；
- 推理退出码为 0，内核日志没有 NPU 或 IOMMU fault。

这证明最终 RK3568 模型不是只在转换机模拟器可用，而是已经在目标板真实 NPU 上完整执行。

### 4.1 板端 C17 后处理验证

提交 `72b9f96` 的新版工具在相同 `bus.jpg` RGB 输入上完成真实 NPU 推理和 C17 后处理：

- 解码前候选框为 55 个，逐类别 NMS 后保留 5 个；
- 检测类别为 4 个 `person` 和 1 个 `bus`，与转换机参考结果一致；
- NPU 中断计数从 1 增加到 2；
- 核心推理耗时为 `96406 us`；
- 程序退出码为 0，内核没有 NPU/IOMMU 错误。

模拟器和板端在个别框坐标、置信度上存在量化计算差异，但类别和目标数量一致，检测框均覆盖
相同物体。

### 4.2 真实摄像头单帧目标检测

2026-08-27 使用 `/dev/video9` 的 1280x720、30 FPS MJPEG 模式连续抓取 5 帧，选择第 5 帧
进行验证：

- 原始 JPEG 为 52224 字节，SHA-256 为
  `e4ac1b83a48a9d8d5f2232dce15ec1f72bd9d47add0a0ff51956f4e80a72376b`；
- GStreamer 成功完成 JPEG 解码、缩放和 RGB 转换；
- 模型输入为严格的 1228800 字节，SHA-256 为
  `03ffa3355ad4950cc67543772087dadeb0d57a589a7c69b6f4bd7cf478e1fa7a`；
- 后处理从 42 个候选框中经 NMS 保留 4 个结果；
- 结果包含 2 个 `person`，最高置信度为 `0.93233359`；
- 另外输出 `backpack` 和 `chair`，分别对应画面中的较弱候选；
- 核心推理耗时为 `102104 us`；
- NPU 中断计数从 2 增加到 3，内核错误计数为 0。

持久化证据保存在板端
`/userdata/rkav/yolov5-camera/19700101-052441-1109`，其中包含原始 JPEG、模型 RGB 输入、
抓取/预处理/推理日志和 `SHA256SUMS`。目录日期显示 1970 是因为板端没有校准 RTC，不影响
单调时钟、文件内容或校验结果。

### 4.3 连续采集与预处理基线

同一摄像头使用单条 GStreamer 管道连续处理 30 帧，从 1280x720 MJPEG 解码、缩放并转换为
640x640 RGB：

- 30 个输出全部严格等于 1228800 字节，无缺失或尺寸异常；
- 总耗时为 1990 ms，折算吞吐为 15.075 FPS；
- 第 30 帧 RGB 的 SHA-256 为
  `0561ba3158671893548ed5524d07e49fe275b6c29ab402029408558196407912`。

首次尝试在同一脚本中执行 10 次重复推理时，发现 `rknn-smoke` 在同时传入迭代数和 RGB
文件的四参数调用中没有解析迭代数，实际只运行了默认的 1 次。该次约 95 ms 的单次结果仅用于
定位问题，不计入 10 次推理基线。参数解析现已独立测试，覆盖带 RGB 输入的重复推理调用；修复
后的板端结果需要重新采集。

## 5. C17 后处理实现

`tools/rknn_smoke/yolov5_postprocess.c` 不依赖 RKNN SDK，可在主机单独测试。它实现：

1. 严格验证三个输出网格与 `8/16/32` stride 的对应关系；
2. 按 NCHW 布局读取三组 anchor 的 `x/y/w/h/object/class` logits；
3. 使用 YOLOv5 的 sigmoid、`xy*2-0.5` 和 `(wh*2)^2*anchor` 公式解码；
4. 选择每个候选框的最高类别概率；
5. 按置信度稳定排序并执行逐类别 NMS；
6. 限制返回容量并显式报告截断，避免无界输出。

`tools/test_yolov5_postprocess.sh` 使用严格编译警告构建主机测试，覆盖命令行参数解析、三尺度
候选解码、同类别重叠框抑制、不同类别保留、输出容量截断和非法网格拒绝。CI 先运行这些测试，
再使用锁定的 RKNN 1.4.0 开发文件交叉编译 AArch64 `rknn-smoke`。
