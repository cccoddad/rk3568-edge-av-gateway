## 2. 当前精确停止点

当前板端仍运行旧 4.19.232。未压缩 v3 归档不得刷写；压缩候选也不得刷写，因为只通过了容量检查，尚未确认
旧 U-Boot 的 boot image magic、页大小、解压支持和环境变量。没有执行 `dd`、升级工具、重启、部署、板端配置
修改、网关启动或高负载测试。

`U-Boot` 是 Linux 前最早执行的启动程序；`FIT boot` 是把内核、设备树等组合在一起的启动镜像；`DTB` 是
设备树二进制，描述网口、供电、串口等板级连线。它们主机侧生成成功，不等同于目标板能启动。

## 3. 本轮问题归档

已在两份项目问题汇总中连续补齐并保留证据边界：

- P095：通用 SDK 与 GEC 板级适配不是一回事；
- P096--P105：Full SDK 离线检出、主机构建工具、SDK 配置、Python wrapper、并发与依赖门禁；
- P106--P110：IO 电源域、PCRE 检查局限、`fdtget` 假失败、Wi-Fi 控制器与串口差异；
- P111--P112：v3 缺失 `};` 的真实语法失败，以及跳过 C 预处理导致的直接 DTC 假失败；
- P113：未压缩 FIT 超出 boot/recovery 容量，直接刷写被阻断；
- P114：压缩候选仅尺寸可行，仍需 U-Boot 格式兼容性证据。

P111--P114 不是“已解决的整板问题”：P111/P112 是构建和验证方法问题且已经闭合；P113/P114 是仍然有效的
刷写安全门禁。

## 4. 下一段任务的固定顺序

1. **RK3568 串口终端，只读**：先检查没有残留 `rkav-gateway`，再读取旧
   `/dev/block/by-name/boot` 的前若干 KiB，记录 magic、页大小、压缩线索；只读查询 U-Boot 环境和启动日志。
   不执行 `dd of=...`、升级工具或重启。
2. 根据真实旧 boot 格式判定是否能使用压缩路线。不能确认兼容时停止，不猜测分区表、不刷写，转而取得匹配的
   升级布局/原厂启动格式资料。
3. 若格式明确兼容，**Ubuntu 终端**仅在隔离 SDK 视图显式设置 `RK_BOOT_COMPRESSED=y`，重新构建、检查
   `zboot.img`/打包产物、哈希、容量、DTB 结构和归档；不能复用只做尺寸试验的旧 `zboot.img` 作为部署物。
4. 完成压缩候选离线验证后，必须向用户说明写入风险并取得新的明确确认；首次启动只观察串口、内核、eMMC、
   串口、GMAC1、USB 枚举和 rootfs 挂载，不启动 `rkav-gateway`、NPU、MPP/RGA 或高负载业务。
5. 首次 5.10 能启动也只是启动验证。旧 4.19 rootfs 与 5.10 内核、驱动及 MPP/RGA/RKNN 用户态兼容性仍未验证；
   必须逐项核验，不能把它说成媒体链路、硬件编码、MP4、AAC 或 RTSP 已完成。
