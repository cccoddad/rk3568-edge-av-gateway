# ZLMediaKit 流媒体服务层升级方案（待实施）

更新日期：2026-09-12
状态：**方案已定，未实施**。本文件用于让后续会话和交接文档知道该升级计划。

## 1. 决策与定位

为网关补充**流媒体服务层**，工具选择 **ZLMediaKit**（国内主流、支持 GB28181/WebRTC、
行业认知度高）。定位与红线：

- **属于本项目**的输出层扩展，不做第二个独立项目；
- **不改网关架构**：继续使用已验证的 FFmpeg RTSP push 输出（含断连恢复、传输选项、
  超时守卫、资源收尾），只把推流目标从任意服务器改为 ZLMediaKit；
- **不进程内嵌** ZLM（mk_api 集成需要交叉编译、生命周期与线程管理，收益相同、风险更高）；
- 目标能力：多客户端并发、多协议输出（RTSP/RTMP/HTTP-FLV/HLS/WebRTC）、浏览器直接
  观看、REST API 管理。

## 2. 架构位置

```text
升级前（当前）：
V4L2/ALSA -> RKNN -> CPU OSD -> MPP/FFmpeg H.264/AAC -> FFmpeg RTSP push -> 外部服务器

升级后（本项目 + ZLMediaKit 独立进程）：
V4L2/ALSA -> RKNN -> CPU OSD -> MPP/FFmpeg H.264/AAC -> FFmpeg RTSP push
                                                              |
                                                              v
                                                    [ZLMediaKit 服务器]
                                                              |
                              +-------------------------------+-------------------------------+
                              |               |               |               |               |
                           RTSP 多客户端   RTMP         HTTP-FLV           HLS           WebRTC
                          （VLC/ffplay） （直播平台）  （浏览器）        （浏览器）    （低延迟预览）
```

网关与 ZLM 是两个独立进程，可同机（板端）或分机（PC/局域网）。

## 3. 与固定路线的关系

- **不改变既定顺序**：收口三硬件长稳 → USB 断连 → FFmpeg MP4 软件基线 → OSD →
  MPP/RGA → RTSP 与恢复 → systemd 及 2/12 小时长稳。
- **阶段 1（PC 预研）** 可在无硬件时并行进行，不触碰板端资源；
- **阶段 2（板端部署）** 排在板端 MPP/RGA 与 RTSP 验证之后，与 systemd 阶段合并验收；
- 板端部署前需评估 ZLM 的 CPU/内存开销，摄像头/麦克风/NPU 仍由网关独占。

## 4. 实施计划

### 阶段 1：PC 预研（无硬件，可立即进行）

1. 获取 ZLM：优先官方预编译包（x86_64），否则源码构建；
2. 网关配置指向 `rtsp://127.0.0.1:8554/live`（或 ZLM 实际端口），推流；
3. 验证项：
   - 3 路客户端**并发** RTSP 拉流，互不干扰，流参数与网关侧一致；
   - HTTP-FLV 拉流可用；
   - WebRTC 会话可用（无头环境受限时如实记录验证方式与限制）；
   - 拉流延迟粗测（记录测量方法，不夸大）；
   - ZLM 重启后网关断连恢复联动（与 69 号交接的重连机制配合）。
4. 产出：证据目录 + 部署说明 + 可写简历的实测数字。

### 阶段 2：板端部署（需硬件）

1. aarch64 获取/构建 ZLM，与网关同机部署；
2. systemd 单元与日志、资源限制；
3. 验收：多客户端并发、协议可用、CPU/RSS 开销、与网关长稳联动。

## 5. 简历口径与红线

- **可写**：实际验证过的客户端路数、协议、延迟范围、部署平台（PC 或 RK3568）。
- **禁止**：未实测的"120 小时""50+ 客户端""<300ms"等数字（参见
  [简历项目经历修改经验总结](66-简历项目经历修改经验总结.md) 的"只写跑通的"原则）。
- 表述模板（阶段 1 完成后按实测填充）：
  "部署 ZLMediaKit 流媒体服务，网关推流后支持 N 路客户端并发 RTSP 拉流与 HTTP-FLV
  播放，实测延迟 X ms（平台：PC/板端）"。

## 6. 待定项

- ZLM 版本与获取方式（预编译包 vs 源码构建）；
- WebRTC 在无头环境下的验证方法；
- 板端 CPU/内存预算与限流参数；
- 是否保留 MediaMTX（单二进制、部署最简）作为轻量备选方案。

## 7. 涉及名词

- **流媒体服务器**：接收推流并分发给多客户端、可转多协议的独立服务进程。
- **推流/拉流**：网关向服务器发送媒体（RTSP ANNOUNCE/RECORD）；客户端从服务器取流
  （RTSP DESCRIBE/PLAY 或 HTTP-FLV/HLS/WebRTC）。
- **GB28181**：国内安防设备联网国标协议，ZLM 支持其信令与媒体转发。
- **WebRTC**：浏览器原生实时通信协议，局域网延迟通常低于传统 RTSP 拉流。
