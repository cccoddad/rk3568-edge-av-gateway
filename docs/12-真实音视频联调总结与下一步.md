## 3. 三个执行环境必须分清

本轮大量操作失败并非命令本身错误，而是命令运行在了错误的机器或文件不在那台机器上。

| 提示符/窗口 | 环境 | 主要用途 |
|---|---|---|
| `PS C:\...>` | Windows PowerShell | 文件保存、TFTP 服务、网络配置、查看下载文件 |
| `china@ubuntu:~$` | VMware Ubuntu | AArch64 交叉编译、使用 CMake/Ninja、复制产物到共享目录 |
| `root@RK356X:/#` | RK3568 Buildroot 板端 | 设备枚举、真实采集、运行 ARM64 程序、板端长稳 |

文档中的命令以后都应先看环境标签。Windows 文件不能直接用 Ubuntu 路径读取；Ubuntu 编译
出的 ARM64 程序也不能在 Windows 或 x86_64 Ubuntu 上直接运行。

## 4. 本轮对话主要完成的事情

### 4.1 验收摄像头和麦克风

板端识别到 UGREEN Camera 2K：

| 项目 | 实测结果 |
|---|---|
| USB VID:PID | `0c45:636f` |
| 视频画面节点 | `/dev/video9` |
| 元数据节点 | `/dev/video10`，不能用于画面采集 |
| 麦克风 | ALSA card 2、device 0，即 `hw:2,0` |
| 目标视频格式 | MJPEG 1280x720@30 FPS |
| 目标音频格式 | S16_LE、48 kHz、双声道 |

先用系统工具做了独立最小验证，而不是直接修改主程序：

- `v4l2-ctl` 成功抓取一帧 1280x720 JPEG，大小 58,120 bytes，JPEG 魔数正确。
- `arecord` 成功录制 10 秒 WAV，大小 1,920,044 bytes，参数为 48 kHz、16 bit、双声道。
- 300 帧视频持续采集完成，稳态约 29.11 FPS，启动阶段出现 1 个 dropped buffer。
- 2 秒录音复验退出码为 0，证明 USB 麦克风能力和 `hw:2,0` 配置有效。

这一步把“硬件/驱动问题”和“项目代码问题”分开。只有系统工具先成功，才继续实现项目后端。

### 4.3 实现真实 V4L2 视频后端

项目新增 V4L2 后端并通过配置选择：

```json
{
  "video": {
    "backend": "v4l2",
    "device": "/dev/video9",
    "format": "MJPEG",
    "width": 1280,
    "height": 720,
    "fps": 30
  }
}
```

后端完成了设备打开、能力检查、格式协商、MMAP buffer、入队、poll、出队和 stream off。程序
不是只相信 JSON 请求值，而是读取驱动最终协商结果。

真实视频 60 秒运行得到 1,741 帧，平均约 29.0 FPS，错误、恢复和队列丢弃均为 0。

### 4.4 实现真实 ALSA 音频后端

板端是旧 Buildroot。为避免 Ubuntu 新版 `libasound` 与板端运行环境产生动态 ABI 依赖，ALSA
后端直接使用 Linux ALSA PCM 内核 UAPI，并继续输出静态 ARM64 可执行文件。

该后端不是一次完成，而是通过多轮板端证据修复：

1. 修复 `std::byte*` 到 `int16_t*` 的错误转换，使用 `reinterpret_cast`。
2. 正确初始化 ALSA 硬件参数结构，解决 `HW_REFINE` 返回 `EINVAL`。
3. 完成硬件参数设置后显式启动 Capture。
4. 正确读取 `SNDRV_PCM_IOCTL_READI_FRAMES` 的 `transfer.result`，而不是把 ioctl 返回值当帧数。
5. 使用累计样本数推进音频 PTS，保证 20 ms 音频块时间轴连续。
6. 在 `poll()` 返回错误时查询 PCM 状态，区分 XRUN、挂起和物理断开。
7. 补充恢复失败日志，使故障不再被笼统归类。

最终 10 秒真实双路结果为 500 个音频块、285 帧视频和 785 个完整路由/消费包；60 秒结果为
3,000 个音频块、1,741 帧视频和 4,741 个包。两次均无错误、无恢复、无队列丢弃。

### 4.5 验证真实设备下的生命周期

真实设备阻塞读取没有破坏程序退出：

- `SIGTERM`：退出码 0，`reason=signal`，已产生数据全部处理，队列关闭并排空。
- `SIGINT`：退出码 0，`reason=signal`，已产生数据全部处理，队列关闭并排空。
- 定时结束：退出码 0，`reason=run_duration_elapsed`。
- USB 断连：程序识别致命设备故障，退出码 1，`reason=fatal_error`，仍排空已进入管道的数据。

这证明程序不只是“能采集”，也能在正常停止和硬件故障时结束所有线程并保存根因。

### 4.6 完成 30 分钟真实音视频长稳

| 指标 | 实测结果 |
|---|---:|
| 运行时长 | 30 分钟 |
| 脚本退出码 / 热保护 | 0 / 未触发 |
| 音频采集/编码 | 90,000 / 90,000 块 |
| 视频采集/编码 | 52,340 / 52,340 帧 |
| 平均视频帧率 | 约 29.08 FPS |
| 路由/消费 | 142,340 / 142,340 包 |
| 错误 / 恢复 / 队列丢弃 | 0 / 0 / 0 |
| 稳态 RSS | 9,728 KiB，保持稳定 |
| 线程数 | 9，保持稳定 |
| 进程 CPU | 约 11%～12% |
| SoC 温度 | 约 48.9～50.6 C |

第 0 秒采到的 RSS 4 KiB、线程数 1 是采样脚本早于程序完成初始化的竞态值，不代表稳定运行
状态。第 10 秒以后才是有效稳态基线。

### 4.7 完成 USB 拔插故障注入

摄像头的视频和麦克风共用一根 USB 线。拔线后：

- V4L2 报告 `device_disconnected`。
- ALSA 报告 `device_disconnected`，原生错误码 19，即 `ENODEV`。
- 健康检查在 3 秒无进展后终止应用。
- 程序自行退出，`forced_stop=0`，退出码 1。
- 已产生的包全部消费，所有队列均关闭并排空。

重新插入后仍枚举为 `/dev/video9` 和 `hw:2,0`，v7 再运行 10 秒得到 500 个音频块、285 帧
视频、零错误和零丢弃。

### 4.8 盘点 RKNN/NPU 环境

板端实测结果：

| 项目 | 结果 |
|---|---|
| SoC | RK3568 |
| NPU 驱动 | `rknpu 0.8.2 20220829` |
| 设备接口 | DRM，存在 `/dev/dri/card1`、`/dev/dri/renderD129` |
| RKNN Runtime | `/usr/lib/librknnrt.so`，约 3.5 MiB |
| Runtime 版本 | 1.4.0，构建日期 2022-09-09 |
| 板端模型 | `/usr/share/model/RK356X/mobilenet_v1.rknn`，约 4.3 MiB |
| `rknn_api.h` | 板端不存在 |

文件指纹：

```text
757e7f089e657a7fc28c67c71738f0cc  /usr/lib/librknnrt.so
1f051a1d9be7411a29e22fcaff030b62  /usr/share/model/RK356X/mobilenet_v1.rknn
```

没有 `/dev/rknpu` 不等于 NPU 不存在。本镜像的 RKNPU 驱动通过 DRM 节点工作，驱动初始化日志
和 `renderD129` 才是关键证据。

### 4.9 识别并停止不可靠的大文件网口回传方案

尝试将 7.7 MiB RKNN 运行库和模型压缩包由板端通过 TFTP 上传 Windows 时，先出现：

```text
NETDEV WATCHDOG: eth0 (rk_gmac-dwmac): transmit queue 0 timed out
rk_gmac-dwmac ... Reset adapter
```

再次尝试后日志还出现 `__memcpy -> dev_gro_receive -> napi_gro_receive -> stmmac_napi_poll` 路径
的内核异常。证据强烈指向旧 BSP 的 `rk_gmac-dwmac/stmmac` 网卡驱动在这类持续传输下不稳定，
而不是普通的文件名或 PowerShell 语法错误。

因此当前决策是：

- 不再通过该网口/TFTP 从板端回传大文件。
- 小型程序下发也只在链路稳定时使用，并校验文件大小或哈希。
- 优先从匹配版本的官方 SDK 获取开发文件。
- 板端已有的 MobileNet 模型直接在原路径运行，无需先复制到电脑。
- 必须转移板端大文件时，使用存储卡和读卡器，先识别设备节点后再挂载，不能盲写。

## 6. 下一步总体策略

下一阶段遵循两个原则：版本先匹配、单变量推进。

```text
冻结真实 A/V 基线
    -> 独立 RKNN Runtime 冒烟测试
    -> 确认检测模型和输入输出契约
    -> 静态图片真实推理
    -> 实现 RknnInferenceEngine
    -> 解决 MJPEG 解码/图像预处理
    -> 接入实时视频
    -> 10 秒 / 60 秒 / 30 分钟 / 故障注入
    -> 再进入 MPP H.264 和实际输出
```

不要同时加入 RKNN、RGA、MPP 和 RTSP。一次变化过多会让任何错误都无法归因。

## 7. 下一步详细实施方案

### 7.1 M6-0：冻结当前基线

目标：保证接 RKNN 时不会破坏已经稳定的真实音视频。

需要保留：

- 当前 v7 源码和配置。
- Windows 34 项测试结果。
- 10 秒真实 A/V 基线：500 音频块、285 视频帧、785 包、零错误。
- 30 分钟真实 A/V 证据包及 SHA-256。
- USB 断连和重新插入后的日志。

验收：任何 RKNN 修改合入前后，Mock 测试和真实 A/V 10 秒基线都必须继续通过。

### 7.2 M6-1：准备与板端匹配的 RKNN 开发文件

目标：在 Ubuntu 取得与板端 Runtime 1.4.0 相匹配的 `rknn_api.h` 和 AArch64 链接库。

优先顺序：

1. 与板卡镜像/BSP 同版本的厂商 SDK。
2. Rockchip 官方 RKNN Toolkit2 v1.4.0 对应 runtime 开发文件。
3. 只有前两者无法取得时，才单独评估升级板端 Runtime、驱动和模型；不能只替换其中一个。

不能直接使用最新头文件、最新 Runtime 或最新 Model Zoo 模型，因为模型格式、Runtime ABI 和
NPU 驱动存在版本约束。

验收：Ubuntu 可以用 AArch64 交叉编译器完成最小程序链接，产物架构正确；板端运行时打印的
Runtime 和驱动版本与盘点结果一致。

### 7.3 M6-2：先做独立 RKNN 冒烟程序

目标：暂不改主程序，只验证 NPU 最小闭环。

最小程序只做：

1. 读取 `/usr/share/model/RK356X/mobilenet_v1.rknn`。
2. `rknn_init`。
3. 查询 SDK、输入和输出 tensor 属性。
4. 准备符合模型尺寸和类型的测试输入。
5. `rknn_run` 和 `rknn_outputs_get`。
6. 打印输出摘要并释放资源。

板端自带 MobileNet 是分类模型，只用于证明“模型能加载、NPU 能执行、输入输出可读取”。它
不能直接替代项目当前返回检测框的 `DetectionBatch` 接口。

验收标准：

- 退出码为 0。
- 日志明确打印 Runtime、驱动、模型输入输出属性。
- 连续运行至少 100 次，无初始化失败、无内存持续增长、无 NPU 驱动错误。
- 错误场景能区分模型不兼容、输入不匹配、运行失败和设备不可用。

### 7.4 M6-3：确定真正的目标检测模型

目标：选择与 RK3568、Runtime 1.4.0 和项目接口兼容的检测模型。

必须记录：

- 原始框架模型和转换工具版本。
- `.rknn` 的目标平台与 toolkit 版本。
- 输入宽高、布局、数据类型、量化参数、颜色顺序和归一化方式。
- 输出 tensor 数量、shape、量化参数和后处理算法。
- 类别表、置信度阈值、NMS 阈值。

如果只能获得最新版模型而无法与 1.4.0 兼容，应先获得匹配 BSP/SDK，再决定是否整体升级；
不能靠反复替换单个 `.so` 试错。

验收：用一张固定图片得到可重复的检测框，并与桌面参考结果比较，而不是只看 `rknn_run=0`。

### 7.5 M6-4：实现 `RknnInferenceEngine`

目标：遵守现有 `IInferenceEngine` 接口，用配置在 `mock` 与 `rknn` 之间切换。

实现边界：

- 模型只在 `Open()`/初始化阶段加载一次。
- 每帧执行预处理、输入设置、运行、输出获取、反量化和 NMS。
- 结果携带源帧序号和 PTS，继续使用过期结果策略。
- 所有 RKNN 返回码映射为项目 `Error` 分类。
- Runtime 资源使用 RAII，正常停止和异常路径都释放。
- 保留 Mock 后端和现有测试，不把 RKNN 依赖传播到公共核心。

验收：Mock 回归不变；静态图片通过项目接口得到与独立冒烟程序一致的结果。

### 7.6 M6-5：解决摄像头图像到模型 tensor 的转换

当前摄像头输入是 MJPEG，V4L2 buffer 中是压缩 JPEG 数据，不能直接把 payload 当 RGB tensor
送入 RKNN。需要从下面两条路线中按证据选择：

| 路线 | 优点 | 代价 |
|---|---|---|
| MJPEG 720p -> JPEG 解码 -> resize/letterbox | 保留接近 30 FPS 和较低 USB 带宽 | 需要 JPEG 解码，随后再接 RGA 或 CPU 预处理 |
| YUYV 640x480@30 -> 色彩转换/resize | 数据容易理解，不需要 JPEG 解码 | 分辨率较低，USB 数据量更大 |

先完成 CPU 参考路径并校验几何映射，再考虑 RGA/DMA-BUF 优化。性能优化不能先于正确性。

验收：固定输入在 CPU 与最终硬件预处理路径得到等价 tensor；检测框能正确映射回原始画面。

### 7.7 M6-6：接入实时视频并做分级验证

执行顺序：

1. 10 秒：确认启动、帧数、推理数、错误和退出。
2. 60 秒：检查平均 FPS、推理延迟、队列高水位和丢帧策略。
3. 慢推理注入：确认 `keep_latest` 生效，延迟不无限积累。
4. SIGINT/SIGTERM：确认真实 RKNN 下仍能排空并退出。
5. 30 分钟：采集 RSS、线程、CPU、温度、NPU 负载和最终指标。
6. USB 拔插：确认设备错误仍被正确分类。

建议验收口径：错误为 0；RSS 和线程稳定；检测结果有固定图片对照；视频积压时允许按策略丢旧，
但内存不能随时间增长；退出后所有队列关闭并排空。

### 7.8 M7：真实编码与输出

RKNN 阶段稳定后再按顺序推进：

```text
RGA 硬件预处理
    -> MPP H.264 编码
    -> AAC 编码
    -> MP4 文件
    -> RTSP 推流
```

每接入一个模块都重复“最小程序 -> 接口实现 -> Mock 回归 -> 板端短测 -> 故障注入 -> 长稳”。

## 8. 文件传输的后续规则

### 8.1 可以继续使用 TFTP 的情况

- 文件较小。
- Windows 接收/发送端先启动。
- 板端 `carrier=1`，双方可以互相 ping。
- 传输后立即比较字节数或哈希。
- 一旦出现 `NETDEV WATCHDOG`、`Reset adapter` 或内核 Call trace，立即停止。

### 8.2 不再使用 TFTP 的情况

- 从板端回传数 MiB 以上文件。
- 网卡已经发生 watchdog 或内核异常后继续重试。
- 需要批量传输 SDK、模型或证据目录。

这类文件使用存储卡/读卡器，或者直接从官方匹配版本重新取得。使用存储卡前应先只读执行：

```sh
cat /proc/partitions
mount
ls -l /dev/mmcblk* 2>/dev/null
blkid 2>/dev/null
```

必须确认哪一个是启动介质、哪一个是可移动存储卡后才能挂载或写入，不能根据编号猜测。

## 9. 下一阶段完成定义

M6 只有同时满足以下条件才算完成：

- 版本清单完整：驱动、Runtime、头文件、模型转换工具和模型版本可追溯。

- 有与项目检测接口匹配的目标检测模型，不再使用分类模型代替检测模型。

- 主程序可以通过配置在 Mock 和 RKNN 间切换。
- 实时摄像头 + 麦克风 + RKNN 完成 10 秒、60 秒和 30 分钟验证。
- SIGINT、SIGTERM、USB 断连和模型错误均能正确停止并保留根因。
