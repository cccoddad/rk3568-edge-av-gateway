# 工程笔记：代表性问题的根因分析与设计决策

从项目问题台账中遴选十个代表性案例，按"现象 → 分层定位 → 根因 → 修复 → 验证 → 经验"
统一结构记录。每案均对应仓库内的实测证据。

---

## 1. ALSA 在 RKNN 加载前过早启动导致确定性 XRUN

- **现象**：三硬件联合首测，音频线程启动即报 XRUN，约 80 ms 的缓冲区在读取线程
  拉起前溢出，且每次复现时机一致。
- **定位**：按启动时序断点——RKNN 模型加载占用 NPU 与总线期间，ALSA 已 `START`，
  硬件持续推流而用户态无人消费。
- **根因**：把"打开设备"与"启动采集"耦合在初始化早期，未考虑后续重初始化耗时。
- **修复**：把 ALSA `START` 推迟到第一次 `Read()`（惰性启动）。
- **验证**：修复后 10 s 三硬件测试错误/恢复/丢弃全 0；30 分钟长稳 50,237 帧视频、
  89,983 音频块、8,714 次推理全部守恒。
- **经验**：设备"打开"不等于"开始喂数据"；初始化顺序里有阻塞点的，采集必须延迟到阻塞点之后。

## 2. MPP 配置键拼写差异使编码器配置返回 -1

- **现象**：板端 MPP H.264 短测在配置阶段返回 `MPP_NOK(-1)`，不产出码流。
- **定位**：主机侧用 MPP 1.0.4 配置服务原生编译链式探针逐键复现，锁定到单个 set 调用。
- **根因**：代码写 `rc:fps_*_denom`，而旧运行库只认历史拼写 `rc:fps_*_denorm`
  （`denom` 是 MPP 1.0.5 才引入的键）；未知键直接使 `mpp_enc_cfg_set_s32` 失败。
- **修复**：改回历史拼写，并为失败路径补充结构化步骤记录（哪个键、哪一步、什么值）。
- **验证**：候选 ELF 过 GLIBC 门禁后板端复测配置通过，10 s 短测 exit 0、零错误、
  H.264 可被独立解码器打开。
- **经验**：跨版本 SDK 的"同名不同拼写"只能靠**主机侧最小复现**锁定；
  失败日志必须带上"上下文键值"，否则 -1 无从下手。

## 3. 板端 RGA/MPP 短测失败的四个独立根因

- **现象**：RGA 硬件加速路径首测失败，表象是同一句"MPP H.264 配置失败"。
- **定位**：拆成四个互不依赖的缺陷逐个关闭——
  ①堆内存虚拟地址传给 RGA（RGA 只认物理/连续内存）；
  ②像素 stride 与实际宽度不一致（行距按宽度算，RGA 按 stride 取行）；
  ③MPP 输入模式选错（帧模式 vs 行模式）；
  ④编码器 EOS 处理空包不当。
- **修复**：逐项修正（DMA-BUF/物理连续缓冲、按对齐计算 stride、纠正输入模式、
  EOS 空包容错）。
- **验证**：10 s 短测 exit 0、零错误零丢弃；随后同一路径上完成板端 RTSP 推拉与
  30/60 秒断连恢复。
- **经验**：硬件管线的一个"失败"往往是**串行叠加的多个缺陷**；必须先拆维度再修，
  否则修一个撞下一个。

## 4. 解码路径丢失标志位导致 OSD 大面积跳帧

- **现象**：板端接入真实 OSD 后 `overlay_skipped` 大面积增长。
- **定位**：断点逐段核对"谁写 `inference_submitted`、谁消费"——采集线程置位后，
  编码线程的 MJPEG 分支解码时新建帧结构。
- **根因**：解码处聚合初始化**漏传最后一个字段**，标志恒回默认 `false`；
  等待条件恒假 → 编码线程不等推理结果（NPU ~93 ms ≫ 33 ms 帧间隔）→ 序号对不上。
  历史 PC 验收走 Mock RGB 源不经过解码分支，所以从未暴露。
- **修复**：解码时透传该标志（1 行）+ 新增覆盖 true/false 两路径的单元测试。
- **验证**：单测 66/66 通过；板端冒烟 475/475、120 h 长稳 1,558,546 次叠加零错。
- **经验**：给结构体加字段不会让旧调用点编译报错，**漏传即静默回默认值**；
  只在特定后端/格式分支出现的缺陷，必须靠路径矩阵（Mock vs 真实解码）覆盖。

## 5. ZLMediaKit WebRTC 黑屏：libsrtp 缺 OpenSSL GCM 引擎

- **现象**：板端 WebRTC 页面连接建立但无画面。
- **定位**：四层排查（页面 → ZLM 日志 → DTLS-SRTP 协商 → `srtp_create` 返回值），
  定位到加密套件 `SRTP_AEAD_AES_256_GCM` 创建失败。
- **根因**：交叉编译 libsrtp 时未带 `--enable-openssl`，GCM 后端不存在，
  协商一旦选中即失败。
- **修复**：容器内重建 libsrtp（`--enable-openssl`）并重编 ZLM，板端整体替换。
- **验证**：浏览器实拍出画面；端到端延迟 0.3~0.7 s；三路并发拉流零错误。
- **经验**："协议支持"取决于**编译期开关**而不是版本号；黑屏类问题要一路下钻到
  协商参数级别。

## 6. 白屏"变砖"：U-Boot 溢出、TF 卡劫持与假重启的三层叠加

- **现象**：刷写试验后板卡白屏，串口无输出，常规重启无效。
- **定位**：串口分层取证——U-Boot 阶段即异常；插入的 TF 卡被
  `rkimg_bootdev` 选为启动源；此前的"重启成功"实际是回滚而非真正引导。
- **根因**：三层独立问题叠加，任何一层都足以致命；TF 卡是启动源劫持的直接触发。
- **修复**：拔除 TF 卡 + 真断电重启回原厂 4.19 系统恢复；确立铁律：
  本板永久禁插 TF、禁刷 p1/p3。
- **验证**：系统恢复、串口 shell 正常、网络与全部外设枚举正常。
- **经验**：变砖≠分区损坏——**"被引导的方式"坏了同样致命**；
  复发性故障的处置顺序永远是"先串口取证、后断电"。

## 7. adb 会话退出时清理后台子进程

- **现象**：经 adb 用 `nohup ... &`、`setsid ... &` 启动的常驻进程，shell 一退就消失。
- **定位**：三种后台方式逐一实验，无一存活；父进程被 adbd 会话回收。
- **根因**：adbd 把 shell 及其子进程组挂在会话生命周期上，`nohup` 只挡 SIGHUP 挡不住进程组清理。
- **修复**：常驻服务一律走 init 脚本（`/etc/init.d/S99rkav`）拉起，不依赖 adb 通道。
- **验证**：SysV 自启 + `kill -9` 后 5 秒守护复活 + 冷启动自动拉起，三级实测通过。
- **经验**：验证通道（adb）≠ 部署通道（init）；用调试通道跑生产进程是环境性错误。

## 8. SSH 连接成功却卡在 banner：反向 DNS 慢超时

- **现象**：`ssh` 报 `Connection timed out during banner exchange`，端口通、进程活、
  loopback 正常，唯独跨网段连接超时。
- **定位**：strace 跟踪 dropbear 子进程——发 banner 前先对客户端 IP 发 PTR 查询
  （`x.x.x.x.in-addr.arpa`），`ppoll` 等满 5 秒超时才 `writev` banner；
  而 ssh 客户端 banner 等待窗约 5 秒——**差 0.6 秒输掉**。
- **根因**：板端无网关/无可用 DNS，反向解析必然慢失败，叠加在 banner 关键路径上。
- **修复**：`/etc/resolv.conf` 写 `options timeout:1 attempts:1` +
  `nameserver 127.0.0.1`（秒失败），并经 `resolv.conf.tail` 在 dhcpcd 重生成后保持。
- **验证**：banner 1 秒内送达，SSH 登录 + SCP 双向往返验收通过。
- **经验**：**"端口通"≠"协议通"**；banner 类握手超时时先 strace 看对端在等什么，
  而不是换端口碰运气。

## 9. USB MJPEG 偶发截断帧的容错设计（120 h 实测）

- **现象**：长稳中零星出现 `Premature end of JPEG file`（120 h 内 20 次）。
- **定位**：错误分类为 `retryable`，均发生在 UVC 单次读取不完整时。
- **根因**：USB 高速链路带宽/调度抖动导致帧数据缺尾；属传输层固有概率事件。
- **修复**：不修——解码器丢弃坏帧、不参与编码（避免花屏/错位框），下一帧继续；
  同路径的"过期检测"（>400 ms 丢弃）与跳帧计数严格 1:1 对账。
- **验证**：四级长稳（冒烟/2 h/12 h/120 h）全部 exit 0，跳帧率 0.0011%，
  错误计数、内核日志无恶化。
- **经验**：工业级稳定不是零瑕疵，是**瑕疵可量化、可解释、不累积**——
  分错误类别、分队列对账，比"消灭每一个异常"更接近工程真相。

## 10. 设计决策记录

**为什么用有界互斥队列而不是无锁队列？**
当前速率与线程数下，有界语义（背压、丢弃策略可测）、可取消阻塞、Drain/Abort 关闭
语义和可测试性优先于理论吞吐。互斥锁版本更容易证明正确；只有指标证明队列锁成为
瓶颈时才考虑 SPSC ring。

**为什么帧与包用 `shared_ptr` 共享？**
同一帧要同时送推理与编码、同一编码包要送多个输出。共享只读 Buffer 消除大块像素复制，
代价是原子引用计数——零拷贝优化必须用指标验证，不能假设它没有成本。

**为什么错误用 `Result<T>` 而不是异常？**
采集失败、XRUN、队列超时是预期运行结果，需要明确的分类与恢复策略；
线程入口捕获未预期异常转结构化致命错误，避免异常逃逸触发 `std::terminate`。

**为什么监控"最近进展"而不只看线程存活？**
线程可能在无限重试或死等，操作系统仍认为它活着。实时服务真正关心的是
是否持续产出有效帧/包，最近成功时间比 alive 更有意义。

**为什么三种队列用三种溢出策略？**
视频帧的新鲜度>完整性（丢旧保实时）、推理结果按最新为准（keep_latest）、
音频必须连续（block_producer 让采集端感知背压而非丢数据）——
策略跟着数据语义走，而不是一个策略套所有。

**为什么 OSD 只叠加同源结果？**
检测结果带 `sequence/PTS`，叠加前校验与当前帧同源且未过期（400 ms）；
错位的框比没有框危险——这是监控场景的正确性底线。
