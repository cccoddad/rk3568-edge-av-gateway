# 项目当前开发状态与验收记录

更新日期：2026-08-28

## 1. 当前一句话结论

项目已经从纯 Mock 基线推进到真实摄像头、真实麦克风和 RKNN NPU 分阶段验收：绿联 USB
摄像头与麦克风可用，RKNN Runtime 1.4.0、MobileNet 和 RK3568 YOLOv5s INT8 均已在
板端独立运行，主程序的 `RknnInferenceEngine` 也已在板端完成 Mock RGB + RKNN 10 秒验证。
当前已新增基于 libjpeg-turbo 的 MJPEG 解码预处理，并使用真实 UGREEN 1280x720 JPEG 样本
完成 Windows Debug/Release 回归。新产物也已完成 AArch64 交叉构建、板端真实
`/dev/video9` MJPEG + RKNN 10 秒/60 秒验证，以及真实 MJPEG + ALSA + RKNN 10 秒联合
验收。启动阶段 ALSA XRUN 已定位并修复；30 分钟三硬件联合长稳已完成，网关正常退出且业务、
NPU、资源和队列指标全部通过。原控制器因误把解码延迟滑动窗口的 3,594 个样本当成累计解码
次数而写出 `failed:1`；原始证据已保留并完成 SHA-256 校验，按累计推理次数重验收后结论为通过。
随后 Ubuntu 主机上的 FFmpeg 软件媒体基线已生成并校验真实 H.264/AAC MP4：5.020 秒、
320x180、48 kHz 双声道，PTS/DTS 单调，音视频起始 PTS 均为零。其后 CPU OSD 已在新的
5 秒软件 MP4 验收中通过：151 帧均完成精确来源帧检测框和文字叠加，零跳过、零错误和零队列丢弃。
MPP/RGA 候选后端源码已完成首次 AArch64 编译；Ubuntu 24.04 的原生交叉产物因最高要求
`GLIBC_2.38` 被兼容门禁拒绝，尚未部署或在板端运行。下一步是用既有 Ubuntu 22.04 容器得到
GLIBC 2.35 兼容产物，再做受控的板端 ABI 短测。

## 2. 已完成的工程基线

- 主链路包含视频、音频、推理、Checksum 编码、包分发、独立 Sink、结构化日志、指标和健康检查。
- 所有线程间队列都有固定容量、超时、丢弃策略和高水位指标。
- 视频允许按策略丢旧帧；音频默认不静默丢块。
- 统一使用单调微秒时间域，推理结果保留来源帧 sequence 和 PTS。
- 正常停止按采集、处理、Sink、后端的顺序排空；必需 Sink 失败会停止管道。
- 可选 FFmpeg 后端已实现 H.264 软件视频编码、AAC 音频编码和 MP4 封装；正常完成时先写
  `.part` 临时文件，成功写入 trailer 后才原子改名为最终 MP4，避免把不完整文件当成成品。
- CPU OSD 已使用独立 RGB/BGR Buffer 绘制检测框与类别/置信度文字；它只接受同一来源序号和
  PTS 的检测结果，并以有限等待避免阻塞视频线程。
- Mock 音频 XRUN、设备重试、无进展健康检查和信号退出均有测试覆盖。
- 主程序接入 JPEG 解码后，单元与集成测试增加到 43 项；Windows Debug、Release 和真实
  摄像头 JPEG 样本均已通过。既有 GitHub CI 的 Debug、Sanitizers、静态分析和 RKNN
  AArch64 交叉构建证据对应解码接入前基线；当前 JPEG/ALSA 修复产物也已单独通过 AArch64
  交叉构建、动态依赖和 GLIBC 兼容门禁。

早期 30 项板端测试、Mock 长稳和 Buildroot 部署证据仍有效，详见
[Buildroot 交叉编译与 RK3568 开发板部署总结](09-Buildroot交叉编译与RK3568开发板部署总结.md)。

传输大产物。

## 4. 真实硬件验收状态

### 4.1 摄像头与麦克风

- 绿联 USB 摄像头已识别并完成真实采集验证，目标视频节点为 `/dev/video9`。
- 摄像头实际输出为 1280x720 MJPEG，不是可直接送入 RKNN 的裸 RGB。
- 已完成单帧 MJPEG 解码、RGB 转换、模型尺寸缩放和原始 RGB 输入生成。
- USB 麦克风已完成 ALSA 枚举、真实录音和 30 分钟音视频联调。
- 三硬件第一次联合运行暴露出 ALSA 在 RKNN 初始化前过早启动导致的启动 XRUN；现已把 PCM
  `START` 和首个 PTS 推迟到第一次 `Read()`，修复版 10 秒取得 500 个音频块、零恢复和零
  工作线程错误。
- 真实摄像头、ALSA、RKNN 三硬件 30 分钟连续运行已通过。
- 带 RKNN 链路的 USB 断连和重插恢复已通过：断连后约 3.27 秒自行安全退出，重插后节点恢复，
  10 秒重启取得 279 视频帧、500 音频块和 49 次推理/NPU 中断，零错误/恢复/工作线程错误。
- 当前降级策略是必需采集设备丢失后安全退出，再由人工或未来 systemd 重启；进程内自动热重连
  尚未实现。

### 4.2 RKNN 与 YOLOv5

- 已固定 RKNN 1.4.0 的 `rknn_api.h` 和 RK356X AArch64 `librknnrt.so` 开发文件及哈希。
- C17 `rknn-smoke` 已在板端完成 MobileNet 单次和 100 次推理。
- RK3568 YOLOv5s INT8 模型已明确使用 `target_platform=rk3568` 转换并校验。
- C17 YOLOv5 后处理已实现三尺度解码、阈值过滤、逐类别 NMS 和坐标还原。
- 固定 `bus.jpg` 已得到 4 个 person 和 1 个 bus；真实摄像头单帧也已完成板端 NPU 检测。
- 连续 10 次真实输入推理无新增 NPU/IOMMU 错误，最后一次核心 NPU 耗时约 93.4 ms。

详细证据见
[RKNN 运行时独立冒烟测试](15-RKNN运行时独立冒烟测试.md)和
[RK3568 YOLOv5 目标检测验证](16-RK3568-YOLOv5目标检测验证.md)。

## 5. 主程序 RKNN 接入状态

提交 `6cefd51` 已实现：

- `RknnInferenceEngine` 和厂商 SDK 隔离层；
- RKNN 模型输入输出校验、RGB/BGR 缩放、推理和输出释放；
- YOLOv5 解码、NMS、来源坐标映射、frame sequence 与 PTS 绑定；
- `backend=rknn` 工厂选择和模型、阈值、最大帧率等配置；
- 推理队列前限帧，当前建议为 5 FPS、容量 1、`keep_latest`；
- 固定 Ubuntu 22.04、GCC/G++ 11.4.0 的 AArch64 容器构建；
- ELF 架构、动态依赖和最高 GLIBC 版本门禁。

GitHub CI 已证明 AArch64 `rkav-gateway` 最高只要求 GLIBC 2.34，低于板端 2.35。
提交 `8c95223` 的本地产物随后已部署到板端：10 秒内完成 51/51 次推理，NPU 中断从 10
增加到 61，错误、恢复、队列丢弃和新增相关内核日志均为 0，温度从 47.777 升至 50.000 摄氏度。
证据目录为 `/userdata/rkav/gateway-8c95223/mock-rgb-rknn-10s`。

当前工作区进一步实现了：

- `IVideoDecoder` 稳定接口和 libjpeg-turbo 3.1.4.1 `JpegVideoDecoder`；
- JPEG 头尺寸、最大像素数、整数溢出和分配失败保护；
- 坏 JPEG 作为可恢复帧错误跳过，同一解码器可继续处理后续帧；
- 只在推理抽帧后解码，保留原始 MJPEG 给视频编码分支；
- `video_decode` 延迟指标和 `rk3568-rknn-mjpeg.json` 板端配置。

1. 30 分钟真实三硬件长稳、USB 断连/重插恢复、Ubuntu FFmpeg 软件 MP4 和 CPU OSD 基线均已归档，
   不重复运行。
2. 使用 Ubuntu 22.04 容器完成 MPP/RGA 候选后端的 AArch64 构建、ELF 动态依赖和 GLIBC 2.35
   门禁。公开 MPP/RGA 头文件只是候选输入，不能因此宣称与板端旧运行库 ABI 已匹配。
3. 容器构建通过后，先经明确确认并确认无遗留网关，再在唯一结果目录做短时真实摄像头、ALSA、
   RKNN、RGA/MPP 联合验证；验证 H.264 elementary stream，不宣称 MP4 成品。
4. 本地 MP4 在 MPP/RGA 路径正确后接入 RTSP 和网络恢复。
5. 最后完成 systemd、SIGTERM、日志轮转及 2 小时/
   12 小时长稳。

## 8. 尚未关闭的系统问题

- Dropbear TCP 22 可达，但 OpenSSH banner 曾超时，SSH/SCP 仍未正式验收。
- RTC 没有注册设备节点，`pcf8563@0x51` probe 失败，冷启动后仍需临时校时。
- 厂商 `reboot` 曾停在 `usbdevice stop` 附近；`poweroff` 已成功，重启根因未关闭。
- NPU 开机日志含功耗模型 warning；推理期间没有新增，但设备树问题仍是残余风险。
- 默认 Checksum 编码器仍不是 H.264/AAC；已新增 Ubuntu Mock 源的 FFmpeg H.264/AAC MP4
  软件基线和 CPU OSD，但尚未在 RK3568 上做 FFmpeg/MPP 实机媒体输出、真实 OSD 或 RTSP 成品。
- MPP/RGA 候选源码尚未取得与板端 GLIBC 2.35 兼容的容器产物，且公开头文件与
  `RK356X_Linux_V1.3.2` 旧运行库的 ABI 匹配性尚未在板端短测证明；详见 P068、
  [MPP/RGA 运行时盘点与 SDK 门禁](27-MPP-RGA运行时盘点与SDK门禁.md)和
  [MPP/RGA 候选后端实现与兼容构建交接](28-MPP-RGA候选后端实现与兼容构建交接.md)。
- MJPEG、真实 ALSA 和实时 NPU 已完成 30 分钟长稳及 USB 断连/重插重启；这不等于进程内
  自动热重连、2 小时/12 小时最终长稳或真实媒体输出已经完成。
- 散热片已经安装；风扇计划更换为独立 USB 供电的 5V、约 40x40x10 mm 规格。
