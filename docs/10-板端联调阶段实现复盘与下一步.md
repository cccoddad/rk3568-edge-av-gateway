# 板端联调阶段实现复盘与下一步

更新日期：2026-08-21

后续真实摄像头与麦克风到货验收结果见
[UGREEN 2K USB 音视频设备验收](11-ugreen-camera-and-microphone-validation.md)。本文其余采购状态保留为
2026-08-21 当时的阶段记录。

## 1. 文档定位

本文复盘项目从 Windows Mock 验证推进到 RK3568 Buildroot 实机运行的过程，并把本次对话中
已经完成的实现、实测证据、涉及知识点和下一步操作集中说明。

必须先明确验收边界：当前运行的是 **Mock 音视频管道**。摄像头、麦克风、RKNN、RGA、MPP、
AAC、MP4 和 RTSP 尚未接入。硬件采购决定也不等于硬件兼容性已经验证。

## 2. 这阶段最终实现了什么

### 2.1 建立了可运行、可替换的 Mock 实时管道

当前程序已经具备视频和音频两条并发数据流：

```text
Mock 视频采集 -> 有界队列 -> Mock 推理 / Checksum 视频编码
Mock 音频采集 -> 有界队列 -> Checksum 音频编码
编码包 -> PacketRouter -> Sink
```

公共接口已经把采集、推理、编码和输出隔开。后续接入 V4L2、ALSA、RKNN 和 MPP 时，主要替换
接口实现，而不是推倒应用生命周期、队列和监控框架。

这一层已经解决或主动规避：

- 视频丢旧、音频保连续的不同溢出策略。
- 单调时钟、PTS 和节拍控制，避免长期漂移。
- Drain/Abort 两种关闭语义，保证正常退出能排空数据，故障退出能快速停止。
- 首个致命错误保留、结构化日志、指标和健康检查。
- SIGINT/SIGTERM 只触发安全的停止请求，不在信号处理函数中执行复杂逻辑。

### 2.2 识别了真实板卡运行环境

通过 COM5 串口读取到：

```text
CPU 架构：aarch64
系统：Buildroot 2018.02-rc3
内核：Linux 4.19.232
初始化方式：BusyBox / SysV init
板端构建工具：没有 cmake、g++、git
```

这个盘点改变了部署方案。原计划中的“板上原生编译 + systemd 服务”不适合当前镜像，因此保留
厂商 BSP，改用 Ubuntu x86_64 主机交叉编译 ARM64 程序。

### 2.3 实现 ARM64 静态交叉编译

新增和调整的核心文件：

- `cmake/Toolchains/aarch64-linux-gnu-static.cmake`
- `CMakePresets.json` 中的 `cross-aarch64-static` preset
- `tools/build_aarch64_static.sh`
- `tests/CMakeLists.txt` 中的交叉编译测试注册分支

工具链文件显式指定 AArch64 C/C++ 编译器和目标库查找范围，当前纯 C++ Mock 版本使用静态链接，
降低 Ubuntu 新工具链与旧 Buildroot 的 glibc、libstdc++ ABI 冲突风险。打包脚本使用 `file`
强制检查产物必须同时满足：

```text
ARM aarch64
statically linked
```

GoogleTest 原生构建继续使用 `gtest_discover_tests()`；交叉构建改为
`gtest_add_tests()`，避免 x86_64 构建机尝试执行 ARM64 测试程序。

### 2.4 建立串口、直连网口和服务诊断链路

当前实际控制路径是：

```text
SecureCRT 串口 COM5，1500000 8N1
    -> Ctrl+C 退出厂商前台测试程序
    -> 获得 root shell
    -> 配置 eth0 为 192.168.50.2/24

Windows 有线网卡
    -> 192.168.50.1/24
    -> 与板卡直连
```

已经确认网卡链路、同网段 IP、ping 和 TCP 22 端口。`/etc/network/interfaces` 的静态地址已在
物理断电后的冷启动中自动生效：板端为 `192.168.50.2/24`，Windows 为 `192.168.50.1/24`，
Windows 到板端 ping 4/4 成功。

Dropbear 已监听 22 端口，也曾用前台诊断实例监听 2222 端口。日志证明 Windows 连接确实到达
Dropbear 子进程，但连接在认证前退出或超时。因此当前结论是：**网络和 TCP 已打通，SSH 协议
握手尚未验收**。串口仍是主控制通道，小文件可以使用板端 `wget` 从电脑提供的 HTTP 服务下载。

### 2.5 完成板端功能和生命周期验证

部署到 `/root/rkav` 后已经完成：

```bash
./rkav-gateway --validate-config --config mock.json
./rkav-gateway --config mock.json --duration 10
./rkav_tests
```

实测结果：

- 配置校验通过。
- 30 项 GoogleTest 全部通过，退出码为 0。
- 10 秒 Mock 双流正常停止，错误和队列丢弃均为 0。
- SIGTERM 和 SIGINT 均在秒级采样精度内立即退出，退出码为 0。
- 两种信号停止日志的 `reason` 均为 `signal`，停止后队列关闭且排空。

这证明 ARM64 产物、应用生命周期、多线程关闭和 Mock 数据流已经在真实 RK3568 Linux 上工作，
而不仅是在 Windows 上工作。

### 2.6 实现适配旧 Buildroot 的长稳脚本

标准 Linux 验收脚本依赖 systemd 和较完整的 GNU 工具，当前板端不满足。为此新增
`tools/soak_test_buildroot.sh`，只依赖 BusyBox、`/proc` 和 `/sys`，周期采集：

- 进程 RSS。
- 线程数。
- 进程 CPU 占用。
- SoC 温度。
- CPU 当前频率。
- 网关最终计数器、延迟和队列状态。

先完成 600 秒基线，随后完成 30 分钟和 2 小时验收。两轮 M5 长稳的最终结果为：

| 指标 | 结果 |
|---|---:|
| 脚本退出码 | 0 |
| 热保护触发 | 0 |
| 30 分钟样本 | 179 个，CSV 另有 1 行表头 |
| 2 小时样本 | 240 个，CSV 另有 1 行表头 |
| RSS | 30 分钟 4360 kB、2 小时 4376 kB，均稳定 |
| 线程数 | 稳定为 9 |
| 进程 CPU | 约 82%～86%，约占用 0.82～0.86 个 CPU 核 |
| SoC 温度 | 30 分钟约 46.7～47.8 C，2 小时约 45.6～46.7 C |
| 2 小时音频捕获/编码 | 360002 / 360002 |
| 2 小时视频捕获/编码 | 216001 / 216001 |
| 2 小时推理请求/结果 | 216001 / 216001 |
| 2 小时路由/消费包 | 576003 / 576003 |
| 错误、恢复和队列丢弃 | 均为 0 |

这里的 CPU 是 RK3568 SoC 内部的 CPU，不是电脑 CPU；这些计数来自 Mock 定时生成的数据，
不是摄像头和麦克风采集的数据。

### 2.7 完成真实硬件接入前的能力盘点

板端已经确认存在：

- `v4l2-ctl`、`arecord`、`aplay` 和 `lsusb`。
- `libv4l2`、`libasound`、`librknnrt`、`librga`、`librockchip_mpp`。
- `/dev/video0` 到 `/dev/video8`、`/dev/media0` 和 `/dev/snd` 节点。

这只能证明 BSP 提供了相关工具、库和设备节点，不能证明外接 USB 摄像头和麦克风已经可用。
外设到货后必须对比插入前后的 `lsusb`、`dmesg`、V4L2 和 ALSA 枚举结果。

## 3. 这一阶段运用了哪些知识

| 领域 | 知识点 | 在项目中的用途 |
|---|---|---|
| 嵌入式 Linux | Buildroot、BusyBox、SysV init | 判断板端不能照 Ubuntu/systemd 教程操作 |
| 交叉编译 | build/host/target、toolchain、sysroot | 在 x86_64 Ubuntu 构建 ARM64 程序 |
| ELF 与 ABI | 架构、静态/动态链接、glibc 符号版本 | 避免新工具链产物无法在旧系统运行 |
| CMake | preset、toolchain、`CMAKE_CROSSCOMPILING` | 建立可重复交叉构建并调整测试登记 |
| Linux 网络 | carrier、DHCP、APIPA、静态 IP、TCP 端口 | 建立电脑与板卡直连并分层诊断 SSH |
| 串口 | UART、波特率、8N1、前台控制终端 | 无网络时获得板端 root shell |
| Linux 进程 | PID、前后台、SIGINT、SIGTERM、`wait` | 验证无限运行模式和优雅退出 |
| Linux 可观测性 | `/proc`、`/sys`、RSS、CPU tick、thermal zone | 在精简系统上实现资源长稳采样 |
| 实时管道 | 有界队列、背压、时间戳、Drain/Abort | 保证内存有界、数据有序和线程可停止 |
| 测试方法 | Mock、单元/集成测试、板端测试、长稳 | 分开证明逻辑正确、目标机可执行和持续稳定 |
| 音视频接口 | V4L2、ALSA、UVC、UAC | 为真实摄像头和麦克风接入做准备 |
| 存储选型 | U1/U3、V10/V30、A1/A2 | 区分持续录像和应用随机读写需求 |

## 4. 当前没有实现什么

面试和项目汇报时必须主动说明：

- 没有从真实摄像头采集任何一帧图像。
- 没有从真实麦克风采集 PCM。
- 当前 `video_captured_total`、`audio_captured_total` 来自 Mock 生成器。
- 当前 inference 是 Mock 延时和测试结果，不是 RKNN/NPU 模型识别。
- Checksum Encoder 不是 H.264/AAC 编码器。
- 没有实现 MP4 文件或 RTSP 推流。
- 10 分钟长稳只是当前 Mock CPU 基线，不代表真实硬件管道性能。
- 绿联摄像头和存储卡仍处于采购阶段，尚无板端枚举和采集证据。

## 5. 硬件采购结论如何理解

计划购买的绿联 2K 自动对焦双麦克风摄像头具有较好的后续复用价值，可用于当前项目，也可在
项目结束后用于电脑会议、直播和普通录像。但品牌和“免驱”宣传不能代替协议验证；到货后要确认
视频使用标准 UVC、麦克风使用 USB Audio/UAC，并查看它实际支持的分辨率、像素格式和帧率。

存储卡选择要区分两种“循环”：

- 项目结束后换到手机、相机或大疆继续使用：优先 U3/V30，A1/A2不是录像关键。
- 监控设备 24 小时循环覆盖录像：要优先 High Endurance 高耐久系列。

在已对比的两张 64GB 卡中，ORICO-TF30 的 U3/V30/A1 和标称 50MB/s 写入比 Kingston
SDCS3 的 U1/V10/A1 更适合连续视频。若目标是尽量降低未来大疆兼容风险，则优先选择大疆兼容
列表中的 Kingston Canvas Go! Plus `SDCG4/64GB` 或 `SDCG4/128GB`。

## 6. 接下来应该怎么做

### 6.1 硬件到货前

1. 向厂商或老师索取与 `RK356X_Linux_V1.3.2` 匹配的 BSP/SDK、sysroot、RKNN/RGA/MPP
   头文件和库、原理图及恢复镜像。
2. 保留当前 Mock 回归，不在接硬件时删除 Mock 实现。
3. 设计配置项，但暂时不要写死 `/dev/video0` 或 `hw:1,0`。
4. 冷启动复核静态 IP，单独记录 SSH banner 超时和 `usbdevice stop` 问题，不让它们阻塞采集主线。

### 6.2 摄像头到货当天：先验收设备，不改主程序

插入前后分别执行：

```bash
lsusb
dmesg | tail -n 100
v4l2-ctl --list-devices
v4l2-ctl -d /dev/videoN --all
v4l2-ctl -d /dev/videoN --list-formats-ext
arecord -l
```

`/dev/videoN` 必须以实际枚举结果替换，不能默认使用已有的 `/dev/video0`。先确认 USB 设备、
UVC 视频节点、UAC 声卡以及 720p/1080p@30 的格式，再做一帧图像和一段 WAV 的最小采集。

### 6.3 按单变量原则接入真实后端

```text
V4L2 摄像头
    -> ALSA 麦克风
    -> RKNN 模型推理
    -> RGA 预处理
    -> MPP H.264
    -> AAC
    -> MP4
    -> RTSP
```

每一步都遵守：设备枚举 -> 独立最小程序 -> 接入接口 -> Mock 回归 -> 故障注入 -> 板端长稳。
不要一次同时加入摄像头、麦克风、NPU 和编码器，否则失败时无法判断是哪一层造成。

### 6.4 下一里程碑验收标准

真实摄像头和麦克风接入后，至少保留：

- 设备型号、USB VID/PID、驱动和协商格式。
- 一帧原始图像或可验证的视频样本。
- 一段可播放 WAV 及其采样率、声道、格式。
- 30 项 Mock 回归继续通过。
- 真实采集 30 分钟资源曲线、错误数、丢帧/丢块、队列高水位和温度。
- 断开/重连摄像头和麦克风的恢复行为。

## 7. 面试表达参考

### 7.1 30 秒版本

我实现了一个可替换后端的 C++20 实时音视频管道，先用 Mock 验证有界队列、时间戳、错误恢复和
优雅退出。目标板是旧 Buildroot，没有本机构建工具，所以我在 Ubuntu 上建立 AArch64 静态交叉
编译，并解决了 GoogleTest 交叉构建时不能运行目标程序的问题。最终在 RK3568 上完成30项测试、
SIGINT/SIGTERM退出、30分钟和2小时双流长稳。2小时内576003个包完整路由消费，RSS约4.3MiB、
温度约45到47摄氏度、错误和丢弃为0。当前边界是尚未接入真实摄像头、麦克风、RKNN和MPP，
下一步按V4L2、ALSA、RKNN、MPP顺序逐个接入。

### 7.2 面试官追问时的回答顺序

```text
背景和约束
-> 观察到的现象
-> 分层排查证据
-> 为什么选择当前方案
-> 如何验证
-> 尚未解决和下一步
```

不要说“已经实现实时识别”或“已经完成摄像头采集”。更准确的说法是：“已经完成可运行的 Mock
管道和 RK3568 部署基线，真实设备后端进入下一阶段。”
