# UGREEN 2K USB 音视频设备验收

更新日期：2026-08-26

## 1. 验收边界

本文记录绿联 2K 摄像头及其 USB 麦克风在粤嵌 RK3568 Buildroot 板卡上的设备级和 Application
联调验收。已经证明 UVC/UAC 枚举、独立视频/录音以及项目真实 V4L2 + ALSA 双路采集可用；
RKNN、MPP、AAC、MP4 和 RTSP 仍未接入。

## 2. 实测环境与设备身份

| 项目 | 实测值 |
|---|---|
| 板端系统 | Buildroot 2018.02-rc3，Linux 4.19.232，aarch64 |
| 摄像头 | UGREEN Camera 2K |
| USB VID:PID | `0c45:636f` |
| USB 速度 | High Speed |
| UVC 版本 | 1.00 |
| 序列号 | `SN0001` |
| 视频采集节点 | `/dev/video9` |
| UVC 元数据节点 | `/dev/video10`，不能作为画面采集节点 |
| Media Controller | `/dev/media1` |
| ALSA 本次枚举 | card 2 `U2K`，device 0 `USB Audio` |

`/dev/video9` 和 ALSA card 2 是本次启动的实测编号。代码和长期部署不能假设编号永远不变，
应通过配置、能力查询和稳定设备标识选择实际设备。

## 3. 视频能力

`/dev/video9` 同时支持 MJPEG 和 YUYV：

| 格式 | 分辨率与帧率摘要 |
|---|---|
| MJPEG | 2560x1440、1920x1080、1280x720、800x600、640x480、320x240；均声明 30/25/20 FPS |
| YUYV 4:2:2 | 800x600@20；640x480 和 320x240 支持 30/25/20 FPS |

项目第一阶段选择 `MJPEG 1280x720@30 FPS`。它符合原架构的目标输入，USB 带宽压力也低于
未压缩 YUYV。`/dev/video10` 的能力是 `Metadata Capture`，格式为 UVC payload header，不能
误用来读取图像。

## 4. 最小视频样本

采集命令：

```sh
v4l2-ctl -d /dev/video9 --set-fmt-video=width=1280,height=720,pixelformat=MJPG \
  --set-parm=30 --stream-mmap=4 --stream-skip=30 --stream-count=1 \
  --stream-to=/root/ugreen-720p.jpg
```

结果：

| 检查项 | 结果 |
|---|---|
| 文件大小 | 58,120 bytes |
| JPEG 魔数 | `ff d8 ff c0` |
| JPEG 内嵌尺寸 | 1280x720 |
| SHA-256 | `930D5FF8E2031949C3D1971F76AFDC9DE392EC5D41DE23712DEB980CB7EA3893` |
| 画面完整性 | 无花屏、断行或压缩损坏 |
| 对焦 | 中央主体和背景文字可辨 |
| 曝光观察 | 逆光窗口过曝、中央主体稍暗；属于当前自动曝光表现 |

## 5. 麦克风能力与样本

ALSA 硬件参数显示：

- `S16_LE`。
- `MMAP_INTERLEAVED` 和 `RW_INTERLEAVED`。
- 双声道。
- 采样率范围 8000～48000 Hz。

录音命令：

```sh
arecord -D hw:2,0 -f S16_LE -r 48000 -c 2 -d 10 /root/ugreen-mic-10s.wav
```

结果：

| 检查项 | 结果 |
|---|---|
| 文件大小 | 1,920,044 bytes |
| PCM 参数 | 48 kHz、16 bit、双声道 |
| 样本帧数与时长 | 480,000 帧，精确 10.000 秒 |
| SHA-256 | `BF8FC8CBEEFC1D0575323A1BC78552CF0A473BA9F64487C4831FA581118EF2F3` |
| 左/右 RMS | -28.202 / -27.179 dBFS |
| 左/右峰值 | 均达到 0 dBFS |
| 左/右削波样本 | 217 / 323，占比很低，来自拍手峰值的可能性较高 |
| 直流偏移 | 两路均约 -2.6 LSB，可忽略 |
| 双声道关系 | 相关系数约 0.538，两路数据不完全相同 |

内核每次打开音频端点时出现：

```text
usb 1-1.1: 3:1: cannot get freq at ep 0x84
```

该警告没有阻止 48 kHz 双声道十秒录音成功，但后续 ALSA 后端和拔插恢复测试必须继续观察，
不能直接将它忽略为永远无害。

一次额外的 2 秒复验也成功：`arecord -D hw:2,0 -f S16_LE -r 48000 -c 2 -d 2` 退出码为 0，
产生 376 KiB WAV。`/proc/asound/card2/stream0` 确认 Capture 端点支持 `S16_LE`、双声道和
48 kHz；这排除了 USB 麦克风能力或声卡编号导致的启动失败。

## 6. 300 帧持续采集

命令：

```sh
time v4l2-ctl -d /dev/video9 --set-fmt-video=width=1280,height=720,pixelformat=MJPG \
  --set-parm=30 --stream-mmap=4 --stream-count=300 --stream-to=/dev/null
```

实测：

- 300 帧全部完成，进程正常返回。
- 实际总耗时 11.107 秒。
- 启动阶段报告 1 个 dropped buffer。
- 工具周期报告从约 24 FPS 逐步上升，最终约 29.11 FPS。
- 未出现新的 USB、UVC 或内核采集错误。

因此当前结论是：`720p MJPEG` 可持续采集，稳态接近 30 FPS；尚不能写成“严格 30 FPS、零
丢帧”。

## 7. Application 真实音视频联调

ARM64 静态程序在板端使用 `/dev/video9` 运行 10 秒和 60 秒测试，均正常打开
`MJPEG 1280x720@30 FPS`。60 秒最终指标：

| 检查项 | 结果 |
|---|---|
| 真实视频采集帧数 | 1,741 |
| 平均采集帧率 | 约 29.0 FPS |
| `errors_total` | 0 |
| 所有队列 `dropped` | 0 |
| 恢复次数 | 0 |
| 退出原因 | `run_duration_elapsed` |

这证明 V4L2 后端和完整 Application 管道可以稳定协作一分钟。30 分钟资源曲线和摄像头拔插
恢复仍是后续测试项。

ALSA 后端直接使用 Linux ALSA PCM 内核 UAPI，以避免旧 Buildroot 与 Ubuntu 交叉工具链的
动态库 ABI 不匹配。ARM64 静态程序使用真实 V4L2 和真实 ALSA 同时运行 10 秒和 60 秒，最终
指标：

| 检查项 | 结果 |
|---|---:|
| 真实音频采集/编码 | 500 / 500 块 |
| 真实视频采集/编码 | 285 / 285 帧 |
| 推理请求/结果 | 285 / 285，当前仍为 MockInference |
| 路由/消费包 | 785 / 785 |
| `errors_total` | 0 |
| `recoveries_total` | 0 |
| 所有队列 `dropped` | 0 |
| 所有队列最终状态 | `closed=true,size=0` |
| 退出原因 | `run_duration_elapsed` |

联调过程中依次修复了 ALSA 参数结构初始化、显式启动 Capture、`READI_FRAMES` 结果字段解析，
以及基于样本数递增的连续音频 PTS。最终 20 ms 音频块稳定达到每秒 50 块，证明真实音频数据
已经通过采集、编码摘要、路由和消费全链路，而不只是成功打开设备。

60 秒真实双路复验得到 3,000 个音频块、1,741 帧视频和 4,741 个完整路由/消费包；错误、恢复
和队列丢弃仍均为 0，退出时所有队列均关闭并排空。另一次运行约 5 秒后发送 `SIGTERM`，进程
退出码为 0、停止原因为 `signal`，242 个音频块和 134 帧视频全部编码及消费，证明真实设备
阻塞读取没有破坏信号停止流程。

`SIGINT` 复验同样以退出码 0 和 `reason=signal` 正常停止，229 个音频块、126 帧视频和 355 个
路由包全部处理，所有队列关闭并排空。

30 分钟真实双路长稳最终结果：

| 检查项 | 结果 |
|---|---:|
| 脚本退出码 / 热保护 | 0 / 未触发 |
| 真实音频采集/编码 | 90,000 / 90,000 块 |
| 真实视频采集/编码 | 52,340 / 52,340 帧 |
| 平均视频帧率 | 约 29.08 FPS |
| 路由/消费包 | 142,340 / 142,340 |
| `errors_total` / `recoveries_total` | 0 / 0 |
| 所有队列 `dropped` | 0 |
| 稳态 RSS / 线程数 | 9,728 KiB / 9 |
| 进程 CPU | 约 11%～12% |
| SoC 温度 | 约 48.9～50.6 C |
| 退出原因 | `run_duration_elapsed` |

启动瞬间第一条 RSS 样本为 4 KiB、线程数为 1，是采样脚本在进程完成初始化前读取 `/proc` 的
竞态值，不作为稳态基线；从第 10 秒到第 1,793 秒，RSS 均为 9,728 KiB、线程数均为 9。

拔下摄像头的单根 USB 线会同时断开 UVC 和 UAC。实测视频后端立即报告
`device_disconnected`，程序在 3 秒健康检查期限后自行以 `fatal_error` 退出，退出码为 1，
没有依赖外部强制停止，停止时 132 个已产生的包全部消费且队列全部排空。重新插入后仍枚举为
`/dev/video9` 和 `hw:2,0`，10 秒重启再次取得 500 个音频块、285 帧视频、零错误和零丢弃。

这次测试也发现 ALSA `poll()` 在物理断开时返回的 `POLLERR` 被第一版实现笼统归类为 XRUN。
后端随后改为通过 `SNDRV_PCM_IOCTL_STATUS` 区分 XRUN、挂起与断开，并补充恢复失败日志。v7
板端复验中，音频和视频均准确报告 `device_disconnected`，音频原生错误码为 19（`ENODEV`）；
程序无需外部强制停止并排空全部队列。修复没有影响正常采集，v7 的 10 秒基线仍为 500 个音频
块、285 帧视频、零错误和零丢弃。

## 8. 文件传输链路

当前 Buildroot 的 BusyBox 没有 `httpd` 和 `nc`，但具有 `tftp`。仓库新增
`tools/tftp_receive.py`，在 Windows 上以无第三方依赖的 TFTP WRQ 接收器收取单个证据文件。
JPG 和 WAV 已通过该链路传回 Windows，接收字节数与板端文件一致。

后续上传 7.7 MiB RKNN 资产时，板端出现 `NETDEV WATCHDOG`、`rk_gmac-dwmac` 网卡复位及
`stmmac` 接收路径内核异常。此后不再使用该网口回传大文件；小文件只在链路稳定时谨慎使用并
校验大小或哈希。完整判断和替代方案见
[真实音视频联调对话总结与下一步方案](12-真实音视频联调总结与下一步.md)。
