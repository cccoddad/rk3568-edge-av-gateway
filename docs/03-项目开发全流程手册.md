# RK3568 只有开发板阶段：企业级开发全流程手册

## 1. 这份手册解决什么问题

本手册把 [02-仅有开发板条件下的开发方案.md](02-仅有开发板条件下的开发方案.md) 中的架构要求转换为可以逐步执行的开发项目流程。它面向刚接触音视频和并发编程的开发者，从创建空仓库、建立编译工程开始，一直讲到 Mock 音视频管道、测试、调试、RK3568 板端运行和阶段验收。

完成本手册后，项目应当得到一个真正可运行的主干：

```text
Mock 视频源 ----> 有界队列 ----> Mock 推理 ----> Checksum 视频编码 ---+
                                                                                |
Mock 音频源 ----> 有界队列 ----------------> Checksum 音频编码 ---+
                                                                                |
                                                                      PacketRouter
                                                                                |
                                                                      Null/JSONL Sink

所有模块 ----------------> 日志、指标、健康检查、可控停止
```

它还不是真实摄像头系统，但已经验证了最容易在项目后期出问题的部分：线程生命周期、时间戳、队列背压、内存上限、错误传递和运行可观测性。

完整硬件下的最终目标与模块边界仍以 [01-项目总体代码架构.md](01-项目总体代码架构.md) 为准。

## 2. 音视频小白必须先理解的概念

### 2.1 视频帧不是“一张普通图片”

视频是按时间连续产生的图像帧序列。30 FPS 表示理论上每秒生成 30 帧，两帧间隔约为 33.333 ms。每帧除图像字节外，还必须携带：

- `sequence`：帧序号，用于发现丢帧和绑定检测结果。
- `pts_us`：展示时间戳，单位微秒，用于播放节奏和音画同步。
- `width/height`：图像宽高。
- `stride`：内存中一行实际占用的字节数，它可能大于“宽度 × 每像素字节数”。
- `format`：RGB、BGR、NV12、YUYV 或 MJPEG 等像素/压缩格式。

当下游处理不过来时，实时视频通常应当丢掉旧帧，而不是让延迟一直累积。用户宁可看到偶尔跳帧的新画面，也不希望看到几秒以前的“流畅旧画面”。

### 2.2 音频块是连续样本

48 kHz 采样率表示每个声道每秒采集 48,000 个样本。`S16_LE` 表示每个样本是 16 位有符号小端整数。单声道、20 ms 的一块音频包含：

```text
48,000 samples/s × 0.020 s = 960 samples
960 samples × 2 bytes = 1,920 bytes
```

音频和视频的丢弃策略不同。丢一帧视频通常只会让画面短暂跳动；随意丢音频样本会产生爆音、断裂和时间轴错位。因此音频队列满时要告警并定位根因，不能静默丢弃。

### 2.3 PTS 是整条链路的时间坐标

PTS 可以理解为“这份数据应该在什么时刻被展示或播放”。本项目内部统一使用单调时钟的微秒值，不使用“当前日期和时间”。

原因是系统时钟可能被 NTP 校时向前或向后调整，单调时钟只会向前走。在封装 MP4/RTSP 时，再将微秒换算为编码器和封装器需要的 `time_base`。

### 2.4 队列和背压

多线程管道中，上游生产数据，下游消费数据。当下游速度低于上游时，数据会积压。

“有界队列”是容量有上限的队列。队列满时必须做出明确决策：等待、丢最新数据、丢最旧数据，或只保留最新数据。这个决策就是背压策略。

如果使用无界队列，系统可能在负载过高时持续吃内存，最后被 Linux OOM Killer 杀死。

### 2.5 Mock 不是“随便返回假数据”

企业级 Mock 必须可重复、可配置、可注入错误，并遵守真实后端的接口契约。同一配置和 seed 必须生成同一结果，这样测试失败才能复现。

## 3. 统一技术选型

为了避免开发过程中不断改标准，本手册固定如下基线：

| 项目 | 选择 | 原因 |
|---|---|---|
| 语言 | C++20 | 使用 `std::jthread` 和 `std::stop_token` 管理线程停止 |
| 构建 | CMake 3.20+ + Ninja | 易于 PC、aarch64 和 CI 复用 |
| 测试 | GoogleTest + CTest | 单元测试与 CMake 集成成熟 |
| 配置 | nlohmann/json | 便于定义和校验 JSON 配置 |
| 日志 | 项目内部轻量结构化日志封装 | 先避免额外库泄漏到核心层 |
| 格式化 | clang-format | 统一排版 |
| 静态检查 | clang-tidy | 发现所有权、类型和并发隐患 |
| 内存检查 | ASan + UBSan，可选 TSan/Valgrind | 在 PC 上尽早发现问题 |
| 版本管理 | Git | 每个里程碑可回溯 |

依赖版本必须在 CMake 或依赖锁定文件中固定。不要每次构建都自动拉取某个仓库的 `main` 分支。企业内网环境可将依赖放入已审核的内部镜像或使用系统包，但 target 名称和代码调用保持一致。

## 6. M0：建立可编译的空工程

### 6.1 顶层 CMake 职责

顶层 `CMakeLists.txt` 只做以下事情：

1. 定义项目和版本。
2. 固定 C++20，禁止编译器私有扩展。
3. 加载 `cmake/Options.cmake`。
4. 查找锁定依赖。
5. 定义子目录或 targets。
6. 在 `RKAV_BUILD_TESTS=ON` 时启用 CTest。

示意骨架：

```cmake
cmake_minimum_required(VERSION 3.20)
project(rkav_gateway VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

include(cmake/Options.cmake)

find_package(nlohmann_json REQUIRED)

add_library(rkav_core)
target_include_directories(rkav_core PUBLIC include)
target_link_libraries(rkav_core PUBLIC nlohmann_json::nlohmann_json)

add_library(rkav_mock)
target_include_directories(rkav_mock PUBLIC include)
target_link_libraries(rkav_mock PUBLIC rkav_core)

add_library(rkav_app)
target_include_directories(rkav_app PUBLIC include)
target_link_libraries(rkav_app PUBLIC rkav_core rkav_mock)

add_executable(rkav-gateway app/main.cpp)
target_link_libraries(rkav-gateway PRIVATE rkav_app)

if(RKAV_BUILD_TESTS)
  enable_testing()
  find_package(GTest REQUIRED)
  add_subdirectory(tests)
endif()
```

这只是目标边界示意，后续每增加一个 `.cpp` 都要显式添加到正确 target。不建议对源文件使用递归 glob，因为新文件可能不会立即触发 CMake 重新配置，且代码审查难以看出 target 变化。

### 6.2 编译选项接口库

创建 `rkav_project_options` 和 `rkav_project_warnings` 两个 `INTERFACE` target，统一管理 sanitizer、优化和告警。业务 target 链接这两个 target，不要在每个目标上复制一遍选项。

```cmake
option(RKAV_BUILD_TESTS "Build tests" ON)
option(RKAV_ENABLE_MOCK "Build mock backends" ON)
option(RKAV_ENABLE_ASAN "Enable AddressSanitizer" OFF)
option(RKAV_ENABLE_UBSAN "Enable UndefinedBehaviorSanitizer" OFF)
option(RKAV_WITH_V4L2 "Build V4L2 backend" OFF)
option(RKAV_WITH_ALSA "Build ALSA backend" OFF)
option(RKAV_WITH_RKNN "Build RKNN backend" OFF)
option(RKAV_WITH_RGA "Build RGA backend" OFF)
option(RKAV_WITH_MPP "Build MPP backend" OFF)
```

### 6.3 CMake Presets

`CMakePresets.json` 用来避免每个人手写一组不同的构建参数。至少定义：

```text
linux-debug          Debug + tests + mock
linux-asan           Debug + tests + ASan + UBSan
linux-release        Release + mock
rk3568-debug         aarch64 原生/交叉编译预留
```

常用命令：

```bash
cmake --preset linux-debug
cmake --build --preset linux-debug
ctest --preset linux-debug
```

### 6.4 第一个主程序

`app/main.cpp` 的第一版只处理：

- `--help`。
- `--version`。
- `--config <path>`。
- 配置验证失败时输出明确错误并返回非 0。
- 调用 `Application::Run()`，将业务逻辑留在 `rkav_app`。

`main.cpp` 不应包含 worker 循环、设备逻辑或 JSON 字段细节。它是进程入口，不是“一切功能的大杂烩”。

### 6.5 M0 调试步骤

1. 运行 `cmake --preset linux-debug`。
2. 如果 `find_package` 失败，先确认依赖安装和 `CMAKE_PREFIX_PATH`，不要改业务代码。
3. 运行 `cmake --build --preset linux-debug -v`，检查真实编译命令。
4. 运行 `./build/linux-debug/rkav-gateway --version`。
5. 运行 `ctest --preset linux-debug --output-on-failure`。

提交前检查：

```bash
git diff --check
git status --short
```

建议提交信息：

```text

```

## 7. M1：先写公共契约，再写业务管道

### 7.1 开发顺序

严格按以下顺序，每完成一项就编译和测试：

1. `error.h` 与 `result.h`。
2. `clock.h` 与时间转换。
3. `buffer.h`。
4. `types.h`中的帧、检测结果和编码包。
5. `bounded_queue.h`。
6. 各后端抽象接口。

原因是后面的 Mock、worker、日志和测试都依赖这些契约。如果边写管道边反复修改帧结构，会造成大量返工。

### 7.2 Error 与 Result

`Error` 保留通用分类和底层原始码。建议提供带上下文的辅助函数：

```cpp
Error WithContext(Error error,
                  std::string_view module,
                  std::string_view operation);
```

一个底层错误从采集层向上传递时，不应丢失 errno 和原始描述；同时上层应能根据 `category` 判断是否重试。

不要用以下方式：

```cpp
if (!ok) {
    return false;  // 错在哪里、是否能重试已经全部丢失
}
```

单元测试文件建议：

```text
tests/unit/result_test.cpp
tests/unit/error_test.cpp
```

### 7.3 Buffer 与内存所有权

第一版 `Buffer` 使用连续 CPU 内存。要明确区分：

- 数据大小 `size`：当前有效字节数。
- 容量 `capacity`：已分配的最大字节数。
- 可变和只读访问。
- 共享所有权：多个下游只读共享。

帧在进入多路分发后应视为不可变。如果 overlay 要修改图像，它应获得独占 buffer 或创建新帧，不得悄悄修改其他 sink 正在读的同一块内存。

### 7.4 Frame 数据校验

提供构造函数或 `Validate()`，至少检查：

```text
width > 0
height > 0
stride > 0
buffer != nullptr
buffer.size() 满足当前格式的最小需求
format != Unknown
pts_us >= 0（如果项目规定起点为 0）
```

像素格式与最小数据大小不能只用 `width * height * channels` 统一计算。RGB24 可以使用 `stride * height`，NV12 和压缩 MJPEG 需要不同逻辑。当前 Mock 只生成 RGB888，但 API 不应阻止后续格式扩展。

### 7.5 时钟与 FramePacer

`IClock` 用于获取时间，`FramePacer` 用于计算下一个截止时间。两者分开是为了让单元测试使用 `ManualClock`。

伪代码：

```cpp
while (!stop_token.stop_requested()) {
    const auto sequence = next_sequence_++;
    const auto deadline = pacer.DeadlineFor(sequence);
    WaitUntil(deadline, stop_token);
    if (stop_token.stop_requested()) {
        break;
    }
    EmitFrame(sequence, deadline);
}
```

`WaitUntil` 必须可被停止请求唤醒，不得使用一个无法中断的长 `sleep_for`。

### 7.6 BoundedQueue 的实现顺序

第一步，先只实现 `BlockProducer` 和 `Close`，写完测试。

第二步，增加 `DropNewest`、`DropOldest`、`KeepLatest`。

第三步，增加 metrics：

```cpp
struct QueueSnapshot {
    std::size_t size{};
    std::size_t capacity{};
    std::size_t high_watermark{};
    std::uint64_t pushed{};
    std::uint64_t popped{};
    std::uint64_t dropped{};
    std::uint64_t push_timeouts{};
    std::uint64_t pop_timeouts{};
    bool closed{};
};
```

第四步，用多线程压力测试验证总数。测试不能只检查“没有崩溃”，要根据每个生产者写入的唯一 ID 检查数据是否重复或丢失。

关键实现原则：

- 使用条件变量时总是带 predicate 等待，抵御伪唤醒。
- 修改队列、关闭标志和高水位时持有同一互斥锁。
- 移动大对象，不做无意义拷贝。
- 离开临界区后再执行耗时业务，不要带着队列锁做推理、编码或日志 I/O。

### 7.7 接口编码

每个接口文件只描述“输入、输出和生命周期”，不包含 Mock 细节。例如：

```cpp
class IVideoCapture {
public:
    virtual ~IVideoCapture() = default;
    virtual Result<VideoCapabilities> Open(
        const VideoCaptureConfig& config) = 0;
    virtual Result<VideoFrame> Read(std::stop_token stop) = 0;
    virtual void Close() noexcept = 0;
};
```

这里的 `Read` 契约需要在注释中说清：

- 正常返回一帧。
- 停止请求后在有界时间内返回 `Cancelled`。
- 超时不等于设备永久失效。
- 设备断开应映射为 `DeviceDisconnected`。
- `Close()` 幂等且不抛异常。

### 7.8 M1 的测试与调试

每写完一个类：

```bash
cmake --build --preset linux-debug
ctest --preset linux-debug --output-on-failure
cmake --build --preset linux-asan
ctest --preset linux-asan --output-on-failure
```

队列测试卡死时：

1. 为该测试增加 CTest timeout，先防止 CI 无限挂起。
2. 用 GDB 运行测试：`gdb --args ./build/linux-debug/tests/rkav_unit_tests --gtest_filter=BoundedQueueTest.*`。
3. 卡住后按 Ctrl+C，执行 `thread apply all bt`。
4. 查看哪个线程等待在 `condition_variable`，关闭路径是否执行 `notify_all()`。
5. 不要通过添加随机 `sleep_for` “修复”竞态条件。

建议提交拆分：

```text
core: add typed error and result handling
core: add owned buffers and media frame types
core: add monotonic clock and timestamp conversion
queue: add bounded queue with close semantics
queue: add overflow policies and metrics
api: define capture inference encoder and sink contracts
```

## 8. M2：实现可验证的 Mock 音视频源

### 8.1 先写测试图数学，后写线程

MockVideoCapture 分为两层：

```text
TestPatternGenerator     纯函数/无线程，根据 sequence 生成图像
MockVideoCapture         负责节拍、PTS、停止和错误注入
```

先实现 `TestPatternGenerator::Generate(sequence, destination)`，对固定帧号计算 checksum。这一层不读系统时间，因此测试完全确定。

建议图案：

1. 背景使用 8 个垂直色条，可看出 RGB/BGR 是否颠倒。
2. 一个固定大小矩形水平移动：`x = sequence % (width - box_width)`。
3. 矩形的类别和位置公式与 MockInferenceEngine 共享一个 `SyntheticScene` 定义，但图像生成器与推理器不相互调用。

### 8.2 视频字节布局

RGB888 每像素 3 字节。第一版 Mock 可以使用：

```text
stride = width * 3
buffer_size = stride * height
pixel_offset = y * stride + x * 3
R = buffer[pixel_offset + 0]
G = buffer[pixel_offset + 1]
B = buffer[pixel_offset + 2]
```

不要在其他模块重复这个偏移计算，将它放进小型图像访问辅助函数，并检查 x/y 边界。

### 8.3 MockVideoCapture 状态

```text
CLOSED -> OPENING -> OPEN -> READING
   ^                    |
   +-------- CLOSING <--+

注入错误时：READING -> ERROR
Close 后：ERROR -> CLOSED
```

`Open()` 返回实际能力，Mock 中就是经校验的宽高、FPS 和 RGB888。重复 `Open()` 是报错还是幂等，必须选择并写入接口契约；建议已打开时返回 `InvalidState`，避免隐藏生命周期错误。

### 8.4 MockAudioCapture 的正弦波

对采样索引 `n`：

```text
sample[n] = amplitude * INT16_MAX * sin(2 * pi * frequency * n / sample_rate)
```

不要用“每块内的索引”作为 n，应使用从开始运行累计的全局样本索引，否则每 20 ms 都会重置相位，产生不连续波形。

防止浮点转整数溢出，先 clamp 到 `[-1.0, 1.0]`，再转为 `int16_t`。

### 8.5 为 Mock 添加错误注入

错误注入必须通过配置开启，生产默认为关闭。示例：

```text
fail_after_frames = 300
fail_for_frames = 60
read_delay_ms = 100
xrun_every_blocks = 500
disconnect_after_blocks = 3000
```

错误发生时日志要包含帧/块序号和注入规则，便于区分真实 bug 与预期故障。

### 8.6 M2 的测试顺序

1. 使用小图像 16×12 测试色条和移动矩形，避免测试数据过大。
2. 检查 sequence 0、1、width-box_width 附近的边界。
3. 检查固定 sequence 的 checksum。
4. 用 ManualClock 生成 30 FPS 的 300 帧，不真实等待 10 秒。
5. 使用实时时钟运行 10 秒，验证帧数和停止响应。
6. 检查音频每块 960 samples、相位连续和幅度上限。
7. 验证每种错误注入在精确序号发生。

建议提交：

```text

mock: add paced video capture with failure injection
mock: add continuous PCM sine-wave capture
test: cover mock timing and deterministic failures
```

## 9. M3：Mock 推理与图像几何

### 9.1 分离预处理几何和像素操作

现在就实现 `ComputeLetterboxTransform()` 和坐标还原，因为这些是纯数学，不需要 RGA。

```cpp
struct TransformMetadata {
    int source_width{};
    int source_height{};
    int destination_width{};
    int destination_height{};
    int resized_width{};
    int resized_height{};
    int pad_left{};
    int pad_top{};
    float scale_x{};
    float scale_y{};
};
```

保存 `scale_x` 和 `scale_y`，而不是只保存一个理论 scale，因为 resize 尺寸取整后两个方向的实际比例可能有微小差异。

### 9.2 MockInferenceEngine 契约

Mock 推理的输入是通用 `VideoFrame`，输出是 `DetectionBatch`。它不需要真正分析像素，而是根据 `SyntheticScene` 中的公式返回目标框。

这样可以精确验证：

- 推理结果是否携带正确帧号。
- 慢推理时是否使用最新帧。
- 结果是否过期。
- 坐标是否可还原到原图。

配置 `latency_ms` 时要使用可取消等待。如果设为 5000 ms，进程收到 SIGTERM 后不应被迫再等待 5 秒。

### 9.3 结果缓存

Overlay/编码支路可以从一个线程安全的 `LatestDetectionStore` 读取最新结果。存储替换必须是原子的或在小临界区内完成，不得向外返回一个可在锁外被修改的引用。

推荐 API：

```cpp
void Publish(std::shared_ptr<const DetectionBatch> result);
std::shared_ptr<const DetectionBatch> Latest() const;
```

### 9.4 M3 图像几何测试

至少覆盖：

| 原图 | 模型输入 | 需检查 |
|---|---|---|
| 1280×720 | 320×320 | 上下 padding、横向无 padding |
| 640×480 | 320×320 | 上下 padding |
| 720×1280 | 320×320 | 左右 padding |
| 320×320 | 320×320 | scale 1、无 padding |
| 1×1 | 320×320 | 极小边界 |

坐标往返转换允许有明确的浮点误差，不要使用精确 `==` 比较浮点数。

## 10. M3：Checksum Encoder、PacketRouter 和 Sink

### 10.1 Checksum Encoder 的目的

当前没有真实编码库时，Checksum Encoder 负责把帧元数据和内容 hash 转为 `EncodedPacket`形式的测试包。

测试 packet 应有明确 codec 标识，例如 `Codec::kMockVideoChecksum`，绝对不标记为 H.264。这能防止日后某个测试文件被错当成真实码流。

### 10.2 视频 Checksum Encoder

- 保留输入 `sequence` 和 PTS。
- 模拟 GOP，例如每 30 帧标记一个 key frame。
- 计算稳定的 checksum；算法一旦选定，在测试中固定。
- `Flush()` 第一次返回剩余包（如果有），重复调用应幂等。

### 10.3 音频 Checksum Encoder

- 保留音频块的起始 PTS。
- 记录 sample rate、channels 和 samples per channel。
- 检查连续块间的理论 PTS 差。
- 发现缺块或倒退时输出可诊断错误。

### 10.4 PacketRouter 的正确性优先级

第一版先使用清晰、可验证的设计：

1. 路由线程从一个编码包队列取包。
2. 对每个 sink 提交 `shared_ptr<const EncodedPacket>`。
3. sink 可以有独立队列，且容量与溢出策略可配置。
4. 慢 sink 的丢包和错误只记到该 sink。
5. 如果配置将某 sink 设为 required，它连续失败达阈值后才升级为 Application 错误。

### 10.5 Null Sink 不应真的“什么都不做”

Null Sink 应在运行时检查：

- packet buffer 不为空。
- codec 与 stream kind 匹配。
- time base 分母非 0。
- 同一 stream 的 DTS 不倒退。
- 输入、接收、丢弃和失败计数可对账。

开启严格校验后，发现时间戳问题应返回错误，而不是只写一条容易被忽略的 warning。

## 11. M3：组装多线程 Application

### 11.1 先建立一条视频管道

不要一次就把音频、视频、推理、路由、日志和恢复全部连起来。按以下顺序逐步扩展：

```text
步骤 1：MockVideoCapture -> Queue -> ConsumerCounter
步骤 2：MockVideoCapture -> Queue -> MockInference -> LatestDetectionStore
步骤 3：MockVideoCapture -> Queue -> ChecksumVideoEncoder -> PacketQueue
步骤 4：PacketQueue -> PacketRouter -> NullSink
步骤 5：加入 MockAudioCapture -> ChecksumAudioEncoder -> PacketQueue
步骤 6：加入健康监测与故障注入
```

每完成一步就建立独立集成测试。当新步骤失败时，前一步仍能运行，这样可以迅速缩小问题范围。

### 11.2 Worker 的标准形态

每个 worker 建议都有类似结构：

```cpp
class VideoCaptureWorker {
public:
    Result<void> Start();
    void RequestStop() noexcept;
    void Join() noexcept;
    WorkerSnapshot Snapshot() const;

private:
    void Run(std::stop_token stop);

    std::unique_ptr<IVideoCapture> capture_;
    BoundedQueue<VideoFrame>& output_;
    std::jthread thread_;
};
```

规则：

- 类拥有自己的线程，不 detached。
- `Start()` 在重复调用时明确失败。
- `RequestStop()` 不阻塞，只发请求并唤醒相关等待。
- `Join()` 等待退出，不在 worker 自身线程中调用。
- `Run()` 顶层捕获所有异常，转为错误和停止请求，不让异常穿过线程入口导致 `std::terminate`。

### 11.3 Application 启动顺序

```text
1. ParseArgs
2. LoadConfig
3. ValidateConfig
4. InitializeLogger
5. CreateMetricsRegistry
6. CreateBackends
7. OpenBackends
8. CreateQueues
9. CreateWorkers
10. Start sinks/router
11. Start encoders/inference
12. Start audio/video capture
13. Start health monitor
14. Enter RUNNING
```

为什么从下游开始启动？因为如果先启动采集，但消费者还没准备好，队列可能在启动期间就溢出。

### 11.4 Application 停止顺序

```text
1. 原子地将状态设为 STOPPING，防止重复执行
2. 请求 capture 停止，不再生产新数据
3. 关闭 capture 输出队列
4. 唤醒 inference/encoder 等待
5. join capture workers
6. drain 或 abort 各处理队列，按退出类型决定
7. flush encoders
8. 关闭 packet queue
9. drain router/sinks
10. join 剩余 workers
11. 输出最终 metrics 和 stop reason
12. 设为 STOPPED
```

正常 SIGTERM 退出应尽量 drain；发生内存破坏或已超出停止超时时，应选择 abort 而不是无限等待。当前 Mock 阶段要将两条路径都测试清楚。

### 11.5 信号处理

信号处理函数内不能打印复杂日志、加锁或释放大量资源。它只设置一个安全的停止标记/通知机制，实际停止由 Application 主控流程执行。

如果使用 Linux `signalfd`，可将信号转换为普通 fd 事件；第一版也可使用最小 `sig_atomic_t` 标记。无论选哪种方案，都要写 SIGINT 和 SIGTERM 集成测试。

## 12. M4：配置系统

### 12.1 配置不是“读 JSON 就结束”

企业级配置需经过：

```text
JSON 语法解析
    -> 字段类型校验
    -> 默认值
    -> 范围校验
    -> 跨字段语义校验
    -> 编译特性校验
    -> 不可变 Config 对象
```

例如，JSON 中 `fps: 30` 语法正确，但还要检查：

- FPS 是否在允许范围内。
- 是否与 `realtime` 和节拍配置矛盾。
- 当前 backend 是否支持该值。
- `queue_capacity` 是否为正数。

### 12.2 配置错误要可定位

错误输出应指向字段路径：

```text
config.video.fps: expected integer in range [1, 120], got 0
config.inference.backend: backend 'rknn' is not compiled in
config.audio.frame_duration_ms: 17 ms does not produce an integer sample count at 48000 Hz
```

不要只输出 `invalid config`。

### 12.3 对未知字段的策略

建议：

- 生产配置默认对未知字段报错，发现拼写错误。
- 配置迁移工具可以显式允许或转换旧字段。
- 日志中输出 `schema_version` 和配置文件 hash，长稳报告才能知道使用了哪份配置。

### 12.4 配置加载的完成定义

- `--validate-config` 只校验而不启动 worker。
- 开启未编译的 RKNN/MPP 后端会在启动前失败。
- 应用启动后不再到处读 JSON 节点，worker 只获取强类型配置。
- 单元测试覆盖缺少文件、无权限、JSON 损坏、类型错误和语义错误。

## 13. M4：日志、指标和健康状态

### 13.1 日志级别约定

| 级别 | 使用场景 |
|---|---|
| TRACE | 采样的帧/包级细节，默认关闭 |
| DEBUG | 模块状态、队列变化、协商细节 |
| INFO | 启动、停止、实际配置、状态转移、定期摘要 |
| WARN | 可恢复错误、丢帧超阈值、队列长期高水位 |
| ERROR | 模块功能失败或降级 |
| FATAL | 进程无法继续，即将退出 |

同一错误如果高频发生，要限速或聚合：第一次立即记录，之后每隔一定时间输出“期间又发生 N 次”。否则设备断开时可能每秒写数千条日志。

### 13.2 指标实现

计数器使用原子整数，延迟分布使用有界结构。快照线程每秒读取一次，输出 JSON 或人类可读摘要。

一条帧的延迟至少区分：

```text
capture_to_inference_start
inference_duration
capture_to_encode_start
encode_duration
capture_to_sink
```

不要只统计一个“总延迟”，否则变慢时无法判断是队列等待、推理还是 sink 导致。

### 13.3 进程内存

Linux 上可以从 `/proc/self/status` 读取 `VmRSS`，但要把这个实现放在 `platform/linux`。核心 metrics 只依赖一个 `IProcessMetricsProvider`接口。

长稳时不应因为标准库 allocator 缓存了内存就立即判定泄漏。正确方法是：

1. 允许启动预热。
2. 观察预热后 RSS 是否持续近似线性增长。
3. 对比队列深度和 buffer 计数。
4. 用 ASan/Valgrind 验证真实未释放分配。

### 13.4 健康监测与恢复命令

健康监测不直接操作 worker 内部对象。它产生命令：

```text
RestartVideoCapture
RecoverAudioCapture
DisableRecording
ReconnectStreamer
EnterDegradedMode
StopApplication
```

Application 串行执行命令并记录状态转移。这能避免健康线程、采集线程和主线程同时关闭同一个设备。

## 14. M4：完整 Mock 集成测试

### 14.1 测试必须可确定重现

不要让测试依赖“大概等 100 ms”。优先使用 ManualClock、latch/barrier 或显式事件。只有验证真实调度和停止响应时才使用真时钟，并给出充足但有界的 timeout。

### 14.2 正常管道测试

运行 10 秒：

```text
video = 1280x720 RGB888, 30 FPS
audio = 48000 Hz, mono, S16_LE, 20 ms blocks
inference latency = 20 ms
video queue = 4, drop_oldest
inference queue = 1, keep_latest
sink = null, strict timestamps
```

验证：

- 视频采集约 300 帧，考虑启停边界容差。
- 音频约 500 块。
- 没有时间戳倒退。
- 所有 worker 在规定超时内停止。
- 最终 metrics 能说明每个阶段收到和输出多少数据。

### 14.3 慢推理测试

将 inference latency 设为 100 ms，理论上最多约 10 FPS。视频采集仍为 30 FPS。

预期：

- `capture_video_fps` 仍接近 30。
- `inference_fps` 接近 10。
- inference queue 不超过 1。
- `dropped_frames_total{queue=inference}` 增长。
- 结果来自较新帧，而不是按顺序慢慢处理旧帧。
- RSS 不随运行时间线性增长。

### 14.4 故障注入测试

每种故障单独写测试，不要一个用例注入所有错误：

- 视频读取连续超时。
- 视频设备断开，指定次数后恢复。
- 音频 XRUN，Recover 成功。
- 音频 Recover 失败，进入降级。
- inference 返回可恢复错误。
- sink 暂时失败与永久失败。
- 队列在 producer/consumer 阻塞时关闭。

每个用例都检查状态序列、错误数、恢复数、退出码和线程退出时间。

### 14.5 信号集成测试

用子进程启动 `rkav-gateway`，等待日志出现 `application_running`，发送 SIGTERM，然后验证：

- 进程在 `shutdown_timeout_ms` 内退出。
- 退出码为 0。
- 日志包含 `stop_reason=signal` 和最终指标。
- 没有 worker 被丢弃或调用 `std::terminate`。

再写一个致命内部错误用例，验证进程返回非 0，为 systemd `Restart=on-failure` 提供正确语义。

## 16. 调试全流程

### 16.1 先分类，再下手

问题先分为：

| 类型 | 常见现象 | 第一工具 |
|---|---|---|
| 编译/链接 | 找不到头文件、undefined reference | CMake verbose build、`ldd`、`nm` |
| 配置 | 启动立即失败 | `--validate-config`、结构化错误 |
| 崩溃 | segfault、abort | ASan、GDB、core dump |
| 内存 | RSS 增长、OOM | ASan/LSan、Valgrind、队列指标 |
| 死锁/卡死 | 进程在但无输出 | health snapshot、GDB all-thread backtrace |
| 数据错 | 帧号跳变、PTS 倒退 | NullSink 严格验证、JSONL |
| 性能 | FPS 低、延迟高 | 阶段 metrics、`perf`、队列水位 |

不要在未分类时同时改线程数、队列长度、日志级别和编译优化。一次只改一个变量，才能判断哪个改动有效。

### 16.2 编译错误

查看完整编译命令：

```bash
cmake --build --preset linux-debug --verbose
```

链接错误 `undefined reference` 通常表示：

- `.cpp` 没有被加到 target。
- target 没有链接所需库。
- 函数声明和定义的 namespace/参数/`const` 不一致。
- 静态库链接顺序或传递依赖有问题。

不要用“把所有库都加到顶层可执行程序”遮盖 target 边界问题。

### 16.3 GDB 调试崩溃

先使用 Debug 构建：

```bash
gdb --args ./build/linux-debug/rkav-gateway --config config/mock.json
```

GDB 内常用命令：

```text
run
bt
frame 3
info locals
info args
thread apply all bt
break rkav::Application::Stop
continue
```

如果进程崩溃后有 core dump：

```bash
ulimit -c unlimited
./build/linux-debug/rkav-gateway --config config/mock.json
gdb ./build/linux-debug/rkav-gateway core
```

systemd 系统可用 `coredumpctl list` 和 `coredumpctl gdb <pid-or-exe>`。

### 16.4 ASan/UBSan

```bash
cmake --preset linux-asan
cmake --build --preset linux-asan
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 \
UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 \
ctest --preset linux-asan --output-on-failure
```

它们可发现：

- 越界读写。
- use-after-free。
- 重复释放。
- 部分内存泄漏。
- 有符号整数溢出等未定义行为。

一旦 sanitizer 报错，先修复第一个报错位置。后面的错误可能是第一处内存破坏引发的连锁现象。

### 16.5 死锁与无进展

现象是进程还在，CPU 可能很低，但 FPS 和计数器不再增长。

排查顺序：

1. 查看 health monitor 的最近进展时间，找出第一个停止前进的 worker。
2. 查看该 worker 输入和输出队列的 depth。
3. `gdb -p <pid>` 附加进程。
4. 执行 `thread apply all bt`。
5. 检查是否有 worker 带着队列锁调用下游。
6. 检查 Close/Stop 是否在所有状态下执行 `notify_all()`。
7. 检查锁顺序是否不一致，如 A->B 和 B->A。

修复后要把该时序转换为自动化测试，否则后续很容易回归。

### 16.6 FPS 低和延迟高

先读指标：

```text
采集 FPS 低             -> 源/节拍/设备层
采集 30, 推理 10     -> 推理能力或配置上限，可能正常
队列深度长期达上限 -> 下游持续跟不上
队列不深但延迟高     -> 某个单阶段耗时高或时间戳计算错
CPU 高但各阶段延迟低  -> 可能是 Mock 图像生成/日志开销
```

在 Linux 上使用：

```bash
top -H -p <pid>
pidstat -p <pid> -t 1
perf stat -p <pid> sleep 10
perf record -g -p <pid> -- sleep 30
perf report
```

优化前先保存基线配置和指标，优化后使用同一配置对比。

## 17. 代码质量门禁

### 17.1 本地提交前

```bash
cmake --build --preset linux-debug
ctest --preset linux-debug --output-on-failure
cmake --build --preset linux-asan
ctest --preset linux-asan --output-on-failure
git diff --check
```

另外执行：

- clang-format 检查，确保没有未格式化文件。
- clang-tidy 检查新增/修改的 `.cpp`。
- 审查 `git diff`，确认没有调试输出、绝对路径、临时密钥和大型生成文件。

### 17.2 CI 流程

企业 CI 至少有以下 job：

```text
format-check
linux-gcc-debug-test
linux-clang-debug-test
linux-asan-ubsan
clang-tidy
linux-release-build
```

硬件到位后再增加自托管 RK3568 runner 的板端 smoke/soak test。普通 PR 不必每次运行 2 小时长稳，可以每夜运行；但 10–60 秒 Mock 集成测试应在每个 PR 运行。

### 17.3 代码审查清单

- 新类的所有权是否清晰。
- 新线程是否有停止和 join 路径。
- 新队列是否有容量与 overflow policy。
- 新错误是否保留底层码和上下文。
- 新配置是否有默认值、校验、示例和测试。
- 主链路是否在持锁状态做耗时操作。
- 日志是否会在每帧/每样本高频写入。
- 是否使用了 wall clock 作为媒体 PTS。
- Mock 输出是否可重复。
- 是否增加了成功路径之外的失败测试。

## 18. M5：在 RK3568 板上编译和运行

### 18.1 前提

板卡必须已启动 64 位 Linux，且你已经能通过本地终端、SSH 或串口登录。只有 USB 线不一定表示电脑能与板卡通信；这取决于板卡 OTG 端口、系统配置和 USB gadget 功能。未查清具体板卡手册前，不默认 USB 线等于调试线。

### 18.2 板卡基线

创建 `docs/environment/board-baseline.md`，记录：

```bash
uname -a
uname -m
cat /etc/os-release
free -h
lsblk
df -h
cat /sys/class/thermal/thermal_zone0/temp 2>/dev/null || true
g++ --version
cmake --version
ninja --version
```

温度文件通常是毫摄氏度，例如 `52000` 可能表示 52°C；具体以当前 BSP 的 thermal zone 定义为准。

### 18.3 原生编译

开发板性能足够时，初期优先原生编译，减少交叉工具链和 sysroot 问题：

```bash
cmake --preset linux-debug
cmake --build --preset linux-debug -j2
ctest --preset linux-debug --output-on-failure
```

`-j2` 是保守示例，根据内存和温度调整。4 GB 板上并行编译过高可能产生内存压力。

### 18.4 交叉编译

只在原生编译过慢或板上不安装工具链时使用。需要：

- aarch64 交叉编译器。
- 与板卡系统匹配的 sysroot。
- CMake toolchain file。
- 依赖库的 aarch64 版本，不能误链接 x86_64 库。

构建后检查：

```bash
file build/rk3568-debug/rkav-gateway
readelf -h build/rk3568-debug/rkav-gateway | grep Machine
```

预期为 AArch64/ARM aarch64，而不是 x86-64。

### 18.5 板上 Mock 运行

```bash
./build/linux-debug/rkav-gateway --validate-config --config config/mock.json
./build/linux-debug/rkav-gateway --config config/mock.json
```

另开一个终端观察：

```bash
pidof rkav-gateway
top -H -p "$(pidof rkav-gateway)"
cat /proc/"$(pidof rkav-gateway)"/status | grep -E 'VmRSS|Threads'
cat /sys/class/thermal/thermal_zone0/temp 2>/dev/null
```

发送停止：

```bash
kill -TERM "$(pidof rkav-gateway)"
```

检查最终日志是否有 stop reason、总帧数、总丢帧和各队列高水位。

## 19. systemd 集成

### 19.1 运行用户与目录

生产服务不应长期以 root 运行。建议：

```text
程序：/opt/rkav/bin/rkav-gateway
配置：/etc/rkav/config.json
模型：/opt/rkav/models/
可变数据：/var/lib/rkav/
日志：journald，必要时 /var/log/rkav/
运行用户：rkav
```

当前 Mock 阶段不需要 video/audio 设备权限。后续接硬件后，把 `rkav` 用户加入必要的 `video`/`audio` 组，不要直接改为 root 回避权限问题。

### 19.2 service 文件

```ini
[Unit]
Description=RK3568 Audio Video Edge Gateway
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=rkav
Group=rkav
ExecStart=/opt/rkav/bin/rkav-gateway --config /etc/rkav/config.json
Restart=on-failure
RestartSec=3
TimeoutStopSec=10
KillSignal=SIGTERM
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/rkav

[Install]
WantedBy=multi-user.target
```

第一次启用强化选项时，逐项验证不要一次堆叠大量限制。后续访问 `/dev/video*`、`/dev/snd/*`、模型和录像目录时，需依据最小权限原则调整 device 和 path 权限。

### 19.3 调试 systemd

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now rkav-gateway
systemctl status rkav-gateway --no-pager
journalctl -u rkav-gateway -f
```

验证正常停止：

```bash
sudo systemctl stop rkav-gateway
```

验证失败重启：使用专用测试配置注入致命错误，不要通过随意杀掉系统关键进程或损坏文件系统来测试。

## 20. 长时间稳定性测试

### 20.1 测试前固定条件

记录：

- Git commit ID。
- Debug/Release 构建类型。
- 编译器和依赖版本。
- 配置文件和 hash。
- 板卡镜像和内核版本。
- 环境温度和散热条件。

如果这些不固定，两次测试的性能和温度无法比较。

### 20.2 收集项目

每秒或每 5 秒记录：

```text
timestamp
VmRSS
thread_count
video/audio/inference/encode FPS
all queue depths and high-watermarks
dropped frames
error and recovery counts
P50/P95/P99 stage latency
board temperature
process CPU usage
```

保存为 CSV 或 JSON Lines，不只保存一张截图。

### 20.3 执行顺序

1. 5 分钟 smoke test：确认配置和指标收集正常。
2. 30 分钟 soak test：检查内存、队列和温度趋势。
3. 2 小时 soak test：作为当前阶段正式验收。
4. 可选 12 小时 nightly test：建立后续硬件比较基线。

每次测试结束必须通过 SIGTERM 正常停止，并检查停止耗时。

### 20.4 报告结构

`docs/test-reports/YYYY-MM-DD-board-mock-soak.md` 建议包含：

```text
1. 测试目标
2. 硬件和软件环境
3. commit/config hash
4. 运行命令
5. 开始/结束时间
6. 指标摘要
7. 内存和温度趋势
8. 错误与恢复事件
9. 停止耗时和退出码
10. 结论与未解决风险
```

## 21. 硬件到货后如何继续，不推倒现有代码

### 21.1 一次只替换一个后端

正确顺序：

```text
1. V4L2VideoCapture + 其他 Mock
2. AlsaAudioCapture + Mock/Checksum 下游
3. FFmpeg 软件编码/封装基线
4. RknnInferenceEngine + CPU 预处理
5. MppVideoEncoder 替换视频软编码
6. RgaPreprocessor 替换 CPU 预处理
7. RtspPublisher
```

每替换一项：

1. 先用官方命令/示例独立证明硬件可用。
2. 实现现有接口，不改业务管道。
3. 添加对应 hardware test。
4. 运行所有 Mock 回归测试。
5. 保存正确性和性能基线。
6. 再进入下一个后端。

### 21.2 接入 V4L2 时复用什么

直接复用：

- `IVideoCapture`、`VideoFrame`、`Buffer`。
- VideoCaptureWorker。
- 视频队列和丢帧策略。
- 帧号、PTS、日志和指标。
- 断开/超时错误分类和恢复状态机。

只新增 `src/capture/v4l2` 的设备枚举、ioctl、MMAP 和 buffer 归还逻辑。

### 21.3 接入 ALSA 时复用什么

直接复用：

- `IAudioCapture`、`AudioFrame`。
- AudioCaptureWorker。
- 音频队列和时间戳。
- XRUN 错误类别和 Recover 契约。
- ChecksumAudioEncoder 用作 ALSA 输入的下游校验器。

只新增 PCM 设备选择、hw params、period/buffer、read 和 recover。

### 21.4 接入 RKNN/MPP/RGA 时复用什么

- RKNN 复用 `IInferenceEngine`、`DetectionBatch`、TransformMetadata、结果时效规则。
- MPP 复用 `IVideoEncoder`、`EncodedPacket`、Flush、PacketRouter 和 sinks。
- RGA 复用预处理输入/输出契约和 CPU 基线测试数据。

任何 Rockchip 专用类型都不能穿透到 `rkav_core` 公开头文件中。

## 23. 新手常见错误与正确做法

| 错误做法 | 为什么错 | 正确做法 |
|---|---|---|
| 把所有代码写在 `main.cpp` | 无法测试和替换后端 | main 只解析参数并调用 Application |
| 用无界 `std::queue` | 下游慢时内存无上限 | 所有跨线程队列有容量和溢出策略 |
| 每帧 `sleep_for(33ms)` | 30 FPS 会漂移 | 根据起点计算绝对 deadline |
| 用当前日期做 PTS | NTP 校时导致跳变 | 内部用 steady/monotonic clock |
| 视频和音频使用同一丢弃策略 | 音频会断裂 | 视频保新鲜，音频保连续并报 XRUN |
| 使用 detached thread | 无法确认何时退出 | worker 拥有 `std::jthread`并可 stop/join |
| 用随机 sleep 修复测试 | 隐藏竞态，CI 仍随机失败 | 使用 latch/barrier/condition predicate/ManualClock |
| 将 Mock packet 冒充 H.264 | 后续会产生假验收 | 使用专用 Mock codec 标识 |
| 队列满了就增大容量 | 只是增加延迟和掩盖瓶颈 | 先看下游耗时和正确丢弃策略 |
| 没摄像头就写死 `/dev/video0` | 真设备序号会变 | 接口和 selector 先定义，实测后接 V4L2 |
| 为解决权限全程 root | 放大安全风险 | 使用专用用户、设备组和最小路径权限 |
